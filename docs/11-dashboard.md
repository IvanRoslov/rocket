# Дашборд

## Решения

- **Стек:** TypeScript + React (Vite). Пакет `web/` в репозитории; продакшен-сборка — статика, которую раздаёт `rocketd` на `127.0.0.1:<port>`. Никакого отдельного сервера.
- **Данные:** только публичный API демона ([03-daemon-api.md](03-daemon-api.md)) — REST + SSE `/v1/events/stream`. Всё, что умеет дашборд, умеет и curl.
- **Главная единица UI — задача**, не сессия и не проект. Это принципиальное отличие от AO: сессии/tmux — техническая деталь под капотом карточки.

## Экран 0: Проекты (стартовый)

Верхний уровень UI — **проект** ([01-concepts.md](01-concepts.md)). Стартовый экран — сетка карточек проектов; в шапке всех остальных экранов — переключатель проектов (дропдаун с поиском). Канбан, задачи и сессии всегда показываются в рамках выбранного проекта.

Карточка проекта:

```
┌─────────────────────────────────┐
│ Биллинг                billing  │
│ ⌂ api  + web, infra             │  main-репо + linked
│ 2 in progress · 1 review        │  задачи по колонкам
│ ● 5 sessions live               │  живые оркестраторы/воркеры
│ ⚠ 1 problem · updated 12m ago   │  сигналы
└─────────────────────────────────┘
```

Клик — канбан проекта. Пустое состояние (нет ни одного проекта) — крупная кнопка «Создать проект» с одним предложением о том, что такое проект.

### Визард создания проекта

Кнопка «＋ проект» открывает трёхшаговый визард.

**Шаг 1 — имя.** Поле «Название» (человекочитаемое, например «Биллинг»); `id` генерируется из названия автоматически (латиница, `[a-z0-9-]`), редактируется по клику. Инлайн-валидация уникальности id.

**Шаг 2 — главный репозиторий.** Единый пикер репозитория с тремя вкладками:

- **GitHub** — список репозиториев аккаунта (`GET /v1/github/repos`): поиск по имени, бейдж private, default branch. Выбор → демон клонирует в `~/.rocket/repos/` (в визарде — прогресс клонирования; ошибка клона показывается тут же, с retry). Если токен не задан — вместо списка placeholder с кнопкой «Подключить GitHub» → инлайн-форма токена (та же, что в Settings), после сохранения список загружается без перезапуска визарда.
- **Зарегистрированные** — уже известные rocket'у репозитории (`GET /v1/repos`), с пометкой, в каких проектах они уже используются.
- **Локальный путь** — текстовое поле с автодополнением путей; демон валидирует, что это git-репозиторий, и показывает определённые origin и default branch перед подтверждением.

Подпись под шагом объясняет роль: «В главном репозитории поднимаются оркестраторы и живут документы продукта».

**Шаг 3 — linked-репозитории.** Тот же пикер, множественный выбор, список выбранных с удалением. Кнопка «Пропустить» — проект из одного репо (подпись: «Linked-репозитории — это где оркестраторы смогут запускать воркеров. Можно добавить позже»). Main-репо в списке недоступен (он и так входит в проект).

**Финал.** Экран-сводка (имя, main, linked) → «Создать» → `POST /v1/projects` → открывается пустой канбан проекта с подсказкой «Создайте первую задачу».

Визард переживает промежуточные действия: клонирование идёт в фоне (SSE-события прогресса), можно добавить несколько репо подряд.

### Настройки проекта

Шестерёнка на карточке проекта / в шапке канбана:

- переименование, правка id (с предупреждением);
- управление репозиториями: добавить/убрать linked (тот же пикер), сменить main (только когда нет активных сессий);
- удаление проекта — доступно только когда все задачи в done/cancelled и нет живых сессий; репозитории при этом остаются в реестре (отдельная страница Repos в Settings позволяет удалить и их).

### Settings

- **GitHub-токен**: поле ввода → `PUT /v1/settings` (демон валидирует токен запросом к GitHub и показывает, под каким аккаунтом авторизован). Токен замаскирован после сохранения.
- **Repos** — реестр репозиториев: путь, origin, кем клонирован (rocket/пользователь), в каких проектах используется; правка env/symlinks/post_create; удаление незанятых.
- Настройки демона — read-only справка (порт, интервалы, пути из config.yaml).

## Экран 1: Канбан (главный экран проекта)

Колонки: **Backlog → In Progress → Review → Done** (+ фильтр-переключатель Cancelled). Сверху: поиск по тексту.

Карточка задачи в колонке:

```
┌───────────────────────────────┐
│ #12 Биллинг v2                │
│ api → web, infra              │  main-репо + репо, где работают воркеры
│ ● orch: active   3 workers    │  живость оркестратора
│ ▸ 2 PR open · 1 merged · CI ✔ │  агрегат по подзадачам
│ ⚠ 1 problem · ？awaiting you   │  сигналы: проблемы, открытые вопросы
└───────────────────────────────┘
```

Бейдж «？ждёт ответа» — самый приоритетный сигнал карточки (выделен цветом): в задаче есть открытый тред, где очередь ответа за вами (`your_turn` в ответе API). Спросить может не только оркестратор задачи: тред — это список участников, и вопрос может прилететь от любого из них (см. [12-tasks.md](12-tasks.md), «Вопросы и ответы через задачу»). Видеть тред и быть в очереди по нему — намеренно разные вещи: тред, адресованный через `--to` кому-то другому, вы по-прежнему видите в списке, но бейджа он не зажигает. Тот же индикатор — на карточке проекта на стартовом экране.

Бейдж «⏳ waiting for input» (тон `warn`, как и точка `waiting_input`) — сессия задачи висит на интерактивном вопросе в терминале дольше `input_stall_threshold` (производное поле `waiting_terminal`, см. [03-daemon-api.md](03-daemon-api.md)). Никто не печатает — задача не двигается, хотя статус у неё `in_progress`. Гаснет сам, как только квиз закрыт.

Действия прямо на карточке: перетаскивание между колонками (= `task move`), кнопка attach (копирует `rocket attach 12`), кнопка «＋ задача» в Backlog. Из Backlog кнопка **Start** — создаёт оркестратора (модалка: выбор агента).

Live-обновления через SSE: смена активности, PR, статусы двигают карточки без перезагрузки.

## Экран 2: Карточка задачи

Открывается кликом по карточке. Слева — контент, справа — рейл сессий.

**Баннер вопросов (над табами).** Если у задачи есть открытые вопросы — они показаны первым делом. Каждый вопрос — **мини-тред**: исходный вопрос (+ раскрываемый markdown-контекст), реплики диалога, и внизу поле ввода с двумя действиями:

- **«Уточнить»** — реплика в тред (`POST /v1/questions/{id}/reply`): «не понял, переформулируй», «раскрой подробнее», «покажи пример». Вопрос остаётся открытым, очередь переходит к остальным участникам; когда кто-то ответит в тред — бейдж «ждут вас» загорится снова. Реплику можно адресовать конкретному участнику (`to`) — тогда ждут только его: так вопрос делегируется, например, постоянному агенту `cto`.
- **«Ответить и закрыть»** — финальный ответ (`POST /v1/questions/{id}/answer`), вопрос уходит в resolved. Рядом — «Закрыть как неактуальный».

Тред показывает список своих участников. Закрыть тред может не только человек: то же право есть у постоянных агентов, поэтому вопрос может уйти в resolved без вашего участия — например, когда вы делегировали ответ. Статус доставки каждой реплики виден как у обычного сообщения. Resolved-треды сворачиваются в Journal целиком.

**Левая колонка (табы):**

- **Overview** — описание задачи; дерево подзадач со статусами, воркерами и PR (декомпозиция как её сделал оркестратор); финальный `report`-документ, когда есть.
- **Docs** — документы задачи (`spec`, `plan`, `report`, …) с версиями; рендер markdown.
- **Journal** — полная хронология задачи: решения, проблемы, заметки, вопросы с ответами, автозаписи о статусах/спавнах/PR. Проблемы и открытые вопросы подсвечены. Фильтр по kind и автору. Это ответ на «как шла задача» — одна лента от создания до done.
- **Messages** — переписка: пользователь ↔ оркестратор ↔ воркеры (из истории очереди сообщений). Поле ввода → `POST /v1/messages` оркестратору: можно отвечать оркестратору прямо из карточки, не заходя в терминал.
- **Chat** — полное зеркало нативного транскрипта оркестратора (не только сообщения человека, но и ходы/тулзы самого агента), с композером внизу для отправки через ту же очередь сообщений. Контракт эндпоинта, семантика курсора, SSE-пинг обновления и статусы отправки — см. [13-chat.md](13-chat.md). Композер есть только у оркестратора; в SessionRail воркеров та же лента показывается read-only, без композера.
- **Квизы в чате** — когда агент задаёт вопрос через AskUserQuestion, чат показывает интерактивный квиз-пузырь (кнопки для одиночного выбора, чекбоксы для множественного, поле «свой вариант») из `pending_quiz` сессии; ответ уходит в `POST /v1/sessions/{id}/quiz/answer`, демон сам нажимает кнопки в TUI. Пока квиз открыт — композер блокируется (сообщения всё равно не доставляются). Закрытые квиз-раунды рендерятся в ленте из пары записей tool+`quiz_answer`. Полный контракт, SSE-события (`session.quiz_asked/quiz_resolved/quiz_answer_unconfirmed`) и краевые случаи — раздел «Квизы» в [13-chat.md](13-chat.md). Это ключевой примитив для мобильного приложения: терминал на тач-экране непригоден, а чат + квизы покрывают весь цикл общения с оркестратором без терминала.

**Правый рейл — сессии задачи:**

```
Orchestrator  billing-v2-orch      ● active
  [attach ⧉] [output] [kill]
Workers
  billing-v2-backend  api   ● ready   PR #14 ✔
  billing-v2-ui       web   ● blocked PR — 
  [attach ⧉] [output] [restore] [kill]
```

- **term ▣** — главный способ взаимодействия: открывает **живой терминал сессии** прямо в дашборде (xterm.js поверх WS `/v1/sessions/{id}/term`, см. [03-daemon-api.md](03-daemon-api.md)). Открывается панелью снизу карточки задачи (не отдельной страницей — контекст задачи остаётся на экране); полноценный ввод, ресайз, копипаста. Можно смотреть и печатать одновременно с локальным tmux-клиентом — это просто ещё один attach.
- **attach ⧉** — для работы в своём терминале: копирует команду `rocket attach <session>` в буфер (Warp и любой другой).
- Индикаторы активности в реальном времени из SSE.

## Экран 2b: Agents — постоянные агенты

`/agents` — **глобальный** список всех агентов, сгруппированный по проектам, с
секцией «No project» в конце и чипсами-фильтрами (All / проект / No project).
Проект у агента необязателен ([10-agents.md](10-agents.md)), поэтому таб Agents
в шапке ведёт именно сюда: агент без проекта иначе не виден нигде (таб Kanban
по-прежнему ведёт на последний открытый проект). `/p/<project>/agents` остаётся
тем же экраном, отфильтрованным по проекту.

Сетка карточек агентов: id, описание, бейджи «● live» (живость сессии по
`session_alive`), «N unread» (инбокс), «awaiting you» (агент ждёт вашего ответа
в треде), «disabled». На карточке — ссылки «▣ term» и «💬 chat» на те же
полноэкранные страницы `/term/<id>` и `/chat/<id>` (сессия агента называется его
id), задизейбленные с подсказкой, пока сессия мёртвая, и «⧉ attach», копирующая
`rocket agent attach <id>` — она работает всегда.

Кнопка «＋ New agent» открывает форму регистрации: id, описание и необязательная
пара лончера `dir`/`command`; в глобальном виде добавляется выбор проекта со
значением «— no project —» по умолчанию. Та же форма в режиме правки — с
карточки агента (id менять нельзя).

Карточка агента (`/p/<project>/agents/<agent>`, либо `/agents/<agent>` для
агента без проекта) — шапка с описанием,
`dir`/`command` и действиями (поле сообщения + Send, Terminal/Stop при живой
сессии либо Start при мёртвой, Enable/Disable, Edit, Delete) и два таба:

- **Questions** — Q&A-треды агента (тот же компонент, что у задач: уточнить /
  ответить и закрыть / закрыть как неактуальный), resolved свёрнуты; внизу
  композер «спросить агента» — открывает тред, текст доезжает агенту так же,
  как обычное сообщение;
- **Inbox** — сообщения инбокса (`from`, тело, `unread|read`, возраст) с
  фильтром по статусу. Помечает прочитанным сам агент (`rocket inbox next`),
  дашборд только смотрит.

**Отправка сообщения.** Поле в шапке шлёт `POST /v1/agents/{id}/messages` — тот
же живой-или-инбокс путь, что у `rocket send`: живой сессии текст уходит в
очередь, мёртвой ложится в инбокс.

**Терминал.** Tmux-сессия агента называется его id, поэтому кнопка Terminal
делает attach к сессии `<id>` в том же оверлее, что у задач. Сессии нет —
вместо Terminal кнопка Start (`POST /v1/agents/{id}/start`); агент без `dir`
получает от демона `agent_no_dir`, и ошибка показывается как есть.

Бейдж «？N agents awaiting you» — на карточке проекта в общем списке, той же
визуальной группой, что «ждёт ответа» у задач.

## Экран 3: Системный (наблюдаемость)

Аналог Resources-страницы из форка AO, вторичный экран:

- живые tmux-сессии и процессы агентов (в т.ч. осиротевшие — есть в tmux, нет в базе, и наоборот);
- worktree на диске и их размер;
- очередь сообщений: queued/failed;
- статус демона, лог-хвост, версия;
- kill/cleanup одной кнопкой.

## Не входит в v1 дашборда

Голосовой ввод, нотификации, мобильная вёрстка. Архитектурно ничего им не мешает — API демона остаётся единственным источником.

## Сборка

`cd web && npm run build`; `web/dist/index.html` — tracked-плейсхолдер, не коммитить собранный.

## Мобильный клиент

Отдельное приложение `mobile/` (Expo / React Native) поверх того же API демона: несколько серверов в локальной сети, SSE-обновления, интерактивный терминал по WebSocket. Требует `host: 0.0.0.0` в конфиге демона. Подробности — `mobile/README.md`.
