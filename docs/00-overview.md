# rocket — обзор

## Что это

**rocket** — инструмент оркестрации AI-кодинг-агентов поверх tmux и git worktree. Состоит из двух частей:

- **`rocketd`** — демон (Go, один процесс на машину): владеет всем состоянием и всей логикой — спавн сессий, очередь сообщений, мониторинг активности агентов, heartbeat, интеграция с GitHub.
- **`rocket`** — CLI (тот же бинарник, тонкий клиент): все команды ходят в демон через Unix-сокет. Демон автозапускается при первой команде.

Позже добавляется **дашборд** (TS + React), работающий поверх того же API демона.

## Зачем, если есть agent-orchestrator

rocket — идейный наследник [agent-orchestrator](https://github.com/AgentWrapper/agent-orchestrator) (AO) и форка [IvanRoslov/agent-orchestrator](https://github.com/IvanRoslov/agent-orchestrator) с фичей cross-project оркестраторов. AO упёрся в два архитектурных ограничения:

1. **Концепция главного оркестратора.** В AO на проект существует один фиксированный оркестратор, управляющий всем; feature-оркестраторы форка были прикручены поверх этой модели (нумерованные сессии, привязка воркеров конвенцией имени ветки). В rocket главного оркестратора нет вообще — см. модель ниже.
2. **Переусложнённость.** AO тащит плагинную систему на 7 слотов, 7 агентов, 3 трекера, 4 нотификатора, Windows/ConPTY, портфолио-режим и т.д. Дорабатывать ядро тяжело. rocket — минимальное ядро только из того, чем реально пользуемся.

## Модель: плоская оркестрация

```
пользователь
   ├── оркестратор A (фича "billing-v2", хаб: proj-api)
   │      ├── воркер a1 (proj-api,   ветка feature/billing-v2/backend)
   │      ├── воркер a2 (proj-web,   ветка feature/billing-v2/ui)
   │      └── воркер a3 (proj-infra, ветка feature/billing-v2/migrations)
   ├── оркестратор B (фича "fix-auth", хаб: proj-web)
   │      └── воркер b1 (proj-web, ветка feature/fix-auth/main)
   └── ...
```

- **Всё начинается с задачи.** Пользователь описывает задачу (канбан: backlog → in_progress → review → done) и назначает на неё оркестратора; декомпозиция, документы, решения и проблемы стекаются обратно в задачу.
- **Оркестратор = фича.** Пользователь запускает оркестратор командой `rocket up "<описание>"` под конкретную задачу. Оркестратор эфемерен: живёт, пока фича не готова, и умирает. Постоянных оркестраторов нет.
- Оркестраторов может быть сколько угодно параллельно, в том числе на один проект.
- Оркестратор спавнит **воркеров** в своём проекте и в **связанных** проектах (`links` в реестре). Один воркер = одна задача = одна ветка = один worktree = один PR.
- Воркеры общаются только со своим оркестратором (question funnel), оркестратор — с пользователем.
- Привязка воркер↔оркестратор **явная** (поле `parent_id` в состоянии демона), а не через конвенцию имени ветки, как в AO.

## Ключевые принципы

- **Одна точка правды.** Всё состояние — в демоне (SQLite). CLI не читает и не пишет файлы состояния напрямую; никаких file-locks и гонок между CLI-вызовами, как в AO.
- **Надёжная доставка сообщений.** `rocket send` кладёт сообщение в очередь демона и возвращается сразу; демон доставляет, когда получатель idle. История сообщений сохраняется.
- **Детекция активности через hooks агента**, не через regex по терминалу.
- **Минимализм.** Нет трекеров задач, нотификаторов, плагинного реестра. Интерфейсы (Runtime, Workspace, Agent) — внутренние Go-интерфейсы, а не плагинная экосистема.
- **Мульти-агентность с первого дня интерфейса.** v1 поддерживает Claude Code и Codex через общий интерфейс `Agent`.
