# Чат с сессией

## Что это

Зеркало нативного транскрипта агента (claude-code: `~/.claude/projects/<slug>/*.jsonl`; codex: `~/.codex/sessions/YYYY/MM/DD/*.jsonl`), а не отдельная сущность. Ходы агента, инжектированные сообщения (`[from …]`) и реплики человека — уже есть в транскрипте; демон только парсит его и отдаёт как ленту. Ничего не дублируется в SQLite: транскрипт и есть хранилище, поэтому история чата переживает cleanup worktree и смерть сессии (пока жив сам файл транскрипта).

Чат = лента чтения (`GET .../chat`) + отправка через уже существующую очередь сообщений (`POST /v1/messages`, см. [06-messaging.md](06-messaging.md)) — это два независимых механизма, соединённых одним экраном.

## Эндпоинт: лента

```
GET /v1/sessions/{id}/chat?cursor=<opaque>&limit=<N>
```

**Параметры:**

- `cursor` — непрозрачный токен. Клиент **хранит и возвращает как есть**, не парсит и не модифицирует. Пустой (или отсутствующий) `cursor` означает «хвост» — то есть первый заход в экран.
- `limit` — по умолчанию `200`, максимум `1000`. К первому хвостовому запросу (`cursor=""`) применяется напрямую: демон возвращает последние `limit` записей транскрипта. К инкрементальным запросам (`cursor` непустой) в обычном случае не применяется — такой ответ возвращает **все** записи после курсора без обрезки (они по построению небольшие: чат читается достаточно часто, чтобы прирост между запросами был мал). Но `limit` всегда действует как страховка: если курсор оказался невалиден (файл транскрипта удалён/провернулся, либо адаптер отверг курсор как выходящий за пределы своей транскрипт-директории), демон откатывается к чтению с начала текущего транскрипта — и в этом случае ответ тоже обрезается до последних `limit` записей, а не отдаёт всю историю целиком. Клиенты должны быть готовы к повторной доставке уже показанных записей после такого отката и дедуплицировать (или просто перерисовывать ленту) по своему усмотрению.

**Ответ `200`:**

```json
{
  "entries": [
    {"role": "user", "text": "почему упал тест biling_test.go?", "ts": 1755550800},
    {"role": "assistant", "text": "смотрю на трейс", "ts": 1755550802},
    {"role": "tool", "tool_name": "Bash", "text": "{\"command\":\"go test ./internal/billing/...\",\"description\":\"Run billing tests\"}", "ts": 1755550803},
    {"role": "assistant", "text": "нашёл: гонка в billing.Reconcile, фикс отправлю", "ts": 1755550810}
  ],
  "next_cursor": "/Users/ivan/.claude/projects/-Users-ivan-rocket-wt-billing/sess.jsonl:48213",
  "session": {"id": "billing-v2-orch", "kind": "orchestrator", "state": "running", "activity": "active"}
}
```

Поля записи (`entries[]`):

- `role` — `"user"` | `"assistant"` | `"tool"`.
- `text` — текст реплики; для `role="tool"` — однострочный дайджест **входа** инструмента: компактный JSON аргументов вызова (не голая команда и не вывод), усечённый до **120 рун** с `…` на конце (для некоторых codex-инструментов — например `apply_patch`, чей вход в транскрипте не JSON, а обычный текст-патч — это просто свёрнутый в одну строку исходный текст входа, не JSON). Планируйте ширину tool-строк в UI под это.
- `tool_name` — присутствует только при `role="tool"` (например `"Bash"`, `"Edit"`); в остальных случаях поле опущено (`omitempty`).
- `ts` — unix-секунды из записи транскрипта; `0`, если у записи нет метки времени.

`session` — минимальная карточка сессии (`id`, `kind`, `state`, `activity`), удобная, чтобы не делать отдельный `GET /v1/sessions/{id}` только ради заголовка экрана чата.

`next_cursor` — курсор для следующего инкрементального запроса. Пустая строка означает «нет сигнала» (см. пустую ленту ниже), не «конец истории» — история продолжает пополняться, пока сессия/агент активны.

**Пустая лента** (сессия только что заспавнена и транскрипта ещё нет, либо демон не может определить агента сессии) — это **`200`** с `{"entries":[],"next_cursor":""}`, не ошибка.

**Ошибки:**

- `404 session_not_found` — сессии с таким `id` нет в сторе.
- `502 transcript_error` — транскрипт есть, но чтение/парсинг файла упало (не то же самое, что «транскрипта пока нет» — это отдельный отказ). На практике оба адаптера (claude-code и codex) сводят большинство ошибок чтения к тому же «нет сигнала», что и отсутствующий транскрипт, — то есть к пустой ленте `200` (см. выше), а не к `502`. Код `502` тем не менее задокументирован и клиенты обязаны уметь его обработать (это контракт на будущее и для файловых ошибок, которые адаптер не поглощает), но на практике он редок.

## SSE: `session.chat_updated`

Публикуется в существующий поток `GET /v1/events/stream` (см. [03-daemon-api.md](03-daemon-api.md)):

```
event: session.chat_updated
data: {"id":123,"ts":1755550811,"type":"session.chat_updated","session_id":"billing-v2-orch"}
```

- Событие — **чистый пинг**: контента чата в нём нет, а поле `data` у пингов **отсутствует целиком** (omitempty) — не пишите клиентский код, который его деструктурирует. Получив событие, клиент должен дёрнуть `GET .../chat?cursor=<последний next_cursor>` и добавить новые записи в конец ленты.
- Публикуется монитором раз в тик (`activity_poll_interval`, по умолчанию **5 секунд**) — то есть событие может отставать от реального изменения транскрипта на этот интервал, и не чаще одного пинга за тик даже при нескольких изменениях подряд.
- Событие **best-effort**: если у сессии нет транскрипта, агент не резолвится, либо `TranscriptStat` временно упал — пинг просто не публикуется в этот тик, без ретраев и без ошибки клиенту. Поэтому клиентам рекомендуется держать периодический фолбэк-поллинг ленты (например, раз в несколько секунд) поверх подписки на SSE, а не полагаться на событие как на единственный источник обновлений.

## Отправка сообщений

Отправка идёт через существующий `POST /v1/messages` — отдельного эндпоинта для чата нет:

```
POST /v1/messages
{"to": "billing-v2-orch", "body": "давай без миграции, просто фикс кода"}
```

`from` не передаётся, когда пишет человек из дашборда/мобильного (значение по умолчанию — пусто, в транскрипте это будет обычная user-реплика без префикса `[from …]`).

Ответ `201 {"id": 42, "status": "queued"}`. Ошибки: `404 session_not_found`; **`409 recipient_terminal`** — получатель уже убит/завершён, сообщение не принимается (покажите пользователю сразу). Статус принятого сообщения дальше отслеживается через `GET /v1/messages?session=<id>` (см. [06-messaging.md](06-messaging.md)): `queued` → `delivering` → `delivered`, либо `failed` (с полем `reason` — покажите его пользователю как есть, не глотайте).

**Большие сообщения рендерятся в ленте иначе — учитывайте это.** Тексты сверх `large_message_threshold` (по умолчанию 2048 байт, либо 20 строк) для получателя с воркспейсом уходят файлом в `<worktree>/.rocket/inbox/msg-<id>.md`, а в терминал агента инжектируется только короткий указатель: `[large message] Full text written to .rocket/inbox/msg-<id>.md — read that file now.` В транскрипт — и значит в ленту чата — попадает **этот указатель, а не исходный текст**. Наивная optimistic-подмена «плейсхолдер → запись из транскрипта» молча заменит текст пользователя на служебную строку. Рекомендация: сохраняйте optimistic-пузырь с исходным текстом как постоянный элемент, а транскрипт-запись с префиксом `[large message]` для СВОЕГО последнего отправленного сообщения схлопывайте в статус доставки (или помечайте «доставлено файлом»).

## Квизы (AskUserQuestion)

Когда агент (только claude-code; у codex такого виджета нет) вызывает интерактивный инструмент `AskUserQuestion`, в его терминале открывается TUI-квиз: вопросы с опциями (одиночный выбор или чекбоксы) и свободным вариантом «Type something». Демон делает этот квиз полностью доступным удалённо — клиент рендерит его как интерактивный пузырь в чате и отвечает кнопками, а демон транслирует выбор в нажатия клавиш в tmux.

**Важно про транскрипт:** пока квиз на экране, в JSONL-транскрипте агента НЕТ ни байта о нём — Claude Code пишет tool_use и ответ одной пачкой только после закрытия квиза. Поэтому «живой» квиз приходит не из ленты, а из отдельного состояния сессии (`pending_quiz`), которое демон получает через свой PreToolUse-хук в момент показа. Лента показывает квиз-раунды только задним числом, уже закрытыми.

### Pending-квиз: обнаружение

- Событие SSE **`session.quiz_asked`** (чистый пинг, без контента, поле `data` отсутствует целиком — как у `chat_updated`). Получив его, клиент дёргает `GET /v1/sessions/{id}` или ленту чата.
- Поле **`pending_quiz`** (omitempty) присутствует в `GET /v1/sessions/{id}`, в списке сессий и в `session{}` ответа `GET .../chat`:

```json
"pending_quiz": {
  "questions": [
    {"question": "Какую стратегию мержа выбрать?", "header": "Мерж", "multi_select": false,
     "options": [
       {"label": "Merge commit", "description": "история сохраняется"},
       {"label": "Squash", "description": "одним коммитом"}
     ]},
    {"question": "Что включить в релиз? (можно несколько)", "header": "Релиз", "multi_select": true,
     "options": [{"label": "Доки"}, {"label": "Миграции"}, {"label": "CLI"}]}
  ],
  "asked_at": 1755551000
}
```

Пока `pending_quiz` непустой — показывайте интерактивный квиз-пузырь и **блокируйте композер** (конвенция клиента: обычное сообщение всё равно не будет доставлено, см. ниже; и оно не является ответом на квиз).

### Ответ

```
POST /v1/sessions/{id}/quiz/answer
{"answers": [
  {"question_index": 0, "option_indices": [1]},
  {"question_index": 1, "option_indices": [0, 2]},
  {"question_index": 2, "text": "свой вариант текстом"}
]}
```

- По каждому вопросу — ровно одно из двух: `option_indices` (индексы опций из `pending_quiz`, 0-based; для `multi_select:false` ровно один индекс) или `text` (непустой — свободный вариант «Other»). Отвечены должны быть **все** вопросы.
- Успех — **`202 {"status":"answering"}`**: демон начал печатать ответ в TUI. Фактическое закрытие квиза подтверждает событие **`session.quiz_resolved`** (и очистка `pending_quiz`) — до него держите пузырь в состоянии «отправляется».
- Ошибки: `404 session_not_found`; `409 no_pending_quiz` (квиза уже нет — например, ответили в терминале; перерисуйте по `quiz_resolved`); `409 quiz_answer_in_flight` (предыдущий POST ещё печатается — не ретраить, ждать `quiz_resolved`); `400 quiz_answer_invalid` (детали в message: индекс вне диапазона, для одиночного выбора не ровно один индекс, `option_indices` вместе с `text`, пустой `text`, отвечены не все вопросы, **опций больше 9** — удалённый ответ умеет печатать только однозначные номера).
- Если демон напечатал ответ, но `quiz_resolved` не пришёл за 60 секунд — публикуется **`session.quiz_answer_unconfirmed`** (тоже пустой пинг): покажите пользователю «не удалось подтвердить — проверьте терминал». `pending_quiz` при этом не очищается.

### Квиз-раунды в ленте

После закрытия квиза его раунд появляется в ленте (следующий `chat_updated`/поллинг):

- Запись `role:"tool"`, `tool_name:"AskUserQuestion"` получает дополнительное поле **`quiz`** — полный JSON вопросов/опций из tool-входа (в нём `multiSelect` в camelCase — это сырой формат Claude Code, в отличие от snake_case в `pending_quiz`). Поле `text` остаётся обычным 120-рунным дайджестом — для рендера квиза используйте `quiz`.
- Ответ — отдельная запись **`role:"quiz_answer"`**: `text` — готовая построчная сводка («вопрос → выбор»; для отменённого квиза — «квиз отменён»), `quiz` — сырой echo результата (`questions` + `answers`, map «текст вопроса → выбранный label»; для multi-select значения — склейка labels, разделитель между версиями CLI нестабилен — показывайте как есть, не сплитуйте).
- У прочих инструментов поля `quiz` нет (omitempty).

Рекомендация UI: рендерите закрытый квиз одним пузырём (вопросы + подсвеченные выбранные опции) из пары tool+quiz_answer; «живой» — из `pending_quiz` с кнопками.

### Очередь сообщений во время квиза

Пока у сессии есть `pending_quiz`, доставка обычных сообщений ей **приостановлена** (они остаются `queued` — инжекция текста сломала бы TUI-виджет) и возобновляется сразу после закрытия квиза. Ещё одна причина блокировать композер на время квиза.

### Краевые случаи

- **Ответили в терминале параллельно** — PostToolUse-хук всё равно закроет квиз: придёт `quiz_resolved`, ваш POST (если успел) получит `409 no_pending_quiz`. Это штатно.
- **Esc / отмена в терминале** — тоже `quiz_resolved`, но с задержкой: Claude Code не репортит отклонённый tool call хуками, поэтому отмену обнаруживает фоновый монитор демона (по исчезновению виджета из pane) — `quiz_resolved` придёт через ~10–20 секунд после Esc, а не мгновенно. Успешный ответ (в терминале или через API) закрывается хуком за секунды. В ленте отменённый раунд появится с `quiz_answer` «квиз отменён».
- **Рестарт демона** — `pending_quiz` хранится в SQLite и переживает рестарт.
- **Демон был недоступен в момент показа квиза** — хук не дозвонился (он никогда не блокирует агента), `pending_quiz` не появится: квиз виден только в терминале. Деградация без ретраев, осознанно.

## Жизненный цикл экрана

1. **Открытие карточки/чата** — `GET /v1/sessions/{id}/chat` без `cursor` (хвост, `limit` по вкусу экрана, обычно default). Рендерим `entries`, запоминаем `next_cursor`.
2. **Подписка на SSE** — `GET /v1/events/stream?session={id}` (или общий поток, если экран уже держит его открытым для других целей), слушаем `session.chat_updated`.
3. **На событие `chat_updated`** — `GET .../chat?cursor=<сохранённый next_cursor>` (без `limit`, он тут не нужен), дописываем полученные `entries` в конец ленты, обновляем `next_cursor` из ответа. Плюс периодический фолбэк-запрос тем же способом, на случай пропущенного SSE-пинга.
4. **Отправка** — `POST /v1/messages {to, body}`; сразу же **optimistic-рендер** реплики в ленте (со статусом «отправляется»), затем статус подтягивается из `GET /v1/messages?session={id}` (или из событий `message.delivered`/`message.failed`) и подменяет плейсхолдер на актуальный (`✓`/`⏳`/`✗ + reason`). Сама реплика в транскрипте появится тоже — следующий `chat_updated`/поллинг её подтянет как обычную запись; дублирования избегаем тем, что optimistic-плейсхолдер — это статус отправки, а не постоянный элемент ленты.

## Ограничения и клиентские конвенции

- **Композер — только для оркестраторов.** Писать человеку в оркестратора можно; воркерам — нет (это конвенция клиента: сервер технически не запрещает `POST /v1/messages` к воркеру, но UI не должен давать такую возможность — question funnel воркер↔оркестратор должен оставаться единственным каналом воркера с внешним миром). SessionRail для воркеров показывает ту же ленту чата, но без композера — read-only.
- **Q&A-треды — отдельный механизм.** Вопросы оркестратора (`POST /v1/tasks/{id}/questions`, `POST /v1/questions/{id}/reply|answer`, см. [03-daemon-api.md](03-daemon-api.md)) чат не подменяет и не поглощает — они показываются отдельным баннером/вкладкой Questions над лентой чата, со своим потоком реплик и статусом open/resolved.
- **Лента best-effort.** Строки транскрипта, которые адаптер не смог распарсить (незавершённая последняя строка на момент чтения, служебные/неизвестные типы записей), молча пропускаются — не считайте отсутствие какой-то реплики в ленте багом сихронизации.
- **Пагинации назад нет.** Первый запрос отдаёт только хвост (`limit` последних записей); углубиться в историю раньше этого хвоста через API в v1 нельзя.
- **История переживает сессию.** Чат читается и после того, как сессия убита/завершена — пока жив файл транскрипта агента на диске. Экран чата может оставаться доступным для просмотра (без композера, конечно — получателя-то больше нет) на «мёртвых» сессиях.

## curl-примеры

Первый (хвостовой) запрос:

```bash
curl -s "http://127.0.0.1:4477/v1/sessions/billing-v2-orch/chat?limit=50"
```

Инкрементальный запрос по курсору из предыдущего ответа:

```bash
curl -s "http://127.0.0.1:4477/v1/sessions/billing-v2-orch/chat?cursor=%2FUsers%2Fivan%2F.claude%2Fprojects%2F-Users-ivan-rocket-wt-billing%2Fsess.jsonl%3A48213"
```

Отправка сообщения оркестратору:

```bash
curl -s -X POST http://127.0.0.1:4477/v1/messages \
  -H 'Content-Type: application/json' \
  -d '{"to":"billing-v2-orch","body":"давай без миграции, просто фикс кода"}'
```
