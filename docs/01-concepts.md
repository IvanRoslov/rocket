# Сущности и жизненные циклы

## Repository

Зарегистрированный в глобальном реестре git-репозиторий — техническая единица, в которой rocket создаёт worktree и сессии.

Поля (реестр — таблица в базе демона, см. [05-state.md](05-state.md)):

- `id` — короткое уникальное имя (`api`, `web`, `infra`). Используется в именах путей.
- `path` — абсолютный путь к основному чекауту репозитория.
- `default_branch` — база для новых веток (обычно `main`).
- `env` — дополнительные переменные окружения для сессий в этом репо.
- `post_create` — shell-команды после создания worktree (установка зависимостей и т.п.).
- `symlinks` — относительные пути, которые симлинкуются из основного чекаута в worktree (например `node_modules`, `.env`).

Регистрация: `rocket repo add <path>` (id выводится из имени директории, можно переопределить) или из UI дашборда.

## Project

Верхняя пользовательская сущность — продукт, над которым идёт работа. Состоит из репозиториев:

- `id`, `name` — идентификатор и человекочитаемое имя.
- `main` — главный репозиторий: в нём поднимаются оркестраторы, живут доки продукта.
- `linked` — список дополнительных репозиториев, в которых оркестраторы проекта могут спавнить воркеров. Может быть пустым — проект из одного главного репо (код и доки вместе).

Внутри проекта живут канбан и задачи: пользователь выбирает проект, видит его доску, создаёт задачи и запускает фича-оркестраторов. Один репозиторий может входить в несколько проектов. Создание — `rocket project create` или UI дашборда ([11-dashboard.md](11-dashboard.md)).

## Session

Единица работы: tmux-сессия + git worktree + запущенный агент. Общие поля:

- `id` — глобально уникальное имя, совпадает с именем tmux-сессии.
- `kind` — `orchestrator` | `worker`.
- `project_id` — проект, к которому относится работа.
- `repo_id` — репозиторий, в котором создан worktree (у оркестратора — main репо проекта).
- `branch`, `worktree_path`.
- `agent` — какой агент запущен (`claude-code`, `codex`).
- `parent_id` — для воркера: id его оркестратора; для оркестратора — NULL.
- `feature_slug` — slug фичи (у оркестратора и всех его воркеров одинаковый).
- `state` — жизненный цикл сессии (см. ниже).
- `activity` — текущая активность агента (см. [07-activity.md](07-activity.md)).
- `pr_number`, `pr_state`, `ci_state` — для воркера (см. [09-github.md](09-github.md)).
- `created_at`, `updated_at`.

### Именование

- Оркестратор: `<feature-slug>-orch` (например `billing-v2-orch`). При коллизии slug получает суффикс `-2`, `-3`.
- Воркер: `<feature-slug>-<task>` (например `billing-v2-backend`). `<task>` задаёт оркестратор при спавне.
- Ветка воркера: `feature/<feature-slug>/<task>`. Ветка оркестратора: `orch/<feature-slug>`.
- Допустимые символы id: `[a-z0-9-]`, tmux-таргеты всегда используют exact-match (`=name`).

### Жизненный цикл сессии (`state`)

```
spawning → running → done | killed | errored
```

- `spawning` — создаётся worktree, стартует tmux и агент.
- `running` — агент работает; детали см. в `activity` и PR-полях.
- `done` — работа завершена штатно (для воркера — PR смержен и cleanup выполнен; для оркестратора — фича закрыта).
- `killed` — убита пользователем или оркестратором.
- `errored` — спавн или восстановление не удались.

Терминальные состояния: `done`, `killed`, `errored`. Богатая машина статусов AO (18 статусов) сознательно не воспроизводится: производные вещи (`pr_open`, `ci_failed`, `stuck`) — это отдельные поля/события, а не состояния жизненного цикла.

## Orchestrator

Эфемерная сессия `kind=orchestrator`, создаётся `rocket up "<описание>" [--project <id>]` или `rocket task start`:

1. Демон генерирует `feature_slug` из заголовка задачи.
2. Создаёт worktree в **main-репозитории проекта** на ветке `orch/<slug>`.
3. Запускает агента с системным промптом оркестратора и kickoff-сообщением (см. [08-orchestrators.md](08-orchestrators.md)).

Права оркестратора: спавнить/убивать воркеров только в репозиториях своего проекта (main + linked); слать сообщения своим воркерам и получать от них; открывать PR в main-репо (например, с фичевым дизайн-доком).

## Worker

Сессия `kind=worker`, создаётся оркестратором через `rocket spawn`. Инварианты:

- ровно один родитель (`parent_id`), заданный при спавне;
- одна задача, одна ветка, один worktree, один PR;
- не общается с пользователем — все вопросы через `rocket send` родителю;
- при merge PR демон выполняет авто-cleanup (tmux + worktree; ветка остаётся).

## Task

Первоклассная запись фичи в базе демона и единица канбана: `backlog → in_progress → review → done`. Пользователь создаёт задачу, назначает на неё оркестратора; демон автоматически создаёт подзадачи под каждого воркера и двигает их статусы по PR-циклу. Оркестратор и воркеры складывают в задачу документы (spec/plan/report) и журнал решений и проблем. Задача переживает сессии и worktree — это durable-история фичи. Подробно: [12-tasks.md](12-tasks.md).

## Milestone

Корневая задача **вне всех проектов**, которую берёт себе постоянный агент (`cto`, `sre`), — единица его собственной работы, а не фичи с оркестратором и воркерами. Признак — колонка `tasks.milestone`, держатель — `tasks.assigned_role` (пусто = не взят). Всё остальное у майлстона такое же, как у задачи: статусы, документы, журнал, вопросные треды.

Отличия от обычной задачи ровно три: у него нет проекта и родителя; он не запускается (`rocket task start` отвечает `403`), а **берётся** агентом (`rocket task take`) или назначается человеком (`rocket task assign`); в `review` он не уходит, пока агент не показал работу, а `done`/`cancelled` ставит только человек. Подробно: [12-tasks.md](12-tasks.md), раздел «Майлстоны».

## Message

Запись очереди в демоне: `id, from_session, to_session, body, status(queued|delivering|delivered|failed), attempts, created_at, delivered_at`. Подробности — [06-messaging.md](06-messaging.md).

## Event

Append-only журнал всего значимого: спавны, смены активности, доставки сообщений, PR/CI-переходы, heartbeat-пробуждения, cleanup. Используется для `rocket events`, отладки и SSE-потока дашборда.
