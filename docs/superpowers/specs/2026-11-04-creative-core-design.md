# Creative workflow foundation (5987 / creative-work)

> Pipeline ownership and filtering below are superseded by [the global catalog correction](2026-11-04-global-pipelines-design.md), approved for creative-work 5986 / subtask 5994. Templates are global; runs remain project-owned.

Separate SQLite tables for creative pipelines, runs, stage instances and items preserve the existing task lifecycle and kanban. Reusing tasks would couple creative work to development gates; a separate external state store would duplicate project/auth infrastructure. This design uses the existing store and API with no launch or generation side effects.

Pipelines belong to a project and contain an ordered `stages` array. Each definition has `name`, `description`, `expected_artifacts`, `repeated`, `approval` (`auto`, `stage`, or `item`; item requires repeated). Updating the whole array edits/reorders it. Runs copy pipeline name and all stage definitions on creation, with an initial `brief`, `name`, existing `project_id`, and source `pipeline_id`. Pipeline updates never modify runs.

All IDs are positive SQLite integers, separately namespaced by entity. Stage IDs and item IDs are globally unique within their tables, immutable, and reference their parent. Artifact/discussion context is `{run_id, stage_id?, item_id?}`; item requires stage. A store resolver verifies ancestry and returns project and orchestrator identity. Siblings reference `creative_runs(id)`, `creative_stages(id)`, `creative_items(id)`; no task rows are created.

Stage and item states: `pending`, `in_progress`, `awaiting_approval`, `completed`. Explicit actions `start`, `submit`, `approve`, `reject` guard transitions; no raw status patch. Only the first unfinished stage can start/progress. Per-item mode requires each earlier item completed before starting the next. Submit completes auto work; stage-mode submit waits for human stage approval; item-mode item submit waits for human item approval. Repeated-stage submission requires at least one item and all items completed. Stage approval in item mode is unnecessary after all item approvals. Reject returns review to in_progress. Human-only approval/rejection uses existing session-header identity, never a client-supplied actor. Run status derives from stages, not a bypassable update endpoint. Mutations serialize on the run row inside a transaction before reading state.

Items can be populated on pending or active repeated stages, including from earlier results, with name/description/expected_artifacts; updates/removal only while pending. Review/completed stages freeze their items. Positions reflect creation order, with pending item edits/removal supported. Stage/item `progress` (0..100) and `progress_note` are editable only while in progress; they cannot complete work.

Run `orchestrator_session_id` associates an existing session from the same project; the launcher owns creation and calls `SetCreativeRunOrchestrator`. No development task required. Prefer a dedicated registered agent/session per run so existing agent discussion threads, inbox, send and transcript endpoints can be used unchanged; discussion bodies carry explicit creative context. This core exposes association/context, not a new discussion subsystem.

API namespace `/v1/creative`: GET/POST `/pipelines`; GET/PUT `/pipelines/{id}`; GET/POST `/runs`; GET `/runs/{run}`; PUT `/runs/{run}/orchestrator`; POST `/runs/{run}/stages/{stage}/actions`; PATCH same stage for progress; POST same stage `/items`; PATCH/DELETE same stage `/items/{item}`; POST same item `/actions`; GET `/runs/{run}/context?stage_id=&item_id=`. Lists filter by `project_id`. Requests/responses use snake_case. Actions carry `{action}`; mutations return the current run. CLI `rocket creative` mirrors these resources with JSON file inputs and JSON output usable by agents.

Core owns migration `0028_creative_core.sql`, `registerCreativeRoutes` and its one server registration, `newCreativeCmd` and root registration, new store/API/CLI files. Siblings own separate migration numbers and route registration calls (coordinate through orchestrator). Core adds no artifact/media/tool/preview/launch implementation.

Validation: focused store tests for snapshot isolation, state guards and serialization; API tests for identity, human approval, malformed contexts and development separation; CLI routing/input tests; existing package checks/build. No daemon restart, paid generation, demo projects or simulated generation suites.

## Accepted additions

Human-only `reopen` explicitly reopens completed stage/item for agreed rework; reopening an item also reopens its stage. Prior materials and downstream states remain unchanged; target submission/approval repeats normally. Submission records `artifact_version_ids` and increments `review_revision`; approve/reject require the displayed revision. Nonempty version IDs must resolve to immutable versions in the same run/stage. Stage reviews include item descendants; item reviews require the exact item (fail closed until assets migration is present). Run-level artifact/discussion scope remains exact. Assets owns version persistence and validation schema, core owns review snapshots. These additions were accepted by the orchestrator on 2026-11-04.

Item progress uses `PATCH /v1/creative/runs/{run}/stages/{stage}/items/{item}/progress`; ordinary item PATCH edits its pending definition. Whole-stage review and stage-context discussion include same-stage item versions, as explicitly ruled by the orchestrator for Q6/Q16. Listing and artifact ownership remain exact; review never substitutes the current version pointer.
