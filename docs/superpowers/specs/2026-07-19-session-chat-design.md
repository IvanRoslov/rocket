# Чат с сессиями (зеркало транскрипта) — дизайн

Дата: 2026-07-19. Статус: подтверждён пользователем (полное зеркало; текст + свёрнутые тулзы; чат с оркестратором, воркеры read-only).

## Зачем

Дашборд и мобильное приложение должны давать «режим Claude-ремоута»: полная переписка с оркестратором как чат — видно каждую реплику агента и его активность, отвечать можно из чата. Сегодня human→orchestrator работает (очередь + инжекция, вкладка Messages), а ответы агента живут только в терминале.

## Ключевое наблюдение

Нативный JSONL-транскрипт агента (claude-code: `~/.claude/projects/<slug>/*.jsonl`; codex: `~/.codex/sessions/YYYY/MM/DD/*.jsonl`) уже содержит **весь диалог**: и ходы агента, и наши инжекции (`[from …]`, сообщения человека) как user-ходы. Чат не нужно собирать — только парсить и отдавать. Ничего не дублируем в SQLite: транскрипт и есть хранилище; история переживает cleanup worktree.

## Архитектура

```
дашборд/моб.  ── GET /v1/sessions/{id}/chat?cursor= ──▶ демон ── Agent.TranscriptTail ──▶ JSONL агента
      ▲                                                   │
      └────────── SSE session.chat_updated (пинг) ◀───────┘ (вотчер mtime в мониторном цикле)
отправка: существующий POST /v1/messages {to, body} — без изменений
```

### 1. Интерфейс Agent (internal/agent)

```go
type ChatEntry struct {
    Role     string // "user" | "assistant" | "tool"
    Text     string // текст реплики; для tool — краткое описание
    ToolName string // только для Role=="tool" (например "Bash", "Edit")
    TS       int64  // unix seconds (из записи транскрипта; 0 если нет)
}
// TranscriptTail возвращает записи после cursor (""=с начала) и новый курсор.
// Курсор непрозрачен для клиента; формат адаптера: "<путь-файла>:<byte-offset>".
// Нет транскрипта → ErrNoSignal. Смена файла транскрипта (новый .jsonl) →
// адаптер сам перескакивает, отдав хвост старого файла до конца.
TranscriptTail(ctx context.Context, ref ActivityRef, cursor string) ([]ChatEntry, string, error)
```

- claude-code: последняя запись типа `assistant` → Role assistant, конкатенация text-блоков content; `tool_use`-блоки → отдельные entries Role tool (`ToolName` + однострочный дайджест входа ≤120 симв.); записи `user` → Role user (текст как есть, включая наши префиксы); `thinking`-блоки и служебные записи (summary, system, progress) пропускаются.
- codex: `response_item`/`event_msg` по фактической таксономии (та же фикстурная методика, что в activity): пользовательские и агентские текстовые item'ы → user/assistant; command/tool-события → tool.
- Оба «best effort»: непарсибельная строка пропускается, не ломает ленту.

### 2. HTTP API (internal/api)

`GET /v1/sessions/{id}/chat?cursor=<opaque>&limit=<N,default 200,max 1000>`
→ `200 {"entries":[{role,text,tool_name?,ts}...], "next_cursor":"...", "session":{"id","kind","state","activity"}}`
- 404 session_not_found; сессия без транскрипта (только что заспавнена) → 200 пустые entries, next_cursor="".
- Семантика limit: при cursor=="" первый запрос отдаёт ХВОСТ ленты (последние N записей), next_cursor указывает на конец файла; дальше клиент двигается только вперёд по курсору. Пагинации назад (глубже хвоста) в v1 нет — осознанное упрощение.

SSE (существующий `/v1/events/stream`): новое событие `session.chat_updated {session_id}` — публикуется монитором, когда mtime/размер транскрипта сессии изменился с прошлого тика (не чаще раза в тик, контента не содержит). Клиент по нему дёргает GET с последним курсором.

Отправка: `POST /v1/messages {to:<orch>, body}` — без изменений (статусы queued/delivered/failed через `GET /v1/messages?session=` как сейчас; inbox-механика больших сообщений работает прозрачно).

### 3. Клиенты (дашборд, мобильное — по докам, реализация за их командами)

- Карточка задачи: режим Chat — лента (user справа, assistant слева, tool-строки серым/свёрнуто), композер внизу; статусы моих сообщений (✓ delivered / ⏳ queued / ✗ failed + reason) из /v1/messages.
- SessionRail: те же ленты для воркеров, read-only (без композера) — писать воркерам нельзя (question funnel сохраняется).
- Q&A-треды остаются отдельным механизмом (баннер) — чат их не подменяет.

### 4. Публичные доки (deliverable этого же проекта)

- **Новый `docs/13-chat.md`** — полный клиент-агностичный контракт: эндпоинт, форма entries, семантика курсора («непрозрачен, храните и возвращайте»; сброс при "" → снова хвост), событие SSE, флоу отправки со статусами, ограничения (воркеры read-only; лента best-effort и может отставать на интервал поллинга ~2-5s; tool-дайджесты усечены), примеры curl + примерный жизненный цикл экрана (open → GET хвост → subscribe SSE → on chat_updated GET cursor → append). ### 5. Ошибки и краевые случаи

- Транскрипт-файл ротировался/новый: адаптер дочитывает старый до EOF, следующий вызов начинает новый (курсор помнит путь).
- Сессия убита/cleanup: транскрипт остаётся → чат читается и после смерти сессии (история фичи).
- Демон не знает про содержимое: никакой фильтрации секретов не делаем (транскрипт локален, как и терминал).
- Гонки: файл дописывается во время чтения — читаем только полные строки (незавершённая последняя строка не отдаётся, попадёт в следующий вызов).

### 6. Тестирование

- Адаптеры: фикстурные JSONL (методика activity-тестов) — типы записей, курсор-инкрементальность, ротация, обрезка tool-дайджеста, непарсибельные строки.
- API: httptest — хвост-первый-запрос, инкремент по курсору, 404, лимиты.
- SSE: событие публикуется при изменении, не спамит без изменений.
- Live-приёмка: реальный оркестратор — диалог из дашборд-эндпоинта совпадает с терминалом; отправка из чата доезжает.

## Вне скоупа v1

Пагинация назад в глубину истории; запись воркерам; пуш-нотификации мобильному; авторизация удалённого доступа (дашборд по-прежнему localhost; выход наружу — отдельный проект с auth).
