# Права постоянных агентов на задачи (задача #710)

Версия спеки: v1. Дата: 2026-08-02.

## Проблема

Постоянный агент (`rocket agent add`, сессия `cto`, `sessions.kind='agent'`) не
может создавать задачи:

```
$ rocket task add "test" --project brain
rocket: forbidden: only orchestrators may create tasks
```

Причина — `internal/api/tasks.go:334`: если в запросе есть заголовок сессии
(CLI подставляет его из `ROCKET_SESSION_ID`), caller обязан быть
`kind='orchestrator'` и может создавать только подзадачи своей задачи. Вид
`agent` под это не подходит и получает 403.

`rocket up` падает по второй причине: `handlePostTaskStart`
(`internal/api/tasks.go:794`) отклоняет любого caller с сессией —
`only the human user may start a task`.

Обход, который применял пользователь, — `env -u ROCKET_SESSION_ID rocket task
add ...`. Он показывает суть: идентификация через env-переменную является
**атрибуцией, а не аутентификацией**, поэтому текущая проверка никого не
защищает, а лишь мешает штатному сценарию (агент-управляющий ставит задачи
командам).

## Решение

Постоянный агент приравнивается к человеку в правах на задачи. Новых сущностей
(флаги привилегий, роли в реестре агентов) не вводим: строить модель прав
поверх легко подделываемого идентификатора — фальшивый периметр.

### 1. Создание задач — `POST /v1/tasks`

Ветвление по caller:

| caller | права | `created_by` |
|---|---|---|
| `nil` (человек) | без ограничений | `user` |
| `kind='agent'` | без ограничений (корневые задачи и подзадачи, любой проект) | `agent` |
| `kind='orchestrator'` | только подзадача (`parent_id != 0`) задачи, принадлежащей этому оркестратору | `orchestrator` |
| прочее (`worker`) | 403 `forbidden` / `workers may not create tasks` | — |

Текст ошибки для воркера меняется с `only orchestrators may create tasks` на
`workers may not create tasks`: старая формулировка вводит в заблуждение, так
как перечисляет не тот набор разрешённых видов.

Существующие проверки для оркестратора (`agents may only create subtasks`,
`parent task does not belong to caller`) сохраняются без изменений.

### 2. Запуск задачи — `POST /v1/tasks/{id}/start`

Разрешено: `caller == nil` и `caller.Kind == 'agent'`. Остальным — 403
`only the human user or a registered agent may start a task`.

Вместе с п.1 это чинит `rocket up` целиком (он = `task add` + `task start`).

### 3. Запись в задачу — `canWriteTask` (`internal/api/auth.go:56`)

Сейчас для агента функция возвращает `false`, то есть агент создал бы задачу и
не смог ни поправить описание, ни перевести статус. `caller.Kind == 'agent'`
трактуется как человек: полный доступ на запись. Права воркеров и
оркестраторов не меняются.

### 4. Спавн воркеров — без изменений

`POST /v1/sessions` остаётся доступен только живому оркестратору
(`isSpawningOrchestrator`, `internal/api/sessions.go:103`). Агент ставит и
запускает задачу; воркеров под неё спавнит оркестратор, у которого есть
нужный контекст (feature slug, ветка, карточка подзадачи). Агент такого
контекста не имеет.

### 5. `created_by='agent'` у потребителей

- `internal/store/migrations/0001_init.sql:68` — обновить комментарий на
  `user|orchestrator|agent`. CHECK-констрейнта нет, миграция не требуется.
- `web/src/lib/types.ts` — `TaskCreatedBy` дополняется `'agent'`.
- `web/src/screens/task/TaskScreen.tsx:110` — тернарник
  `created_by === 'user' ? 'you' : 'orchestrator'` заменяется на отображение
  всех трёх значений (`you` / `orchestrator` / `agent`).
- `mobile/src/api/types.ts:119` — то же расширение типа.

### 6. Документация

- `docs/10-agents.md` — раздел о правах постоянного агента: создаёт и
  запускает задачи наравне с человеком, редактирует задачи, воркеров не
  спавнит; идентификатор сессии — атрибуция, не аутентификация.
- `docs/12-tasks.md` и `docs/03-daemon-api.md` — актуализировать описания
  доступа и тексты 403 для `POST /v1/tasks` и `POST /v1/tasks/{id}/start`.

## Критерии приёмки

1. Из tmux-сессии зарегистрированного агента (`ROCKET_SESSION_ID=cto`)
   `rocket task add "test" --project <p>` создаёт корневую задачу; в ответе
   `created_by = "agent"`.
2. Оттуда же `rocket up "..."` создаёт задачу и запускает оркестратора.
3. Агент может изменить описание и статус созданной задачи.
4. Воркер, пытающийся создать задачу, получает 403 с текстом
   `workers may not create tasks`.
5. Оркестратор по-прежнему может создавать только подзадачи своей задачи и
   не может стартовать задачу.
6. Задача с `created_by='agent'` корректно отображается в web и mobile.

## Тесты

Пишутся до реализации (TDD).

Go (`internal/api`):
- агент создаёт корневую задачу → 201, `created_by='agent'`;
- агент создаёт подзадачу к чужой задаче → 201;
- агент стартует задачу → 200 (оркестратор спавнится);
- воркер создаёт задачу → 403 `workers may not create tasks`;
- оркестратор стартует задачу → 403;
- агент правит задачу (`canWriteTask`) → успех;
- существующие тесты прав оркестратора не меняются.

Web/mobile: рендер лейбла автора для `created_by='agent'`.

## Вне скоупа

Настоящая аутентификация сессий (подписанный токен вместо env-переменной).
Известное ограничение сохраняется: `env -u ROCKET_SESSION_ID` по-прежнему
выполняет команду от имени человека. После этих изменений это уже не «обход
запрета» — запрета для агентов нет, теряется только корректная атрибуция
`created_by`. Если понадобится реальный контроль доступа, это отдельная
задача про аутентификацию, а не про флаги привилегий в реестре агентов.
