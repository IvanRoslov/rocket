# Свежесть зеркал ~/.rocket/repos: синхронизация перед стартом, `repo status`/`repo sync`, ремонт зеркал

Задача #3576. Дата: 2026-09-13.

## Проблема

Замер 2026-09-13 по 77 зеркалам lessly-hub: 25 отставали от `origin/main`
(до 78 коммитов), в 22 был сделан checkout чужой рабочей ветки
(`orch/…`, `docs/…`), в части — незакоммиченные правки. Агент, читающий
файлы такого зеркала, уверенно оперирует кодом и CLAUDE.md многонедельной
давности, не имея способа это заметить.

## Что уже работает (и не переделывается)

- `internal/mirror.Sync` — `git fetch origin --prune` + `git merge --ff-only origin/<default>`;
  никогда не перетирает: грязное дерево, HEAD не на default-ветке и невозможный
  FF оставляют зеркало как есть.
- `internal/mirror.Check` — отставание в коммитах, время последнего fetch,
  причина блокировки. Без сети.
- `internal/mirror.Syncer` — фоновый обход всех зеркал в `repos_dir` раз в
  `mirror_sync_interval` (5m). Рабочие копии, добавленные через
  `rocket repo add <path>`, не трогаются.
- `rocket status` и `rocket repo ls` печатают строку `mirror <id>: ПРОТУХЛО — …`.
- `workspace.Create` делает `git fetch origin` и ветвится от `origin/<default>`,
  а не от локального `refs/heads/main`.

Следствие: код в новом воркспейсе уже берётся со свежего `origin/main`.
Оставшаяся дыра — файлы самого зеркала, которые агенты читают напрямую, и
зеркала, которые фоновый sync подтянуть не может и чинить не умеет.

## Решения

**Зеркала остаются обычными клонами с рабочим деревом (вариант A).** Bare
отвергнут: рабочее дерево зеркала — это то, что агенты читают через
Read/Grep по пути `~/.rocket/repos/<id>/<path>`, и это зафиксировано в
промптах оркестратора и воркера. Вместо bare вводится инвариант «зеркало
всегда на default-ветке» и команда ремонта.

**Предупреждение о несинхронизированном зеркале видно в `rocket task show`**
(вариант 1), отдельной строкой; запись в журнал задачи не создаётся.

**Команды — подкоманды существующей группы `repo`** (`rocket repo status`,
`rocket repo sync`) с алиасом группы `repos`, чтобы не заводить вторую
почти одинаковую группу.

## Объём работ

### 1. Синхронная подтяжка зеркала перед созданием воркспейса

`session.Manager` перед `ws.Create` вызывает `mirror.Sync(ctx, repo)` для
зеркал под `repos_dir` (рабочие копии пользователя — как и сейчас —
пропускаются).

- Сбой сети или заблокированное зеркало **не блокируют** создание сессии:
  пишется `slog.Warn` и результат запоминается.
- Ограничение по времени на синхронизацию — отдельный таймаут, чтобы
  медленный origin не подвешивал спавн.

### 2. Предупреждение в `rocket task show`

`rocket task show <id>` дополнительно печатает строку свежести по зеркалам
репозиториев, задействованных в задаче:

```
mirror rocket: ПРОТУХЛО — синхронизация не может обновить дерево: HEAD не на ветке main
```

Свежесть считается локально через `mirror.Check` (без сети, без обращения к
демону), тем же кодом, что уже используют `rocket status` и `rocket repo ls`
(`internal/cli/mirror.go`). В `--json` добавляется ключ `mirrors` с массивом
строк-состояний; существующие ключи не двигаются.

### 3. `rocket repo status`

Таблица по всем зеркалам под `repos_dir`:

| колонка | содержимое |
|---|---|
| `repo` | id репозитория |
| `head` | короткий SHA HEAD зеркала |
| `origin` | короткий SHA `origin/<default_branch>` |
| `behind` | отставание в коммитах |
| `branch` | checked-out ветка (или `detached`) |
| `dirty` | `да`/`нет` |
| `fetched` | сколько назад последний fetch |

Без сети. `--json` отдаёт те же поля структурой. Рабочие копии из
`repo add <path>` в таблицу не попадают (как и в остальных местах).

### 4. `rocket repo sync`

`rocket repo sync [<id>…]` — синхронизировать все зеркала (или указанные).
Делает то же, что фоновый тикер: `mirror.Sync` по каждому. Печатает
построчный итог: обновлено на N коммитов / уже актуально / заблокировано с
причиной. Ненулевой код возврата — только если ни одно зеркало не удалось
обработать; отдельные блокировки кодом возврата не считаются ошибкой.

### 5. `rocket repo sync --repair` — ремонт заблокированных зеркал

Единственное место, где rocket трогает содержимое зеркала сверх FF. Для
каждого заблокированного зеркала, строго в этом порядке:

1. Если дерево грязное — незакоммиченные правки **сохраняются коммитом** в
   спасательную ветку `rescue/<YYYY-MM-DD-HHMMSS>` (`git checkout -b`,
   `git add -A`, `git commit`). Ничего не удаляется, `reset --hard`,
   `checkout -f` и `clean` в коде не появляются.
2. HEAD переводится на default-ветку (`git checkout <default>`).
3. Выполняется обычный `mirror.Sync`.

Итог печатается отчётом: какие зеркала починены, в какие спасательные ветки
уехали правки, что осталось заблокированным и почему. Без `--repair`
команда ничего из этого не делает.

Инвариант «rocket сам никогда не делает checkout рабочей ветки в зеркале»
уже соблюдается кодом (ветки в зеркале появляются только от ручных
действий человека) и фиксируется в документации.

### 6. Документация

- `docs/04-cli.md` — `repo status`, `repo sync`, `--repair`, алиас `repos`.
- `docs/05-state.md` — инвариант «зеркало всегда на default-ветке», спасательные
  ветки `rescue/*`, что именно делает `--repair`.
- `docs/02-architecture.md` — синхронная подтяжка перед созданием воркспейса и
  её неблокирующий характер.

## Приёмка

- `rocket repo status` показывает 0 отстающих и 0 заблокированных после
  `rocket repo sync --repair`.
- Воркспейс, созданный после нового коммита в `origin/main`, содержит этот
  коммит без ручного `pull` (интеграционный тест на локальном origin).
- Заблокированное зеркало не мешает спавну: сессия создаётся, предупреждение
  видно в `rocket task show`.
- Грязное зеркало после `--repair` не теряет правки: они находятся коммитом
  в ветке `rescue/*`.

## Вне объёма

- Перевод зеркал в bare (отвергнуто выше).
- Изменение путей `~/.rocket/repos/<org>__<repo>`.
- Команда `rocket repos migrate` из исходного тикета: миграции нет, её роль
  выполняет `repo sync --repair`.
