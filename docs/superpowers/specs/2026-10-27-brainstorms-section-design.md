# Раздел «Брейнштормы» (веб и мобилка)

## Коротко

**Проблема.** Брейншторм сейчас показывается в инбоксе «Вопросы» строкой «Storm #N» и входит в счётчик на его бейдже. Из-за этого:

1. Человек видит бейдж и думает, что его ждёт обычный вопрос, а там брейншторм. Это отвлекает.
2. Строка висит, пока у задачи есть открытые storm-вопросы, и статус задачи не учитывается. Брейншторм бросили, задачу перевели в Review или Done, а строка осталась навсегда.
3. Гейт «Go на спеку» нигде не собран в общий список. Его видно только во вкладке Brainstorm самой задачи. Частый случай: задача уже в работе, всплыл непредусмотренный кейс, спеку меняют, и оркестратор встаёт в паузу и ждёт Go. Узнать об этом можно, только открыв задачу.

**Что строим.** Отдельный раздел «Брейнштормы» в вебе и в мобилке. В нём только то, что ждёт человека: одна строка на задачу, два фильтра («Ждёт ответа», «Ждёт Go»). Задачи в Review, Done и Cancelled не показываются. Из «Вопросов» брейнштормы убираются полностью, вместе со счётчиком на бейдже. У раздела свой бейдж.

**Чего не делаем.**
- Не отвечаем на storm-вопросы и не жмём Go прямо в списке. Строка ведёт во вкладку Brainstorm задачи, там всё как сейчас.
- Не показываем брейнштормы, где от человека ничего не ждут (агент думает, пишет спеку). Фильтра «Агент работает» нет: это решение человека.
- Не закрываем автоматически висящие storm-вопросы и гейты у задач в Review, Done и Cancelled. Их просто не показываем, данные не трогаем.
- Не меняем саму механику гейтов и storm-вопросов (создание, ответ, outcome, supersede).

## 1. Что считается «брейншторм ждёт меня»

Задача попадает в раздел, если её статус **не** `review`, `done` или `cancelled` и выполнено хотя бы одно условие:

- **Ждёт ответа:** у задачи есть хотя бы один open-вопрос `type = brainstorm` с `your_turn = true` для человека. Правило то же, что сейчас в `stormGroups` (`web/src/lib/storm.ts`, `mobile/src/lib/storm.ts`).
- **Ждёт Go:** у задачи есть гейт в статусе `pending` (`task_gates.status = 'pending'`).

Видимые статусы: `backlog`, `brainstorm`, `in_progress`, `blocked`. Если в будущем появится новый статус, он показывается по умолчанию. Скрытие задаётся явным списком скрытых статусов.

Задача, которая подходит под оба условия, это одна строка с обеими пометками. Она попадает в оба фильтра.

Задачи без проекта (milestones) участвуют на общих правилах. Их строка ведёт на `/milestones/:id`, как сейчас делает `stormHref`.

## 2. API

### 2.1 `GET /v1/brainstorms`

Новый эндпоинт, отдаёт список задач из §1. Фильтр по статусу задачи и сборка pending-гейтов делаются на сервере, чтобы веб и мобилка не дублировали правило и не ходили в `GET /v1/tasks/{id}/gates` по каждой задаче.

Права (моё решение). Гейт решает только человек: `handleDecideGate` отвечает 403 любой сессии. Поэтому раздел и эндпоинт только для человека, сессия-агент получает 403. Задача должна быть видна человеку по тому же правилу, что в `GET /v1/tasks`. `canReadThread` здесь не подходит: у задачи с одним pending-гейтом может не быть ни одного треда. «Ждёт ответа» считается так же, как `your_turn` в инбоксе для `human`.

Ответ: массив, одна запись на задачу.

```json
{
  "task_id": 5138,
  "project_id": "rocket",
  "task_title": "Usage screen",
  "task_status": "in_progress",
  "questions_waiting": 2,
  "questions_stale": false,
  "pending_gate": {
    "id": 17,
    "spec_version": 3,
    "requested_at": 1761550000
  },
  "waiting_since": 1761540000
}
```

- `questions_waiting`: число open storm-вопросов с `your_turn`. `0`, если таких нет.
- `questions_stale`: хотя бы один из них stale, по тому же правилу, что `Stale` в `threadInboxEntry`.
- `pending_gate`: `null`, если pending-гейта нет.
- `waiting_since`: самый ранний момент среди ожидающих элементов (минимальный `updated_at` ждущих вопросов и `requested_at` гейта). По нему идёт сортировка.

Порядок: сначала строки с `questions_stale = true`, потом по `waiting_since` по возрастанию (дольше всех ждёт выше). Правило то же, что сейчас у `stormGroups`.

Параметров фильтрации у эндпоинта нет. Фильтры «Ждёт ответа» и «Ждёт Go» клиент применяет к полученному списку.

### 2.2 Живые обновления

Список должен обновляться без перезагрузки. Клиенты инвалидируют запрос раздела на те же события, что уже приходят по SSE:
- события тредов/вопросов (как сейчас инвалидируется инбокс);
- `task.gate_requested`, `task.gate_decided`, `task.gate_superseded`;
- смена статуса задачи (строка должна исчезнуть, как только задачу перевели в Review или Done).

Новых типов событий не вводим, но существующие должны покрывать все смены статуса. Сейчас `task.status_changed` публикуется только при смене статуса через API (`internal/api/tasks.go`). Молча меняют статус:
- PR-поллер, который переводит задачу в `review` и `done` (`internal/ghpoller/reactions.go`). Это самый частый путь в Review и Done, то есть ровно тот случай, ради которого делается D4;
- отмена подзадачи при неудачном спавне (`internal/api/sessions.go`).

Решение (моё): на обоих путях публиковать `task.status_changed`, как в API. Другие подписчики тоже от этого выигрывают, и клиентам не нужно догадываться о смене статуса по `pr.*`.

Мобилка: в `parseEventType` (`mobile/src/api/events.ts`) добавить query-ключ раздела к маппингам `task.*` (сюда же входят гейт-события и `task.status_changed`) и `pr.*`. В вебе `sse.ts` уже слушает все три гейт-события и `pr.*`, нужно только добавить ключ раздела в инвалидацию.

## 3. Веб

### 3.1 Навигация

- Пункт `Brainstorm` в шапке (`AppShell.tsx`) ведёт на `/brainstorm`. Получает бейдж того же вида, что у Questions (заливка `--q-amber`). Число = количество строк из `GET /v1/brainstorms`.
- Бейдж Questions больше не считает брейнштормы: `inboxCount` считает только обычные треды на человеке.

### 3.2 Экран `/brainstorm`

Сейчас тут `BrainstormMetricsScreen` (метрики). Экран получает две вкладки:
- **Ждут меня** (по умолчанию): новый список.
- **Метрики:** текущий `BrainstormMetricsScreen` без изменений.

Вкладка хранится в query-параметре (`?tab=metrics`), чтобы на метрики можно было дать ссылку.

Список:
- Сверху переключатель фильтра: **Всё** (по умолчанию) · **Ждёт ответа** (N) · **Ждёт Go** (N). Счётчики считаются по полученному списку.
- Строка: `#id` и название задачи, проект, статус задачи, пометки:
  - «N вопросов ждут ответа» и тег STALE, если `questions_stale`;
  - «Ждёт Go · спека vN»; если статус задачи `in_progress` или `blocked`, дополнительно «смена спеки в работе».
  - Сколько времени ждёт (от `waiting_since`).
- Клик по строке ведёт во вкладку Brainstorm задачи (`stormHref`).
- Пустое состояние: «Брейнштормы тебя не ждут».

### 3.3 Инбокс «Вопросы»

Убрать всё, что связано с storm-строками:
- `StormRows` / `StormCard` и их использование в `BrowseMode`, `FocusMode`, `QuestionsScreen`;
- storm-строки из счётчиков фильтров и из J/K-навигации Decide;
- текст «Only storm questions are left…» в `FocusMode`.

Storm-треды по-прежнему отфильтрованы из обычного списка, как сейчас (`!isStorm(t)`). Так они не появятся в инбоксе обычными карточками.

Подсчёт storm-вопросов на карточке задачи в канбане (`stormsByTask`) не трогаем.

## 5. Тесты

- API: `GET /v1/brainstorms`.
  - Задача с open storm-вопросом на человеке попадает в список, с вопросом на агенте не попадает.
  - Задача с pending-гейтом попадает в список, с `go`, `changes` или `superseded` не попадает.
  - Задача в `in_progress` с pending-гейтом попадает в список.
  - Задачи в `review`, `done` и `cancelled` не попадают ни с вопросами, ни с гейтом.
  - Оба условия дают одну запись.
  - Порядок: stale первыми, затем по `waiting_since`.
  - Сессия-агент получает 403. Человек видит задачи по правилу `GET /v1/tasks`.
  - PR-поллер, переводя задачу в `review` или `done`, публикует `task.status_changed`. То же при отмене подзадачи из-за неудачного спавна.
- Веб: экран раздела (фильтры, счётчики, пустое состояние, ссылка), бейдж в шапке. Инбокс «Вопросы» без storm-строк, бейдж Questions их не считает. Обновить существующие тесты, которые проверяют storm-строки в инбоксе.
- Мобилка: то же для новой вкладки и для `questions.tsx`, плюс `storm.test.ts`.
