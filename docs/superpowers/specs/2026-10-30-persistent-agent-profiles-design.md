# Запуск постоянных агентов через профиль модели

## Зачем

Сейчас `rocket agent start <id>` запускает только сохранённые `dir` и произвольную `command`. Чтобы запустить постоянного агента в нужном harness и с нужной моделью, человек вынужден вручную собирать команду, а адаптер сессии затем определяется из её текста. Нужен короткий сценарий: выбрать профиль при запуске, затем просто делать attach и не перенастраивать агента при следующих запусках.

## Целевой сценарий

```bash
rocket agent start cto --profile claude-opus
rocket agent attach cto

rocket agent stop cto
rocket agent start cto   # снова использует claude-opus
rocket agent attach cto
```

Профиль выбирается из существующего реестра `model_profiles`; он уже объединяет harness (`agent`), модель и необязательный effort. Последний явно выбранный профиль сохраняется в регистрации постоянного агента и используется последующими запусками без `--profile`.

## Решение

- `POST /v1/agents/{id}/start` принимает необязательное поле `profile`. CLI добавляет одноимённый флаг `rocket agent start <id> [--profile <name>]`.
- При переданном профиле демон проверяет, что он существует, включён и его адаптер доступен. Успешный выбор сохраняется как `launch_profile` постоянного агента. Отдельных флагов `--agent`, `--model` и `--effort` у `agent start` нет.
- Запуск с профилем использует существующий `agent.Agent`: `LaunchCommand` и `Env` с `LaunchSpec{Kind: "agent", WorktreePath: a.Dir, Model, Effort}`. Никакого системного промпта или первого сообщения Rocket не добавляет: контекст постоянного агента остаётся в его собственной директории.
- `SetupWorkspace` при таком запуске не вызывается: он предназначен для управляемых worktree оркестраторов и воркеров и мог бы изменить файлы личной директории агента.
- В `sessions` сохраняются `agent`, `profile`, `model`, `effort` на момент запуска. Адаптер больше не нужно угадывать из текста команды для запусков через профиль. При повторном запуске используется сохранённый профиль, даже если позже его отредактировали: новый запуск берёт актуальные model/effort профиля; уже живая сессия не меняется.
- Если профиль сохранён, но к следующему запуску удалён или выключен, запуск возвращает понятную ошибку и просит выбрать другой `--profile`; молчаливого fallback на другой harness нет.
- `rocket agent show <id>` и ответ API агента показывают сохранённый `launch_profile`; список сессий продолжает показывать фактический снимок запуска.

## Совместимость

- Агент без сохранённого профиля запускается ровно как раньше: `dir` + `command`, пустая команда означает shell, адаптер определяется из `command`.
- Старый `rocket agent add/edit --command` остаётся. Профиль имеет приоритет над `command` только когда сохранён или передан при запуске.
- Ручной запуск tmux-сессии и её adoption не меняются. Для внешней сессии по-прежнему используется определение адаптера из зарегистрированной `command`.
- Живую сессию нельзя перезапустить с новым профилем: сохраняется текущая ошибка `agent_live`; сначала нужен `stop`.

## Не входит

- Автоматический attach после start.
- Изменение модели внутри уже живого агента.
- Отдельные профили, специфичные для постоянных агентов, и прямые флаги harness/model.
- Изменения дашборда и mobile в этой итерации.
- Новый lifecycle: Rocket по-прежнему только запускает/останавливает tmux-сессию и не управляет внутренним устройством агента.

## Рассмотренные подходы

1. **Расширить существующий `agent start` — выбран.** Одна команда запуска, переиспользование профилей и адаптеров, обратная совместимость с ручными командами.
2. **Отдельный `agent launch`.** Оставил бы старый тонкий launcher нетронутым, но создал бы две похожие команды и сохранил бы основную сложность для пользователя. Отклонён.

## Проверка

- Unit/API/CLI-тесты: запуск с явным профилем, повтор последнего профиля, снимок `agent/profile/model/effort`, legacy `command`, ошибки неизвестного/выключенного профиля и живой сессии.
- Стандартный `make test` для Go и web.
- Живая проверка: постоянный агент запускается на выбранном профиле, после `stop` запускается без флагов с той же конфигурацией, `rocket agent attach <id>` подключается к правильному TUI; сообщение агенту доставляется с правильным диалектом адаптера.
