# Доставка сообщений без повреждения ручного ввода — первый этап

## Коротко для согласования

Сохраняем привычные терминалы Claude, Codex, Pi и Kimi. На первом этапе добавляем отдельный канал сообщений для новых и восстановленных сессий Pi: внутреннее сообщение поступает агенту, не вставляется в строку человека. Для Codex проверяем отдельный серверный канал с сохранением окружения сессии, для Kimi — доступные входы в работающий терминальный процесс. Их подключение к рабочей доставке пойдёт следующим этапом, по новой спецификации и Go после проверки.

Claude и ранее запущенные сессии продолжают работать как сейчас. Общей гарантии сохранности ввода для старой доставки через tmux этот этап не даёт. Собственный интерфейс общения вместо терминалов и плагины tmux не строим.

## Основания и решение человека

Задача #5902: ручной текст может портиться, когда Rocket доставляет внутреннее сообщение через tmux. Проверка экрана и последующая вставка — разные операции; устранить гонку одним распознаванием черновика нельзя.

Решение 5902/Q1: «Сохранить штатные терминалы, внедрять поэтапно».

Ресерч: `docs/features/tmux-delivary/research.md`. Проверенные версии: Pi 1.4.0, Codex 0.160.0, Kimi Code 2.4.0; базовый Rocket — 86f21d8. Возможности установленных CLI и документация проверены, живые проверки одновременного ввода ещё не выполнены.

Разделение первого этапа — предложение оркестратора для этого Go, а не дополнительное решение, уже принятое человеком: рабочее подключение Pi; воспроизводимая проверка вариантов Codex/Kimi без изменения их рабочего запуска.

## Подходы

1. Улучшать вставку tmux: быстро, но общий ввод и гонка остаются. Не обеспечивает требуемое свойство.
2. Использовать каналы самих агентов, поэтапно сохраняя их терминалы: выбранное направление. Pi Extension API даёт прямой вход в агент, Codex требует проверки server/TUI режима, Kimi — проверки совместимости со штатным TUI.
3. Собственный клиент Rocket поверх API: большой объём изменения привычной работы; не входит в выбранное направление.

## Цели и границы

- Для нового канала Pi ручной черновик и положение курсора сохраняются при внутренней доставке; отсутствуют автоматические clear/paste/Enter.
- Работают существующие rocket send, сообщения вопросов, напоминания и длинные сообщения с ссылкой на inbox; отправители не выбирают новый транспорт вручную.
- При занятом агенте используем followUp: сообщение принимается в отдельную очередь и обрабатывается после текущего хода. Принятие в очередь не означает немедленное включение в текущий ответ.
- Отказ нового канала не переключает его сессию на вставку через tmux. До отправки сообщение можно повторить; после неоднозначной отправки нельзя повторять вслепую.
- Прежние сессии сохраняют старый транспорт до явного restore. Автоматически их не перезапускаем.
- Claude socket/held/fallback, прежние Codex/Kimi/Pi и интерактивные ответы пользователя не переделываются.
- Нет fork агентов, изменения глобальных конфигов/установок и нового UI. Без обещания exactly-once при произвольных падениях процессов.

## Архитектура Pi

### Запуск и адресация

Rocket поставляет собственное расширение Pi и подключает его явным --extension в SetupWorkspace/LaunchCommand. Расширение загружается из подготовленного Rocket файла, без установки глобального плагина. Порог нового режима — Pi 1.4.0 с поддерживаемым Extension API. Версии 1.0–1.3 сохраняют прежний транспорт; сломанный или неразобранный ответ версии не включает новый канал. Новые версии должны пройти проверку возможности запуска расширения и handshake, одного номера версии недостаточно.

Сокет находится в приватном локальном runtime-каталоге Rocket с коротким путём, подходящим для macOS UDS. Каталог 0700, сокет 0600. Имя производно от идентификатора сессии; запрос содержит также идентификатор конкретного запуска. Нельзя выбирать получателя по одному имени панели, newest-файлу или похожему cwd.

Расширение открывает канал на session_start, закрывает его на session_shutdown; при смене активной Pi-сессии закрывает прежний endpoint и не принимает его сообщения в новую историю. Restore создаёт новую идентичность запуска. Kill/авария не оставляют доверенный endpoint для следующего процесса.

Выбор транспорта фиксируется в данных запуска сессии и при первой попытке сообщения: legacy или pi-uds-v1. Для существующих записей значение legacy. Отсутствие или временная недоступность сокета не изменяет сохранённый выбор.

### Обмен и подтверждения

Один JSON-объект на строку, версия протокола 1. Обязательны идентификаторы Rocket-сессии, запуска и сообщения. Текст берётся из существующего prepareText без изменения пользовательского содержимого. Максимальный размер кадра — 1 MiB; существующая подготовка длинных сообщений остаётся общей.

Расширение вызывает sendUserMessage с followUp без расширения slash-команд/шаблонов и не обращается к editor setText/submit. Повтор одного ID в том же живом запуске не вызывает повторную подачу текста; одинаковый текст с разными ID остаётся двумя разными сообщениями.

Состояния отправки:

- not_sent: доказан отказ до передачи запроса агенту; остаётся queued и допускает обычный повтор в пределах существующих лимитов.
- accepted: мост принял запрос; Rocket сохраняет accepted и проверяет существующий Pi transcript через DeliveryConfirmer.
- unknown: соединение оборвалось после возможной передачи; сообщение также остаётся под подтверждением, без слепой повторной подачи.
- delivered: только подтверждённое пользовательское сообщение в правильной истории после момента отправки.

Сам вызов Extension API не подтверждает сохранение: он запускает асинхронную операцию. Старое правило accepted → повтор по отсутствию текста на экране не применяется к pi-uds-v1. Если подтверждения нет, при завершении/restore получателя либо по существующему QueueTimeout сообщение становится failed с причиной native_delivery_unconfirmed; если таймаут отключён, ожидание сохраняется до завершения/restore. Это ограничение отражается в документации: возможна недоставка вместо риска дубля. Явный повтор пользователем остаётся отдельным действием.

Новые сообщения используют ту же маршрутизацию, expiry и события очереди. Момент начала отправки и выбранный транспорт сохраняются до побочного действия; при Recover сообщения нового транспорта в delivering переводятся в accepted/проверку, а не переотправляются автоматически.

### Очередь Rocket

Новый NativeSender не подменяет Claude SocketSender. Native маршрут выбирается до проверок визуального черновика/диалога. Он обходится без tmux Inject/Capture для доказательства доставки; состояние приёма в расширении определяет возможность подачи. Диалоги/compaction, где подача не подтверждена как безопасная, дают not_sent до вызова API. Терминальные состояния сессии и истечение queued-сообщений продолжают учитываться.

## Codex и Kimi: результат исследования первого этапа

Codex: в изолированной сессии проверить отдельный app-server + штатный TUI --remote и внешний отправитель. Проверка должна доказать общий thread UUID, доставку idle/busy, сохранение черновика/курсора и ROCKET_* в shell-tools. Проверить выход/restore/отказ канала. Не снимать --no-daemon в рабочем адаптере и не использовать общий сервер с потерей окружения. Документировать воспроизводимые команды и фактический результат, включая отрицательный.

Kimi: проверить официальные API/расширения именно 2.4.0 и поддерживаемый вход в тот же процесс штатного TUI. Не отбирать блокировку у живого процесса и не использовать второй писатель истории. Старый Python --wire не является доказательством для текущего CLI. Если поддерживаемого пути нет, результат — конкретное ограничение и возможный upstream-запрос; рабочий транспорт остаётся прежним.

После этих проверок оркестратор предлагает следующую спецификацию подключения или явно фиксирует ограничение. Этот Go не разрешает заменять интерфейс или менять рабочий запуск Codex/Kimi без следующей спецификации.

## Проверка и приёмка

- Pi: один и несколько внутренних текстов при пустом поле, одно-/многострочном русском черновике и курсоре внутри строки; idle и занятый агент. Черновик/курсор сохраняются, сообщение появляется в правильной истории один раз.
- Повтор ID, одинаковые тексты с разными ID, длинное сообщение, невалидный/слишком большой кадр, неверная сессия/запуск.
- Разрыв до передачи, после передачи, потеря сокета, перезапуск Rocket, restore/kill Pi, переключение истории. Нет скрытого возврата в tmux и автоматического дубля из unknown.
- Fake runtime тесты доказывают отсутствие Inject/SendKeys/Capture на новом маршруте; регрессии Claude/legacy остаются зелёными.
- Если живая проверка Pi показывает, что сохранность ввода или подтверждение нельзя обеспечить, остановить подключение и вынести факты на новый вопрос; небезопасный канал не выдавать за готовый.
- Для Codex/Kimi приложены версии, команды, редактированные свидетельства и разделение проверенного/непроверенного.
- Все PR имеют зелёные доступные CI-проверки; отсутствие CI фиксируется явно и заменяется локальными обязательными проверками, а не выдается за зелёный CI.

## Оставлено исполнителям

Внутреннее размещение типов и функций, способ наблюдения ошибок/приёма внутри Pi и реализация управления сокетом — в пределах контракта выше. Схемы и handshake уточняются по установленному Pi. Расширение не должно обещать подтверждение, которого API не предоставляет. Новые продуктовые компромиссы, ослабление гарантий и изменение объёма требуют вопроса и новой версии спецификации с Go.
