# Доставка сообщений без повреждения ручного ввода — первый этап

Полная Spec v2. Изменённая часть Pi требует нового Go Ивана; решение CTO в 5902/Q2 разрешает подготовку документов, а не реализацию.

## Коротко для согласования

Сохраняем привычные терминалы. Для новых и восстановленных сессий Pi добавляем отдельный канал: сообщение Rocket поступает агенту без очистки строки, вставки текста и нажатия Enter. Проверки показали, что при обычной доставке сохраняются русский черновик и курсор — и когда агент свободен, и когда занят.

**Два ограничения самого Pi:** агент иногда может начать ответ, пока на экране открыто окно другого плагина: общего надёжного сигнала всех диалогов Pi не даёт. А если после доставки нажать Escape или вернуть ожидающую очередь в редактор, Pi может сам добавить ожидающее сообщение рядом с черновиком и поставить курсор в конец. При закрытии некоторых пользовательских окон Pi также сам переставляет курсор. Мост не будет скрыто переписывать редактор, чтобы это замаскировать.

Этот Go означает внедрить канал с этими явными ограничениями. Альтернатива — отложить рабочее подключение Pi до доработки его API. Поддержка произвольных плагинов без исключений здесь не обещается; пользовательские плагины сохраняем.

Claude, Codex, Kimi и ранее запущенные сессии продолжают работать как сейчас. Для Codex/Kimi сохраняем результаты исследования; их рабочее подключение потребует следующей спецификации. Общей гарантии сохранности ввода для прежней доставки через tmux этот этап не даёт. Новый интерфейс вместо терминалов, fork Pi и плагины tmux не строим.

Go здесь разрешает реализацию моста и перечисленные изолированные синтетические проверки. Установка общей версии Rocket и проверки на рабочих сессиях потребуют отдельного разрешения.

## Основания и решение человека

Задача #5902: ручной текст может портиться, когда Rocket доставляет внутреннее сообщение через tmux. Проверка экрана и последующая вставка — разные операции; устранить гонку одним распознаванием черновика нельзя.

Решение 5902/Q1: «Сохранить штатные терминалы, внедрять поэтапно».

Проверенные версии: Pi 1.4.0, Codex 0.160.0, Kimi Code 2.4.0. Первичное исследование: `docs/features/tmux-delivary/research.md`. Исследование Codex/Kimi уже merged в PR164, SHA af9189f832e40b10d145bc67347aabf787e3a13a, содержимое проверено rocket verify-merge5907. Pi preflight сохранён в draft PR163: `pi-live-recon.md`, `pi-modal-safety.md`, `pi-test-matrix.md` и небольшие sanitized результаты; это исследовательские данные, не product release.

В 5902/Q2 CTO выбрал подготовить полный вариант с границами публичного Pi API. Иван ещё не принял этот компромисс: для него предназначен новый gate. Старый Go по v1 продолжает разрешать ядро #5905 и ограниченное исследование #5907. Изменённый product scope Pi #5906 ждёт нового Go и stable merged/content-verified5905.

Состав этапа: ядро доставки #5905, рабочий мост Pi #5906 в границах ниже и исследовательский результат Codex/Kimi #5907. Отдельная #5911 расширяет существующий Claude SocketSender; она не входит в этот scope и ждёт merge/verify5905 плюс совместный разбор общих участков до своих product edits.

## Подходы

1. Улучшать вставку tmux: быстро, но общий ввод и гонка остаются. Не обеспечивает требуемое свойство.
2. Использовать каналы самих агентов, поэтапно сохраняя их терминалы: выбранное направление. Pi Extension API даёт прямой вход в агент, Codex требует проверки server/TUI режима, Kimi — проверки совместимости со штатным TUI.
3. Собственный клиент Rocket поверх API: большой объём изменения привычной работы; не входит в выбранное направление.

## Цели и границы

- Собственный путь доставки Pi не меняет редактор, текст и курсор: нет editor/setText/paste/submit, clear/Enter/SendKeys или имитации выбора окна. Для проверенных idle/busy/model-selector сценариев это подтверждается точными снимками до/после. Последующие действия человека и собственная логика Pi имеют границы из матрицы ниже.
- Работают существующие rocket send, сообщения вопросов, напоминания и длинные сообщения с ссылкой на inbox; отправители не выбирают новый транспорт вручную.
- При занятом агенте используем followUp: сообщение принимается в отдельную очередь и обрабатывается после текущего хода. Принятие в очередь не означает немедленное включение в текущий ответ.
- Отказ нового канала не переключает его сессию на вставку через tmux. До отправки сообщение можно повторить; после неоднозначной отправки нельзя повторять вслепую.
- Прежние сессии сохраняют старый транспорт до явного restore. Автоматически их не перезапускаем.
- Claude socket/held/fallback, прежние Codex/Kimi/Pi и интерактивные ответы пользователя не переделываются.
- Нет fork агентов, private modal fields, production monkeypatch, изменения глобальных конфигов/установок и нового UI. Пользовательские extensions не удаляются и не переставляются ради гарантии. Без обещания exactly-once при произвольных падениях процессов.

## Архитектура Pi

### Запуск и адресация

Rocket поставляет собственное расширение Pi и подключает его явным --extension в SetupWorkspace/LaunchCommand. Расширение загружается из подготовленного Rocket файла, без установки глобального плагина. Порог нового режима — Pi 1.4.0 с поддерживаемым Extension API. Версии 1.0–1.3 сохраняют прежний транспорт; сломанный или неразобранный ответ версии не включает новый канал. Новые версии должны пройти проверку возможности запуска расширения и handshake, одного номера версии недостаточно.

Сокет находится в приватном локальном runtime-каталоге Rocket с коротким путём, подходящим для macOS UDS. Каталог 0700, сокет 0600. Имя производно от идентификатора сессии; запрос содержит также идентификатор конкретного запуска. Нельзя выбирать получателя по одному имени панели, newest-файлу или похожему cwd.

Расширение открывает канал на session_start, закрывает его на session_shutdown; при смене активной Pi-сессии закрывает прежний endpoint и не принимает его сообщения в новую историю. Restore создаёт новую идентичность запуска. Kill/авария не оставляют доверенный endpoint для следующего процесса.

Выбор транспорта фиксируется в данных запуска сессии и при первой попытке сообщения: legacy или pi-uds-v1. Для существующих записей значение legacy. Отсутствие или временная недоступность сокета не изменяет сохранённый выбор.

### Обмен и подтверждения

Один JSON-объект на строку, версия протокола 1. Обязательны идентификаторы Rocket-сессии, запуска и сообщения. Текст берётся из существующего prepareText без изменения пользовательского содержимого. Максимальный размер кадра — 1 MiB; существующая подготовка длинных сообщений остаётся общей.

Расширение вызывает sendUserMessage с followUp без расширения slash-команд/шаблонов и не обращается к editor setText/submit или синтетическому вводу. Повтор одного ID в том же живом запуске не вызывает повторную подачу текста; одинаковый текст с разными ID остаётся двумя разными сообщениями.

Состояния отправки:

- not_sent: доказано, что агенту ничего не подавалось (например, target/frame/pre-API guard отклонил запрос). Допускается обычный ограниченный повтор, после исчерпания лимита — честный отказ.
- accepted: мост принял запрос; Rocket сохраняет accepted и проверяет существующий Pi transcript через DeliveryConfirmer.
- unknown: соединение оборвалось после возможной передачи; сообщение также остаётся под подтверждением, без слепой повторной подачи.
- delivered: только точное, с допустимой нормализацией пробелов существующего confirmer, пользовательское сообщение в правильной истории после сохранённого момента отправки. Одна запись не подтверждает два равных текста с разными ID; потреблённое доказательство переживает Recover и нужное pending-подтверждению хранение. Идентичность сессии/запуска не выводится из editor echo или похожего cwd.

После вызова API, который уже мог принять сообщение, нельзя возвращать ложный NotSent: accepted/unknown ждут доказательства по истории. В частности, асинхронная ошибка обработки, в том числе compaction/input handler, не разрешает автоматическую повторную подачу. Сам вызов Extension API не подтверждает сохранение: он запускает асинхронную операцию. Старое правило accepted → повтор по отсутствию текста на экране не применяется к pi-uds-v1. Если подтверждения нет, при завершении/restore получателя либо по существующему QueueTimeout сообщение становится failed с причиной native_delivery_unconfirmed; если таймаут отключён, ожидание сохраняется до завершения/restore. Это ограничение отражается в документации: возможна недоставка вместо риска дубля. Явный повтор пользователем остаётся отдельным действием.

Новые сообщения используют ту же маршрутизацию, expiry и события очереди. Момент начала отправки и выбранный транспорт сохраняются до побочного действия; при Recover сообщения нового транспорта в delivering переводятся в accepted/проверку, а не переотправляются автоматически.

### Очередь Rocket

Новый NativeSender не подменяет Claude SocketSender. Native маршрут выбирается до проверок визуального черновика/диалога. Он обходится без tmux Inject/Capture для доказательства доставки; состояние приёма в расширении определяет возможность подачи. Известные мостику состояния prompt/compaction блокируют вызов API и дают not_sent. Скрытое или запоздало сообщённое состояние не гарантирует такого отказа: агент может начать ход при открытом диалоге. Терминальные состояния сессии и истечение queued-сообщений продолжают учитываться.

## Границы состояний Pi

Гарантия моста — отсутствие собственного вмешательства в ввод. Это не гарантия неизменного курсора после любого дальнейшего действия Pi или стороннего расширения. Нельзя объявить реальную потерю черновика, синтетическое подтверждение выбора или неверную историю допустимым «поведением Pi», если это следствие доставки: такой результат останавливает release и требует пересмотра.

| Состояние | Что известно сейчас | Допустимое поведение и граница |
| --- | --- | --- |
| Idle и busy с русским одно-/многострочным черновиком | Live 4/4 PASS на stock Pi 1.4.0, локальный детерминированный provider | Вызов followUp; точные текст/курсор сохраняются до/после доставки и обработки. Accepted не равно delivered |
| Встроенный model selector | Live PASS: окно остаётся открытым, ввод идёт в поиск, Escape возвращает тот же редактор, внешнее сообщение в истории один раз | Разрешено принимать; мост не делает выбор и не закрывает окно |
| Другие селекторы через общий showSelector | Только вывод из общей ветки исходников, отдельных live-прогонов нет | Такой вывод не выдаётся за live proof; доставка не должна менять фокус/редактор или подтверждать выбор |
| Обычные окна extensions select/confirm/input/editor | Публичные ui_prompt_start/end есть; production-проверки ещё предстоят | Пока guard знает об окне — not_sent до API. После возможного вызова API — accepted/unknown, без слепого повтора |
| Окно extensions с задержанным событием | Live timing-проба: чужой более ранний async handler задержал guard на 1202 ms, ход начался при открытом окне; control без него — 0 ms | Это явное исключение: возможен ход при открытом окне. Причина — последовательный await handlers; queueMicrotask сам по себе не доказательство гонки |
| Login/OAuth и прочие скрытые модальные состояния | Source-only, нет полного публичного сигнала; live не проверено | Абсолютный pre-API отказ не обещается; приём может запустить ход. Реальные credentials для тестов не использовать; непроверенное указывать явно |
| Reload/session switch | Lifecycle-сигналы поддерживаются, production bridge ещё не проверен | Закрыть старый endpoint, запретить обработку старого запроса в новой истории; возможная уже начатая отправка остаётся unknown/accepted, доказательство только в нужной истории |
| Compaction | Есть before/success/failure events; isIdle также false при обычном busy, поэтому нельзя отказать всему busy | Известное состояние — not_sent до API. Запоздалое событие/асинхронная обработка после API — accepted/unknown до истории либо native_delivery_unconfirmed. Синхронный guard-to-call участок без await сам по себе не окно межзадачной гонки |
| Escape/dequeue после busy followUp | Исходники Pi: очередь объединяется с редактором через setText; live сценарий ещё предстоит | Pi может добавить queued текст к черновику и поставить курсор в конец. Не восстанавливать курсор скрытой записью в редактор. Наличие текста в редакторе не delivered |
| Закрытие custom UI extensions | Исходники не-overlay close делают setText(savedText); live сценарий ещё предстоит | Сам Pi может сдвинуть курсор; мост не должен добавлять свою мутацию. Для произвольного чужого custom UI общей гарантии нет |

Все указанные live-пробы используют изолированный локальный provider, а не DeepSeek. Они доказывают поведение штатного TUI/API в этих сценариях и не доказывают работу внешнего модельного провайдера. Невозможную гарантию всех произвольных extensions нельзя заменить конечным набором тестов.

## Codex и Kimi: результат исследования первого этапа

Codex: PR164 фиксирует отдельный app-server + штатный TUI --remote и внешний отправитель с общим thread UUID; подтверждены idle/busy, follow-up, окружение двух изолированных серверов, сохранение черновика и восстановление после перезапуска сервера. **Mid-line cursor не доказан**, отдельный restart TUI не проверен. Ограниченный probe завершился timeout observer, хотя TUI показал завершённый ход. Production адаптер и --no-daemon не меняются; общей exactly-once гарантии исследование не даёт.

Kimi: в проверенной официальной поверхности 2.4.0 поддерживаемый внешний вход в тот же процесс stock TUI не найден. REST/ACP — другие backend-процессы; захват lock у живой сессии и второй писатель исключены. Background completion — уведомление agent-owned задачи, не общий inbox. Это ограниченный отрицательный результат, не утверждение о невозможности любого внутреннего решения.

Результаты уже сохранены в `codex-live-recon.md`, `kimi-native-recon.md` и sanitized evidence. Новые платные/live-пробы для этого этапа не нужны. Для рабочего подключения Codex/Kimi потребуются следующая полная спецификация и Go.

## Проверка и приёмка

- Pi: один и несколько внутренних текстов при пустом поле, одно-/многострочном русском черновике и курсоре внутри строки; idle и busy. Без последующих editor-changing действий Pi точные черновик/курсор сохраняются, сообщение появляется в правильной истории один раз. Проверить после production bridge, а не подменять его успехом preflight.
- Повтор ID, одинаковые тексты с разными ID, длинное сообщение, невалидный/слишком большой кадр, неверная сессия/запуск.
- Разрыв до передачи, после передачи, потеря сокета, перезапуск Rocket, restore/kill Pi, переключение истории. Нет скрытого возврата в tmux и автоматического дубля из unknown.
- Fake runtime тесты доказывают отсутствие Inject/SendKeys/Capture на новом маршруте; регрессии Claude/legacy остаются зелёными.
- Изолированные синтетические проверки штатных extension prompts/custom UI, delayed ordering/control, selector, compaction/error/deferred handling, Escape/dequeue, reload/switch/kill. Для каждого результата указать exact outcome, историю, draft/cursor и границу доказанного. Login/реальный OAuth без соответствующей controlled проверки остаётся непроверенным; не инициировать реальный login.
- Тесты не используют платных провайдеров, реальные auth, рабочие сессии или общий daemon. Новый gate разрешает только указанные изолированные синтетические сценарии; deployment/restart общего daemon и live send участникам из него не следуют.
- Если доставка вызывает реальную потерю draft, синтетический выбор, неверную адресацию или неподтверждаемую корректность истории, остановить подключение и вынести факты на пересмотр; не ослаблять описание задним числом.
- Для Codex/Kimi приложены версии, команды, редактированные свидетельства и разделение проверенного/непроверенного.
- Все PR имеют зелёные доступные CI-проверки; отсутствие CI фиксируется явно и заменяется локальными обязательными проверками, а не выдается за зелёный CI.

## Что изменилось относительно Spec v1

| Было | Стало |
| --- | --- |
| Отказ до API во всех состояниях, где безопасность не доказана | Отказ по известным prompt/compaction guards; при скрытом/запаздывающем окне возможен ход агента, это явный принимаемый риск |
| Сохранение черновика/курсора без разделения дальнейших действий | Доставка сама не мутирует ввод; штатные Escape/dequeue/custom close Pi могут изменить курсор/вернуть очередь |
| Live-проверки ещё предстояли | Есть конкретные preflight результаты и матрица live/source-only/unverified; product bridge ещё предстоит проверить |
| Исследование Codex/Kimi запланировано | PR164 merged и content-verified; ограничения сохранены, новых probes не требуется |

Не меняются stock TUI, сохранение пользовательских extensions, отсутствие tmux fallback, outcome/recovery/one-to-one history proof, private UDS и границы Codex/Kimi/Claude. Изменённая часть Pi начинает исполняться только после нового Go и verified merge5905. На gate можно принять эти границы либо отложить Pi.

## Оставлено исполнителям

Внутреннее размещение типов и функций, способ наблюдения ошибок/приёма внутри Pi и реализация управления сокетом — в пределах контракта выше. Схемы и handshake уточняются по установленному Pi. Расширение не должно обещать подтверждение, которого API не предоставляет. Новые продуктовые компромиссы, ослабление гарантий и изменение объёма требуют вопроса и новой версии спецификации с Go.
