# Очередь сообщений

## Проблема, которую решаем

В AO `ao send` — синхронная инжекция текста в tmux получателя: отправитель сам ждёт (до 10 минут), пока получатель освободится, ретраит Enter, и при неудаче сообщение просто теряется. Нет истории, нет очереди, отправитель-агент блокируется.

В rocket отправка и доставка разделены: **отправка — мгновенная запись в очередь демона; доставка — фоновая, когда получатель готов принять ввод.**

## Поток

```
rocket send billing-orch "текст"
  → POST /v1/messages {from: <из ROCKET_SESSION_ID>, to, body}
  → INSERT messages(status=queued) → ответ {id, queued}   (отправитель свободен)

доставщик (в демоне, пер-получатель):
  ждёт activity получателя ∈ {ready, idle, waiting_input}
  → проверка черновика в composer'е: занят — остаёмся в queued (см. draft guard)
  → status=delivering
  → runtime.Inject(получатель, "[from <from>] <body>")  # C-u, paste-buffer, адаптивный Enter
  → подтверждение: черновик покинул composer (capture-pane)
  → status=delivered, событие message.delivered
```

## Правила

- **FIFO пер-получатель.** Сообщения одному получателю доставляются в порядке постановки; следующее не начинается, пока текущее не delivered/failed.
- **Готовность получателя:** `ready`, `idle` — доставляем; `waiting_input` — доставляем (агент ждёт ввода — сообщение и есть ввод); `active` — ждём; `blocked`, `exited` — не доставляем, см. ниже.
- **Pending-квиз блокирует доставку.** Пока у получателя открыт TUI-квиз AskUserQuestion (`pending_quiz` сессии непустой — см. [13-chat.md](13-chat.md), раздел «Квизы»), сообщения ему не доставляются и остаются `queued` (инжекция текста сломала бы виджет): попытки не тратятся, `failed` не ставится. После закрытия квиза (`session.quiz_resolved`) доставка возобновляется сразу — событие будит воркер очереди, 2-секундный фолбэк-тикер страхует.
- **Черновик человека блокирует доставку (draft guard).** Доставка начинается с `C-u`, который стирает всё, что лежит в строке ввода получателя, — включая сообщение, которое человек в этот момент дописывает (реальная потеря текста). Поэтому перед `C-u` composer получателя проверяется: если в нём лежит непустой черновик, сообщение остаётся `queued`, `C-u` не отправляется, попытки не тратятся, `failed` не ставится — ровно как при pending-квизе. Проверка идёт дважды: в очереди перед клеймом сообщения и внутри `runtime.Inject` вплотную к самому `C-u` (там она возвращает `ErrComposerBusy`, и очередь возвращает сообщение в `queued`, не съедая попытку). Через `composer_busy_deadline` (yaml, по умолчанию 10m) непрерывной занятости доставка идёт по-старому — черновик стирается: брошенный черновик (или ложное срабатывание эвристики) не должен держать очередь получателя вечно. Общий `queue_timeout` при этом продолжает действовать, потому что сообщение всё это время лежит в `queued`.
- **Эвристика черновика намеренно консервативна.** Распознаются только проверенные формы composer'а Claude Code (строка `❯ …` между двумя горизонтальными линейками; старый вариант в рамке `│ > … │`); подсказки-плейсхолдеры (`Press up to edit queued messages`, `Try "…`) и пустой composer занятостью не считаются. Незнакомый рендер (в том числе codex, чей composer не проверялся) и нечитаемая панель — «не занято», то есть поведение как до гварда: цена ложного «занято» — отложенное сообщение, цена ложного «свободно» — уничтоженный текст человека, поэтому неопределённость всегда трактуется в сторону «не занято». Новая форма composer'а добавляется в `runtime.LooksLikeUserDraft`.
- **Формат:** если `from_session` задан — префикс `[from <id>] `; от человека/системы — без префикса. Многострочные тексты и файлы (`--file`) передаются как есть через paste-buffer.
- **Записи вопросных тредов** идут той же очередью, но со своей рамкой: `[#1023/Q2 reply from cto] <текст>` для треда задачи и `[cto/Q1 answer from human] ...` для треда роли — локальная ссылка, вид записи и автор (см. [12-tasks.md](12-tasks.md)). Второго префикса `[from ...]` у них не появляется: автор уже назван в рамке. Ссылка в рамке — это тот же id, которым получатель отвечает: `rocket task reply #1023/Q2 ...` (решётка необязательна).
- **Большие сообщения — доставка через inbox-файл.** Прямая инжекция большого текста в TUI (в частности, Claude Code) иногда теряет часть паста, даже когда сама инжекция технически проходит успешно. Поэтому тело сообщения, превышающее `large_message_threshold` байт (по умолчанию 2048) или 20 строк, для получателя с воркспейсом (`WorktreePath != ""`) записывается целиком в `<worktree>/.rocket/inbox/msg-<id>.md` (атомарно: temp-файл + rename), а в TUI инжектируется короткий указатель — `[from X] [large message] Full text written to .rocket/inbox/msg-<id>.md — read that file now.` Если получатель без воркспейса, или запись файла не удалась — доставляется полное тело по-старому (сбой записи логируется как warn). Файл не удаляется после прочтения — он же служит историей. Как дополнительная защита, `runtime.Inject` вставляет паузу перед первым Enter для текстов длиннее 20 строк (`200ms + 5ms × строк`, не более 2s), давая TUI время «зарегистрировать» большой паст перед сабмитом.
- **Ретраи:** до 5 попыток инжекции с экспоненциальной паузой (подтверждение через capture-pane). После — `failed` + событие `message.failed`.
- **Получатель exited/killed:** сообщение сразу `failed`; отправителю-агенту heartbeat/статус покажут, что адресат мёртв.
- **Таймаут ожидания готовности:** конфигурируемый (по умолчанию 30 минут в очереди) → `failed`.
- **История:** `rocket send --wait` поллит статус до delivered/failed; `GET /v1/messages?session=` — переписка сессии для CLI и дашборда.

## Почему всё же инжекция в терминал, а не «настоящий» канал

Агенты (Claude Code, Codex) — интерактивные TUI: единственный универсальный способ передать им ход — пользовательский ввод. Очередь в демоне убирает хрупкость (потери, блокировки, отсутствие истории), сохраняя универсальность механизма. Если агенты получат нормальный API для входящих сообщений (например, MCP-инструмент с подпиской), доставщик станет ещё одним транспортом за тем же интерфейсом очереди — модель данных не изменится.
