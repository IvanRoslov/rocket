# Очередь сообщений

## Проблема, которую решаем

В AO `ao send` — синхронная инжекция текста в tmux получателя: отправитель сам ждёт (до 10 минут), пока получатель освободится, ретраит Enter, и при неудаче сообщение просто теряется. Нет истории, нет очереди, отправитель-агент блокируется.

В rocket отправка и доставка разделены: **отправка — мгновенная запись в очередь демона; доставка — фоновая, когда получатель готов принять ввод.**

## Поток

```
rocket send billing-orch "текст"
  → POST /v1/messages {from: <из ROCKET_SESSION_ID>, to, body}
  → INSERT messages(status=queued) → ответ {id, queued}   (отправитель свободен)

доставщик (в демоне, пер-получатель):
  ждёт activity получателя ∈ {ready, idle, waiting_input}
  → выбор транспорта (заново на каждом проходе)
  → status=delivering
  → транспорт 1 — сокет Claude Code (если доступен):
       socketmsg.Send(<сокет получателя>, "[from <from>] <body>")
       # composer не трогаем: ни draft guard, ни pending-квиз не блокируют
       → успешная запись = delivered
  → транспорт 2 — tmux (фолбэк при любой ошибке выше):
       проверка черновика в composer'е: занят — остаёмся в queued (см. draft guard)
       runtime.Inject(получатель, "[from <from>] <body>")  # C-u, paste-buffer, адаптивный Enter
       → подтверждение: черновик покинул composer (capture-pane)
  → status=delivered, событие message.delivered
```

## Правила

- **FIFO пер-получатель.** Сообщения одному получателю доставляются в порядке постановки; следующее не начинается, пока текущее не delivered/failed.
- **Готовность получателя:** `ready`, `idle` — доставляем; `waiting_input` — доставляем (агент ждёт ввода — сообщение и есть ввод); `active` — ждём; `blocked`, `exited` — не доставляем, см. ниже.
- **Pending-квиз блокирует tmux-доставку, но не сокет.** Пока у получателя открыт TUI-квиз AskUserQuestion (`pending_quiz` сессии непустой — см. [13-chat.md](13-chat.md), раздел «Квизы»), инжекция текста сломала бы виджет, поэтому tmux-путь закрыт. Если получатель достижим по сокету (см. «Транспорты доставки»), сообщение доставляется по нему прямо во время квиза: сокет не трогает TUI. Если сокета нет — сообщение остаётся `queued`: попытки не тратятся, `failed` не ставится. После закрытия квиза (`session.quiz_resolved`) доставка возобновляется сразу — событие будит воркер очереди, 2-секундный фолбэк-тикер страхует.
- **Черновик человека блокирует доставку (draft guard).** Доставка начинается с `C-u`, который стирает всё, что лежит в строке ввода получателя, — включая сообщение, которое человек в этот момент дописывает (реальная потеря текста). Поэтому перед `C-u` composer получателя проверяется: если в нём лежит непустой черновик, сообщение остаётся `queued`, `C-u` не отправляется, попытки не тратятся, `failed` не ставится — ровно как при pending-квизе. Проверка идёт дважды: в очереди перед клеймом сообщения и внутри `runtime.Inject` вплотную к самому `C-u` (там она возвращает `ErrComposerBusy`, и очередь возвращает сообщение в `queued`, не съедая попытку). Через `composer_busy_deadline` (yaml, по умолчанию 10m) непрерывной занятости доставка идёт по-старому — черновик стирается: брошенный черновик (или ложное срабатывание эвристики) не должен держать очередь получателя вечно. Общий `queue_timeout` при этом продолжает действовать, потому что сообщение всё это время лежит в `queued`.

  Всё это относится к **tmux-пути**. Если получатель достижим по сокету Claude Code, гвард не применяется вовсе: сокет не шлёт `C-u` и не трогает строку ввода, поэтому черновик человека переживает доставку без всякого откладывания — сообщение приходит сразу, черновик остаётся на месте. `composer_busy_deadline` при этом не тикает: «занятость» копится только там, где ей есть что стирать. Ради этого сценария транспорт и делался.
- **Эвристика черновика намеренно консервативна.** Распознаются только проверенные формы composer'а Claude Code (строка `❯ …` между двумя горизонтальными линейками; старый вариант в рамке `│ > … │`); подсказки-плейсхолдеры (`Press up to edit queued messages`, `Try "…`) и пустой composer занятостью не считаются. Незнакомый рендер (в том числе codex, чей composer не проверялся) и нечитаемая панель — «не занято», то есть поведение как до гварда: цена ложного «занято» — отложенное сообщение, цена ложного «свободно» — уничтоженный текст человека, поэтому неопределённость всегда трактуется в сторону «не занято». Новая форма composer'а добавляется в `runtime.LooksLikeUserDraft`.
- **Подсказка агента — не черновик.** Claude Code рисует в composer'е ghost-text: предсказанное сообщение, которого человек не набирал. В обычном `capture-pane -p` оно побайтно неотличимо от черновика, и доставка откладывалась на весь `composer_busy_deadline` из-за пустого по сути composer'а. Различает их атрибут яркости: подсказка целиком лежит внутри SGR 2 (dim), реальный ввод идёт нормальной интенсивностью. Поэтому оба места проверки читают панель через `capture-pane -p -e` (метод `runtime.CaptureEscaped`; обычный `Capture` для подтверждения доставки и активности остался плоским), а `LooksLikeUserDraft` разбирает escape-последовательности и выбрасывает dim-руны из содержимого composer'а: целиком dim — «не занято», хоть одна не-dim руна (человек дописывает подсказку) — «занято». Рамки и линейки composer'а при этом опознаются по всему видимому тексту независимо от яркости: TUI рисует их приглушёнными, и выбрасывание dim-чрома просто отключило бы гвард. Захват без `-e` (или чужой рендер без атрибутов) трактуется как раньше.
- **Формат:** если `from_session` задан — префикс `[from <id>] `; от человека/системы — без префикса. Многострочные тексты и файлы (`--file`) передаются как есть через paste-buffer.
- **Записи вопросных тредов** идут той же очередью, но со своей рамкой: `[#1023/Q2 reply from cto] <текст>` для треда задачи и `[cto/Q1 answer from human] ...` для треда роли — локальная ссылка, вид записи и автор (см. [12-tasks.md](12-tasks.md)). Второго префикса `[from ...]` у них не появляется: автор уже назван в рамке. Ссылка в рамке — это тот же id, которым получатель отвечает: `rocket task reply #1023/Q2 ...` (решётка необязательна).
- **Большие сообщения — доставка через inbox-файл.** Прямая инжекция большого текста в TUI (в частности, Claude Code) иногда теряет часть паста, даже когда сама инжекция технически проходит успешно. Поэтому тело сообщения, превышающее `large_message_threshold` байт (по умолчанию 2048) или 20 строк, для получателя с воркспейсом (`WorktreePath != ""`) записывается целиком в `<worktree>/.rocket/inbox/msg-<id>.md` (атомарно: temp-файл + rename), а в TUI инжектируется короткий указатель — `[from X] [large message] Full text written to .rocket/inbox/msg-<id>.md — read that file now.` Если получатель без воркспейса, или запись файла не удалась — доставляется полное тело по-старому (сбой записи логируется как warn). Файл не удаляется после прочтения — он же служит историей. Как дополнительная защита, `runtime.Inject` вставляет паузу перед первым Enter для текстов длиннее 20 строк (`200ms + 5ms × строк`, не более 2s), давая TUI время «зарегистрировать» большой паст перед сабмитом.
- **Ретраи:** до 5 попыток инжекции с экспоненциальной паузой (подтверждение через capture-pane). После — `failed` + событие `message.failed`.
- **Получатель exited/killed:** сообщение сразу `failed`; отправителю-агенту heartbeat/статус покажут, что адресат мёртв.
- **Таймаут ожидания готовности:** конфигурируемый (по умолчанию 30 минут в очереди) → `failed`.
- **История:** `rocket send --wait` поллит статус до delivered/failed; `GET /v1/messages?session=` — переписка сессии для CLI и дашборда.

## Транспорты доставки

Сообщение доставляется одним из двух способов. Выбор делается заново на каждом проходе доставщика.

### Сокет Claude Code (предпочтительный)

Живая сессия Claude Code слушает unix-сокет для cross-session сообщений (протокол разобран в [design/cc-socket-protocol.md](design/cc-socket-protocol.md)). Доставка по нему **не трогает composer получателя** — это и есть главная причина существования транспорта: инжекция в tmux начинается с `C-u`, который стирает недописанный человеком черновик, а сокет кладёт сообщение в очередь промптов, не касаясь строки ввода. Как следствие, сокет — единственный путь доставить сообщение, пока человек печатает или пока на экране висит квиз.

Сокет используется, только если выполнено всё сразу:

- у получателя `agent == "claude-code"` (ни у кого больше такого сокета нет);
- включён конфиг `socket_delivery` (по умолчанию `true`);
- в реестре `~/.claude/sessions/<pid>.json` нашлась **ровно одна** запись, у которой префикс поля `tmux` до `:` равен `tmux_name` сессии rocket;
- у записи непустой `messagingSocketPath` и `peerProtocol == 1`;
- `connect` по этому сокету удался.

Про последние два пункта. `peerProtocol` — прямой сигнал версии протокола; наш клиент разбирался против версии `1`, и при росте значения мы считаем себя несовместимыми, а не угадываем формат. `connect` обязателен потому, что мёртвый сокет-файл остаётся на диске после падения процесса — наличие файла не доказывает ничего.

**Ключ сопоставления — имя tmux-сессии, а не рабочий каталог.** Несколько процессов Claude могут делить один worktree (человек открыл второй claude в том же каталоге), и тогда `cwd` неоднозначен; имя tmux-сессии уникально на сессию rocket по построению (`store.Session.TmuxName`). Если под одно имя всё же попали две живые записи, это считается неоднозначностью и сокет не используется: доставить не в ту сессию хуже, чем откатиться на tmux.

В сообщение кладётся `session_id` найденной записи: если pid успели переиспользовать между чтением реестра и записью, новый владелец сокета отбросит сообщение, а не покажет чужой текст. `from-mode` не выставляется намеренно — заявлять `bypass` значило бы протаскивать наши сообщения мимо гварда получателя с правами, на которые мы не имеем оснований.

### tmux-инжект (фолбэк)

Любой промах на любом шаге выше — нет записи в реестре, не тот `peerProtocol`, сокет не отвечает, ошибка `connect`/`write` — приводит к инжекции в tmux **в рамках той же попытки**. Сбой сокета никогда не проваливает сообщение и не тратит попытку; он пишется в лог на уровне info. Дальше действуют все обычные правила tmux-пути, включая draft guard и ретраи.

### Семантика delivered

В протоколе нет подтверждения в том же соединении: успешная запись означает «байты приняты ядром», а не «получатель прочитал». Квитанции существуют только для придержанных сообщений, а сессии, поднятые rocket, работают с `crossSessionInbound: "accept"` — придержания у них не бывает. Поэтому **успешная запись в сокет считается доставкой**, ровно так же, как подтверждение инжекции по capture-pane считается доставкой на tmux-пути. Обратного канала rocket не слушает.

Одно следствие стоит знать: у Claude Code есть антифлуд на отправителя (дедупликация одинаковых тел в окне 30 с, token bucket). Отброшенные им сообщения квитанций не порождают, так что «доставлено» и «съедено дедупликацией» снаружи неразличимы.

### Тело сообщения не зависит от транспорта

По сокету уходит ровно тот же текст, что ушёл бы в tmux, — включая правило больших сообщений: тело сверх `large_message_threshold` (или 20 строк) точно так же уезжает в `<worktree>/.rocket/inbox/msg-<id>.md`, а по сокету идёт короткий указатель на файл. Так один и тот же message выглядит у получателя одинаково независимо от того, каким путём приехал.

### Конфиг

`socket_delivery: false` в `config.yaml` выключает транспорт целиком — вся доставка идёт через tmux. Это escape hatch на случай, если протокол Claude Code поедет: выключение не ломает доставку, а возвращает прежнее поведение со стиранием черновика.

## Почему всё же инжекция в терминал, а не «настоящий» канал

Агенты (Claude Code, Codex) — интерактивные TUI: единственный универсальный способ передать им ход — пользовательский ввод. Очередь в демоне убирает хрупкость (потери, блокировки, отсутствие истории), сохраняя универсальность механизма. Если агенты получат нормальный API для входящих сообщений (например, MCP-инструмент с подпиской), доставщик станет ещё одним транспортом за тем же интерфейсом очереди — модель данных не изменится.

**Обновление.** У Claude Code такой канал появился — cross-session UDS-инбокс, и rocket уже предпочитает его инжекции (см. «Транспорты доставки»). Предсказание выше сбылось буквально: модель данных очереди не изменилась, транспорт встал за тот же интерфейс, поменялась одна ветка в доставщике. Инжекция остаётся универсальным фолбэком — для всех прочих агентов и для сессий Claude Code без живого сокета.
