# Оркестраторы

## Запуск: `rocket up`

```
rocket up "перенести биллинг на v2 API" --project api
→ SLUG=billing-v2   SESSION=billing-v2-orch
```

Демон:
1. Генерирует slug из описания (транслитерация/LLM не нужны: до 4 слов, `[a-z0-9-]`, при коллизии суффикс `-2`).
2. Создаёт worktree хаб-проекта на ветке `orch/<slug>`.
3. Запускает агента с **системным промптом оркестратора** и передаёт **kickoff-сообщение** первым ходом.

## Системный промпт оркестратора

Шаблон (embedded в бинарник, переопределяется файлом `~/.rocket/prompts/orchestrator.md`), в него подставляются: id сессии, slug, хаб-проект, список разрешённых проектов (хаб + `links`), команды CLI. Содержание:

- Ты — оркестратор фичи `<slug>`. Твоя работа: декомпозировать фичу, спавнить воркеров, координировать, доводить до смерженных PR.
- Спавнить воркеров можно только в проектах: `<список>`. Команда: `rocket spawn --task <t> --project <p> --prompt "<бриф>"`.
- Один воркер = одна задача = один PR. Независимые задачи спавнь параллельно.
- Общение только через `rocket send` (никогда напрямую tmux). Воркерам пиши по-английски; с человеком — на его языке.
- Воркеры не имеют доступа к человеку: их вопросы приходят тебе (`[from <id>] ...`) — отвечай сам, к человеку эскалируй только решения уровня продукта.
- Статус своих воркеров: `rocket status <slug>`. Мёртвого воркера можно `rocket restore` или пересоздать.
- Веди фичевый дизайн-док в хаб-репо (`docs/features/<slug>.md`) как источник правды; итог фичи — PR в хаб при необходимости.
- Когда все PR смержены и фича закрыта — доложи человеку и заверши работу (сессию убьёт человек или авто-cleanup).

## Kickoff-сообщение

Первое сообщение задаёт конкретную фичу: описание от пользователя, требование сначала уточнить у человека детали (перед декомпозицией), пайплайн `research → plan → implement → verify`, гейты между стадиями. Kickoff — данные (описание) + процедура; процедура редактируется тем же файлом-шаблоном.

## Спавн воркеров

`rocket spawn` из сессии оркестратора (проверяется по `ROCKET_SESSION_ID`):
- имя `<slug>-<task>`, ветка `feature/<slug>/<task>`, `parent_id` = оркестратор, `feature_slug` наследуется;
- бриф из `--prompt` становится первым ходом воркера; расширенный бриф оркестратор досылает `rocket send --file`;
- воркеру в системный промпт добавляется: ты воркер задачи `<task>` фичи `<slug>`, твой оркестратор `<parent>`, все вопросы — `rocket send <parent>`, человек недоступен, работай неинтерактивно, результат — PR из своей ветки.

## Heartbeat

Цикл демона (каждые 5m, конфигурируемо) для каждого живого оркестратора:

1. Собирает воркеров (`parent_id`), их `activity`, PR/CI, время последней активности.
2. Определяет застрявших: воркер в `idle`/`blocked`/`waiting_input` дольше 15m, или `exited` без merged PR, или `ci_state=failing` без движения.
3. Если есть застрявшие, а сам оркестратор не `active` — кладёт ему в очередь сводку:
   ```
   [rocket heartbeat] Feature billing-v2 status:
   - billing-v2-backend: blocked 22m, PR #14 CI failing
   - billing-v2-ui: idle 40m, no PR
   Act autonomously: unblock, restart or replace stalled workers.
   ```
4. Анти-спам: не чаще одного heartbeat на оркестратора за интервал; событие `orchestrator.heartbeat_sent`.

Оркестраторы в `blocked`/`exited` heartbeat не будит — это сигнал человеку (`rocket ls` подсветит; дашборд/нотификации позже).

## Завершение фичи

- Штатно: пользователь видит доклад оркестратора → `rocket kill <orch> --cascade --cleanup` (или оркестратор убивает своих воркеров сам по мере merge, а пользователь убивает только его).
- Воркеры чистятся автоматически при merge их PR ([09-github.md](09-github.md)).
- Оркестратор автоматически не чистится никогда (урок из AO — авто-cleanup оркестраторов по merge PR приводил к убийству живой координации).
