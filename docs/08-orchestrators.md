# Оркестраторы

## Запуск: `rocket task start` / `rocket up`

Оркестратор всегда назначается на задачу ([12-tasks.md](12-tasks.md)): либо на существующую (`rocket task start 12`), либо `rocket up "<описание>"` создаёт задачу и назначает сразу.

```
rocket up "перенести биллинг на v2 API" --project billing
→ TASK=#12   SLUG=billing-v2   SESSION=billing-v2-orch
```

Демон:
1. Генерирует slug из заголовка задачи (транслитерация/LLM не нужны: до 4 слов, `[a-z0-9-]`, при коллизии суффикс `-2`).
2. Создаёт worktree в **main-репозитории проекта** на ветке `orch/<slug>`.
3. Запускает агента с **системным промптом оркестратора** и передаёт **kickoff-сообщение** первым ходом.

## Системный промпт оркестратора

Полный референс-текст шаблона — [prompts/orchestrator.md](prompts/orchestrator.md) (embedded в бинарник, переопределяется файлом `~/.rocket/prompts/orchestrator.md`). В него подставляются: id сессии, slug, проект, список репозиториев проекта (main + linked), команды CLI. Суть:

- Ты — оркестратор фичи `<slug>` проекта `<project>`. Твоя работа: декомпозировать фичу, спавнить воркеров, координировать, доводить до смерженных PR.
- Спавнить воркеров можно только в репозиториях: `<список>`. Команда: `rocket spawn --task <t> --repo <r> --prompt "<бриф>"`.
- Один воркер = одна задача = один PR. Независимые задачи спавнь параллельно.
- Общение только через `rocket send` (никогда напрямую tmux). Воркерам пиши по-английски; с человеком — на его языке.
- Воркеры не имеют доступа к человеку: их вопросы приходят тебе (`[from <id>] ...`) — отвечай сам, к человеку эскалируй только решения уровня продукта.
- Статус своих воркеров: `rocket status <slug>`. Мёртвого воркера можно `rocket restore` или пересоздать.
- **Веди задачу #<id> как источник правды**: спека — `rocket task doc put <id> --kind spec`, план/декомпозиция — `--kind plan`; каждое значимое решение — `rocket task log <id> --kind decision`, каждая проблема — `--kind problem`. Подзадачи на воркеров создаются автоматически при spawn; декомпозицию до спавна фиксируй заранее через `rocket task add --parent <id>` и спавнь с `--subtask`.
- Когда все PR смержены и фича готова к приёмке — загрузи итоговый отчёт (`--kind report`), переведи задачу в review (`rocket task move <id> review`) и доложи человеку. Задачу в done переводит человек.

## Kickoff-сообщение

Полный референс-текст — [prompts/kickoff.md](prompts/kickoff.md). Первое сообщение задаёт конкретную фичу: номер задачи и её описание, требование сначала уточнить у человека детали и подтвердить спеку (перед имплементацией), пайплайн `clarify → research → spec/plan → execute → deliver` с гейтами.

## Спавн воркеров

`rocket spawn` из сессии оркестратора (проверяется по `ROCKET_SESSION_ID`):
- имя `<slug>-<task>`, ветка `feature/<slug>/<task>`, `parent_id` = оркестратор, `feature_slug` наследуется;
- бриф из `--prompt` становится первым ходом воркера; расширенный бриф оркестратор досылает `rocket send --file`;
- системный промпт воркера — полный референс-текст в [prompts/worker.md](prompts/worker.md): ты воркер задачи `<task>` фичи `<slug>`, твой оркестратор `<parent>`, все вопросы — `rocket send <parent>`, человек недоступен, работай неинтерактивно, результат — PR из своей ветки; веди журнал своей подзадачи; отчитайся оркестратору о PR/блокировке/завершении.

## Heartbeat

Цикл демона (каждые 5m, конфигурируемо) для каждого живого оркестратора, **чья задача в статусе `in_progress`** — задачи в `review` (ждут приёмки человеком), `done` и `cancelled` heartbeat не трогает:

1. Собирает воркеров (`parent_id`), их `activity`, PR/CI, время последней активности.
2. Определяет застрявших: воркер в `idle`/`blocked`/`waiting_input` дольше 15m, или `exited` без merged PR, или `ci_state=failing` без движения.
3. Если есть застрявшие, а сам оркестратор не `active` — кладёт ему в очередь сводку:
   ```
   [rocket heartbeat] Feature billing-v2 status:
   - billing-v2-backend: blocked 22m, PR #14 CI failing
   - billing-v2-ui: idle 40m, no PR
   Act autonomously: unblock, restart or replace stalled workers.
   ```
4. Анти-спам: не чаще одного heartbeat на оркестратора за интервал; событие `orchestrator.heartbeat_sent`.

Оркестраторы в `blocked`/`exited` heartbeat не будит — это сигнал человеку (`rocket ls` подсветит; дашборд/нотификации позже).

### Застревание на интерактивном вводе

Отдельная ветка того же цикла: сам оркестратор может встать не на воркерах, а на вводе — открыт квиз `AskUserQuestion` (`pending_quiz` непустой) или `activity = waiting_input`. Сводка тут бесполезна: она адресована именно тому, кто ждёт нажатия клавиши, а пока открыт квиз, доставка сообщений вообще приостановлена (см. [06-messaging.md](06-messaging.md)).

Поэтому heartbeat эскалирует наружу — постоянному агенту `cto`:

1. Порог — `input_stall_threshold` (по умолчанию 10m). Отсчёт от `asked_at` квиза, если квиз есть (метка активности при открытом квизе продолжает двигаться и занизила бы ожидание), иначе от `activity_ts`; без пригодной метки времени стойло не объявляется.
2. Строка в inbox агента `cto` (`agent_inbox`, не очередь сообщений: агент может быть не запущен, эскалация не должна теряться) — с id и заголовком задачи, id сессии, длительностью, текстом первого вопроса квиза и тем, как ответить (`rocket attach <session>` или пузырь квиза в чате дашборда).
3. Событие `orchestrator.input_stalled` с `{task_id, session_id, since_seconds, kind}`, где `kind` = `quiz` | `prompt`.
4. Анти-спам — не чаще одной эскалации на оркестратора за интервал heartbeat, отдельно от обычной сводки: одно не глушит другое.

Если агент `cto` не зарегистрирован, запись в inbox не удаётся (внешний ключ на `agents`) — это логируется, а событие шины публикуется в любом случае; тик не падает. Сообщение самому застрявшему оркестратору намеренно не отправляется.

## Завершение фичи

- Штатно: пользователь видит доклад оркестратора → `rocket kill <orch> --cascade --cleanup` (или оркестратор убивает своих воркеров сам по мере merge, а пользователь убивает только его).
- Воркеры чистятся автоматически при merge их PR ([09-github.md](09-github.md)).
- Оркестратор автоматически не чистится никогда (урок из AO — авто-cleanup оркестраторов по merge PR приводил к убийству живой координации).
