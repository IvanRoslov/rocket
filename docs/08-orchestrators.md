# Оркестраторы

## Запуск: `rocket task start` / `rocket up`

Оркестратор всегда назначается на задачу ([12-tasks.md](12-tasks.md)): либо на существующую (`rocket task start 12`), либо `rocket up "<описание>"` создаёт задачу и назначает сразу.

```
rocket up "перенести биллинг на v2 API" --project billing
→ TASK=#12   SLUG=billing-v2   SESSION=billing-v2-orch
```

Демон:
1. Генерирует slug из заголовка задачи (транслитерация/LLM не нужны: до 4 слов, `[a-z0-9-]`, при коллизии суффикс `-2`).
2. Создаёт worktree в **main-репозитории проекта** на ветке `orch/<slug>`.
3. Запускает агента с **системным промптом оркестратора** и передаёт **kickoff-сообщение** первым ходом.

## Системный промпт оркестратора

Полный референс-текст шаблона — [prompts/orchestrator.md](prompts/orchestrator.md) (embedded в бинарник, переопределяется файлом `~/.rocket/prompts/orchestrator.md`). В него подставляются: id сессии, slug, проект, список репозиториев проекта (main + linked), команды CLI. Суть:

- Ты — оркестратор фичи `<slug>` проекта `<project>`. Твоя работа: декомпозировать фичу, спавнить воркеров, координировать, доводить до смерженных PR.
- Спавнить воркеров можно только в репозиториях: `<список>`. Команда: `rocket spawn --task <t> --repo <r> --prompt "<бриф>"`.
- Один воркер = одна задача = один PR. Независимые задачи спавнь параллельно.
- Общение только через `rocket send` (никогда напрямую tmux). Воркерам пиши по-английски; с человеком — на его языке.
- Воркеры не имеют доступа к человеку: их вопросы приходят тебе (`[from <id>] ...`) — отвечай сам, к человеку эскалируй только решения уровня продукта.
- Статус своих воркеров: `rocket status <slug>`. Мёртвого воркера можно `rocket restore` или пересоздать.
- **Веди задачу #<id> как источник правды**: спека — `rocket task doc put <id> --kind spec`, план/декомпозиция — `--kind plan`; каждое значимое решение — `rocket task log <id> --kind decision`, каждая проблема — `--kind problem`. Подзадачи на воркеров создаются автоматически при spawn; декомпозицию до спавна фиксируй заранее через `rocket task add --parent <id>` и спавнь с `--subtask`.
- Когда все PR смержены и фича готова к приёмке — загрузи итоговый отчёт (`--kind report`), переведи задачу в review (`rocket task move <id> review`) и доложи человеку. Задачу в done переводит человек.

## Kickoff-сообщение

Полный референс-текст — [prompts/kickoff.md](prompts/kickoff.md). Первое сообщение задаёт конкретную фичу: номер задачи и её описание, требование сначала уточнить у человека детали и подтвердить спеку (перед имплементацией), пайплайн `clarify → research → spec/plan → execute → deliver` с гейтами.

## Спавн воркеров

`rocket spawn` из сессии оркестратора (проверяется по `ROCKET_SESSION_ID`):
- имя `<slug>-<task>`, ветка `feature/<slug>/<task>`, `parent_id` = оркестратор, `feature_slug` наследуется;
- бриф из `--prompt` становится первым ходом воркера; расширенный бриф оркестратор досылает `rocket send --file`;
- системный промпт воркера — полный референс-текст в [prompts/worker.md](prompts/worker.md): ты воркер задачи `<task>` фичи `<slug>`, твой оркестратор `<parent>`, все вопросы — `rocket send <parent>`, человек недоступен, работай неинтерактивно, результат — PR из своей ветки; веди журнал своей подзадачи; отчитайся оркестратору о PR/блокировке/завершении.

## Heartbeat

Цикл демона (каждые 5m, конфигурируемо) для каждого живого оркестратора, **чья задача в работе — в `brainstorm` или `in_progress`** — задачи в `backlog`, `review` (ждут приёмки человеком), `done` и `cancelled` heartbeat не трогает. Фаза `brainstorm` входит сюда намеренно: именно на ней оркестратор чаще всего застревает на вопросе в терминале, и именно там эскалация нужнее всего:

1. Собирает воркеров (`parent_id`), их `activity`, PR/CI, время последней активности.
2. Отбрасывает неживых: застрять может только сессия в состоянии `spawning`/`running`. Убитый или завершённый воркер навсегда сохраняет свою последнюю `activity` (обычно `exited`), и без этого фильтра он попадал бы в сводку на каждом тике до конца задачи.
3. Определяет застрявших среди живых: воркер в `idle`/`blocked`/`waiting_input` дольше 15m, или `exited` без merged PR (агент умер, сессия ещё жива), или `ci_state=failing` без движения.
4. Если есть застрявшие, а сам оркестратор не `active` — кладёт ему в очередь сводку:
   ```
   [rocket heartbeat] Feature billing-v2 status:
   - billing-v2-backend: blocked 22m, PR #14 CI failing
   - billing-v2-ui: idle 40m, no PR
   Act autonomously: unblock, restart or replace stalled workers.
   ```
5. Анти-спам: не чаще одного heartbeat на оркестратора за интервал; событие `orchestrator.heartbeat_sent`.

Оркестраторы в `blocked`/`exited` heartbeat не будит — это сигнал человеку (`rocket ls` подсветит; дашборд/нотификации позже).

### Застревание на интерактивном вводе

Сам оркестратор может встать не на воркерах, а на вводе — открыт квиз `AskUserQuestion` (`pending_quiz` непустой) или `activity = waiting_input`. Heartbeat на это **не реагирует**: раньше он слал nudge оркестратору и эскалацию агенту `cto`, но эпизод зависания опознавался по `activity_ts`, а её обновляет каждая нотификация Claude Code — поэтому любая пауза считалась новым эпизодом, и оркестраторы получали поток ложных срабатываний. Механика удалена целиком — вместе с событием шины, порогом в конфиге (`input_stall_threshold` в существующих `config.yaml` просто игнорируется) и записью `problem` в журнал задачи; о состоянии воркеров и просроченных тредах оркестратор и так узнаёт из обычной сводки.

Осталось только наблюдение — производный флаг `waiting_terminal` (`internal/api/waiting.go`, фиксированный порог 10m; отсчёт от `asked_at` квиза, если квиз есть, иначе от `activity_ts`; без пригодной метки времени стойло не объявляется). Он ничего никому не шлёт, а только рисуется: в `rocket ls` состояние подписано глифом `⏳` в колонке ACTIVITY, в `rocket task ls` корневая задача (та, что ведёт оркестратор) подписана «⏳ ждёт ввода в терминале — вероятно, застрял», подзадача воркера — нейтральным «⏳ ждёт ответа в терминале», в дашборде — бейджем на карточке (см. [03-daemon-api.md](03-daemon-api.md), [11-dashboard.md](11-dashboard.md)).

### Устаревание вопросных тредов

Тот же цикл раз в тик проходит по всем открытым тредам задач и ролей (`store.ListOpenThreads`) — устаревание принадлежит треду, а не оркестратору:

1. Тред считается устаревшим, если он `open`, типа `decision`, его attention-множество непусто, и от последней записи (последнего сообщения, а если сообщений нет — от самого вопроса) прошло больше `question_stale_after` (yaml, по умолчанию 24h). Точка отсчёта — именно запись треда, а не `question_attention.added_at`: передача хода через `--to` не считается движением разговора.
2. Каждому участнику из attention уходит одно напоминание с локальным id треда, цитатой вопроса, временем ожидания и готовыми командами (`rocket task reply|close`, для тредов ролей — `rocket agent …`). Адресация — как у любого сообщения участнику: живой сессии в очередь, спящему постоянному агенту в `agent_inbox`.
3. **Человеку сообщение не отправляется** — доставлять некуда. Его канал — производное поле `stale` у треда в ответах API (см. [03-daemon-api.md](03-daemon-api.md)) и событие `question.stale`, из которых дашборд рисует бейдж; в `rocket questions` то же видно как возраст треда в заголовке строки.
4. Анти-спам — не чаще одного напоминания на пару «тред + получатель» за фиксированные 24 часа. Порог намеренно не равен `question_stale_after`: уменьшение порога должно делать треды устаревшими раньше, а не напоминать чаще. Состояние хранится в памяти демона, поэтому после рестарта одно напоминание может повториться.
5. Событие `question.stale` публикуется на каждый устаревший тред, независимо от того, кому что доставлено.

### Молчащие майлстоны

Тот же цикл раз в тик проходит по всем майлстонам в работе (`brainstorm` или `in_progress`) — майлстон не принадлежит ни проекту, ни оркестратору, поэтому он, как и устаревание тредов, живёт вне пер-оркестраторного прохода:

1. Майлстон молчит, если он взят агентом, находится в работе (`brainstorm` или `in_progress`), и от последнего **видимого следа держателя** прошло больше `milestone_quiet_after` (yaml, по умолчанию 24h). След — не-`status`-запись журнала, положенный документ, открытый в майлстоне вопрос или сообщение в его треде; всё строго за авторством текущего держателя, поэтому чужие записи его часы не сбрасывают. Следов нет вовсе — отсчёт от `updated_at` задачи, который ставят take/assign: часы идут с момента, когда майлстон стал чьим-то.
2. Держателю уходит одно напоминание `[rocket quiet milestone] #N "…" has had no visible activity from you for …` с тремя готовыми командами — `rocket task log`, `rocket task doc put`, `rocket task ask`. Доставка обычная: живой сессии в очередь, спящему агенту в `agent_inbox`.
3. **Человеку сообщение не отправляется.** Его канал — производное поле `quiet` у задачи в ответах API (см. [03-daemon-api.md](03-daemon-api.md)) и событие `milestone.quiet`, из которых дашборд и mobile рисуют бейдж.
4. Анти-спам — не чаще одного напоминания на майлстон за фиксированные 24 часа; порог намеренно не равен `milestone_quiet_after` (уменьшение порога должно делать майлстоны «молчащими» раньше, а не напоминать чаще). Состояние — в памяти демона, после рестарта одно напоминание может повториться.
5. Событие `milestone.quiet` публикуется на каждый молчащий майлстон независимо от того, доставлено ли напоминание (`reminded` в `data`).

Модель майлстонов целиком — [12-tasks.md](12-tasks.md), раздел «Майлстоны».

## Завершение фичи

- Штатно: пользователь видит доклад оркестратора → `rocket kill <orch> --cascade --cleanup` (или оркестратор убивает своих воркеров сам по мере merge, а пользователь убивает только его).
- Воркеры чистятся автоматически при merge их PR ([09-github.md](09-github.md)).
- Оркестратор автоматически не чистится никогда (урок из AO — авто-cleanup оркестраторов по merge PR приводил к убийству живой координации).
