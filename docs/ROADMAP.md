# Роадмап

Каждая фаза заканчивается работающим инструментом, которым можно пользоваться. Внутри фазы работа идёт по циклу spec → plan → implement → verify.

## Фаза 1 — скелет: демон, tmux, worktree

**Цель:** `rocket` умеет поднять агента в изолированном worktree и управлять сессиями руками.

- Go-модуль, каркас CLI (cobra) и демона; автозапуск демона, PID/сокет, `daemon start|stop|status|run`.
- SQLite-store + миграции; журнал событий (запись + `rocket events`).
- Реестр проектов: `project add|ls|rm|link`, config.yaml.
- Runtime tmux: create/inject/capture/alive/destroy, exact-match, keep-alive shell, launch-скрипты.
- Workspace worktree: create/restore/destroy, symlinks, post_create, коллизии веток.
- Адаптер claude-code (launch + env; активность — в фазе 2).
- Команды: `spawn` (пока без проверки «только оркестратор»), `ls`, `attach`, `kill`, `restore`, `doctor`, `logs`.
- Реконсиляция при старте демона (store vs tmux/файлы).

**Готово, когда:** `rocket project add … && rocket spawn … && rocket attach …` даёт живого Claude Code в worktree; `kill --cleanup` корректно всё сносит; демон переживает рестарт.

## Фаза 2 — активность и сообщения

**Цель:** надёжный `rocket send` и честные статусы в `rocket ls`.

- Монитор активности: каскад поллинга (процесс/TTY, JSONL Claude Code), пороги, события `activity_changed`.
- Push-канал: hook-скрипты в worktree → `POST /v1/internal/activity`.
- Очередь сообщений: таблица, пер-получатель FIFO-доставщик, инжекция с подтверждением, ретраи, `failed`, история.
- `rocket send` (+ `--file`, `--wait`), `GET /v1/messages`.
- SSE `/v1/events/stream`.

**Готово, когда:** два вручную заспавненных агента устойчиво переписываются через `rocket send`, включая случай «получатель занят 10 минут»; статусы в `ls` соответствуют реальности.

## Фаза 3 — оркестраторы

**Цель:** основной сценарий продукта — `rocket up` ведёт фичу через несколько проектов.

- `rocket up`: slug, worktree в хабе, системный промпт + kickoff (шаблоны, переопределение файлом).
- `rocket spawn` — только для оркестраторов, проверка `links`, `parent_id`, наследование `feature_slug`, системный промпт воркера.
- `rocket status <slug>`; `kill --cascade`.
- Heartbeat: детект застрявших воркеров, сводки оркестратору, анти-спам.

**Готово, когда:** реальная фича с 2+ воркерами в 2 проектах доведена до PR только через оркестратора; зависший воркер разбужен оркестратором после heartbeat.

## Фаза 4 — GitHub

**Цель:** демон видит PR/CI и закрывает петлю доставки.

- Поллер: поиск PR по ветке, `pr_state`/`ci_state`, события.
- Реакции: CI failing → сообщение воркеру; changes requested → сообщение воркеру.
- Авто-cleanup воркера после merge (grace, ветка остаётся, off-switch per-project).
- PR/CI-колонки в `ls`/`status`.

**Готово, когда:** merge PR воркера сам приводит к его зачистке; красный CI сам возвращает воркера в работу.

## Фаза 5 — мульти-агент

**Цель:** оркестратор и воркеры могут быть разными агентами.

- Финализация интерфейса `Agent`, адаптер codex (launch, активность), `--agent` per-spawn, `defaults.agent`.
- `doctor` проверяет все настроенные агенты.

**Готово, когда:** воркер на codex проходит полный цикл (спавн → PR → merge → cleanup) под оркестратором на claude-code.

## Фаза 6 — дашборд

**Цель:** наблюдение и управление из браузера.

- Отдельный дизайн-док (оркестратор-центричный UI) — пишется в начале фазы.
- `web/` (TS + React), статика раздаётся демоном; данные — REST + SSE.

## За горизонтом (не обещания)

Нотификации (macOS/Telegram), терминал в браузере, MCP-транспорт сообщений вместо инжекции, шаблоны фич, метрики/стоимость агентов.
