# Детекция активности агентов

## Состояния

| Состояние | Смысл |
|---|---|
| `active` | Агент прямо сейчас работает (думает, вызывает инструменты) |
| `ready` | Только что закончил ход, готов к вводу (свежее N минут) |
| `idle` | Давно ничего не делает |
| `waiting_input` | Ждёт ответа человека (permission prompt, вопрос) |
| `blocked` | Ошибка API/цикл прерван — сам не продолжит |
| `exited` | Процесс агента завершился |

Используется: очередью сообщений (когда доставлять), heartbeat'ом (кто застрял), `rocket ls`/дашбордом (наблюдаемость).

`waiting_input` — вместе с непустым `pending_quiz` — это ещё и признак застревания на интерактивном вводе: сессия считается застрявшей, пока открыт квиз `AskUserQuestion` либо `activity = waiting_input`, и если это длится дольше 10 минут, она помечается производным флагом `waiting_terminal` (`internal/api/waiting.go`) — он только рисуется в CLI и дашборде, никаких сообщений и эскалаций по нему не отправляется (см. [08-orchestrators.md](08-orchestrators.md)).

## Два канала, поллинг + push

1. **Поллинг (авторитетный).** Монитор демона каждые ~5s вызывает `agent.Activity(session)` адаптера. База каскада для всех агентов:
   - жив ли процесс агента в pane: TTY pane (`tmux list-panes -F '#{pane_tty}'`) → поиск процесса агента на этом TTY (`ps`); нет процесса → `exited`;
   - далее — агент-специфичные источники (см. [10-agents.md](10-agents.md)); для Claude Code — mtime и тип последней записи нативного JSONL-транскрипта (`~/.claude/projects/<slug>/<uuid>.jsonl`): свежая работа → `active`, стоп → `ready`/`idle` по порогу, api_error → `blocked`.
2. **Push (уточняющий).** При спавне демон настраивает hooks агента в worktree (для Claude Code — `.claude/settings.json`): hook-скрипт на события (`PreToolUse`, `Stop`, `Notification(permission)` и т.д.) дёргает `POST /v1/internal/activity` через сокет. Даёт мгновенные переходы и главное — надёжный `waiting_input`, который по транскрипту не отличим от `ready`.

Поллинг сглаживает потери push-событий; push ускоряет реакцию. Конфликт разрешается по timestamp (свежее побеждает), `exited` из поллинга всегда приоритетен.

## Пороги (конфигурируемые)

- `active`: последняя работа < 30s назад;
- `ready` → `idle`: 5 минут без активности;
- изменение состояния публикует событие `session.activity_changed`.

## Никакого regex по содержимому терминала

Правило из опыта AO: парсинг вывода TUI для определения состояния хрупок и ломается при каждом обновлении агента. Терминальный capture используется только для подтверждения доставки сообщений (черновик ушёл из composer), не для классификации состояния.
