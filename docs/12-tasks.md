# Задачи (канбан)

Задача — первоклассная сущность в базе демона. Всё начинается с задачи: пользователь описывает, что нужно сделать, видит её на канбане, назначает на неё фича-оркестратора. Декомпозиция, документы, решения и проблемы стекаются в задачу — это durable-запись фичи, которая живёт дольше сессий и worktree.

## Модель

Два уровня:

- **Задача** (фича) — создаёт пользователь. На неё назначается оркестратор.
- **Подзадача** — создаётся **автоматически демоном** при `rocket spawn`: одна подзадача = один воркер. Оркестратор может создавать подзадачи и заранее (при декомпозиции), а потом привязывать к ним воркеров при спавне (`rocket spawn --subtask <id>`).

Так пользователь видит всю декомпозицию: как оркестратор разбил фичу, кто над чем работает, что уже сделано.

### Поля

- `id` — короткий числовой (#12), используется в CLI и UI.
- `parent_id` — NULL у задачи, id задачи у подзадачи.
- `title`, `description` (markdown).
- `project_id` — проект, которому принадлежит задача (канбан сгруппирован по проектам); у подзадачи дополнительно `repo_id` — репозиторий её воркера.
- `status` — `backlog | brainstorm | in_progress | review | done | cancelled`.
- `feature_slug` — присваивается при назначении оркестратора; общий для задачи и её подзадач.
- `session_id` — привязанная сессия: у задачи — оркестратор, у подзадачи — воркер. Через неё из карточки задачи всегда доступны `tmux_name` и команда attach (см. «Интеграция с терминалом»).
- `milestone` — задача вне проектов, которую берёт постоянный агент (см. «Майлстоны»); у обычной задачи `0`.
- `assigned_role` — id постоянного агента, держащего майлстон; пусто — не взят. Непустым может быть ровно одно из `session_id` (оркестратор фичи) и `assigned_role` (агент майлстона): пути взаимоисключающие.
- `created_by` — `user | orchestrator | agent`.
- `created_at`, `updated_at`, `completed_at`.

## Статусная механика

Статусы двигаются и автоматически (из жизненного цикла сессий/PR), и явно (командой). Явное всегда побеждает автоматическое.

У задачи две фазы работы, и канбану важно их различать. `brainstorm` — задача обсуждается с оркестратором, кода никто не пишет; `in_progress` — воркеры пишут код. Оба перехода делает демон сам: `start` доводит задачу до `brainstorm`, первый `spawn` — до `in_progress`. Второй и последующие спавны статус не трогают, и задачу, уведённую человеком куда-то ещё, спавн назад не тянет. Ограничений на ручные переходы нет: `rocket task move <id> brainstorm` работает как любой другой статус.

**Задача (фича):**

| Переход | Триггер |
|---|---|
| `backlog → brainstorm` | назначен оркестратор (`rocket task start`) |
| `brainstorm → in_progress` | человек дал **Go** по гейту шторма (`rocket task gate go`, см. «Гейт выхода из шторма») или оркестратор заспавнил первого воркера (`rocket spawn`) |
| `in_progress → review` | оркестратор доложил о готовности: `rocket task move <id> review` (kickoff требует сделать это, когда все PR смержены) |
| `review → done` | пользователь принял работу (CLI или канбан) |
| `→ cancelled` | пользователь; убивает оркестратора каскадно |

**Подзадача (воркер):**

| Переход | Триггер |
|---|---|
| создана `in_progress` | `rocket spawn` (или `backlog`, если создана оркестратором заранее без воркера) |
| `in_progress → review` | автоматически: у воркера открылся PR |
| `review → done` | автоматически: PR смержен (вместе с авто-cleanup воркера) |
| любые ручные переходы | `rocket task move` — оркестратором или пользователем |

## Документы и журнал задачи

Оркестратор обязан (это часть kickoff-промпта) складывать в задачу все значимые артефакты. Хранение — в базе демона, привязано к задаче, переживает смерть сессий.

**Документы** (`task_docs`) — версионируемые markdown-документы:

- `kind`: `problem` (что болит, для кого, что будет успехом — первый шаг шторма), `spec` (спека фичи), `plan` (план/декомпозиция), `report` (итоговый отчёт), `doc` (прочее).
- Обновление того же документа создаёт новую версию (старые сохраняются).
- Каждая запись публикует событие `task.doc_put` `{task_id, kind, version}`; новая версия `spec` вдобавок снимает ожидающий гейт (см. ниже).

**Журнал** (`task_log`) — append-only записи-события хода работы:

- `kind`: `decision` (принятое решение + почему), `problem` (возникшая проблема), `note` (заметка), `status` (автозаписи о переходах статусов, спавнах, PR).
- Автор — сессия (оркестратор или воркер) либо пользователь.

Воркеры тоже пишут в журнал своей подзадачи (их системный промпт требует фиксировать решения и проблемы).

### Гейт выхода из шторма

Выход из `brainstorm` — не вопрос в треде, а отдельный механизм (`task_gates`), привязанный к **версии спеки** (задача #4901).

- **Запрос.** Оркестратор, положив спеку (и план), делает `rocket task gate request <id>`. Гейт фиксирует последние версии `spec` и `plan` задачи (последняя — самая свежая запись этого вида; плана может не быть → `plan_version: null`). Без спеки — `400 no_spec`. Запросить может любой, кто пишет в задачу (оркестратор, постоянный агент, человек). Если уже есть ожидающий гейт, он становится `superseded`.
- **Новая спека снимает гейт.** Запись новой версии `spec` переводит ожидающий гейт в `superseded`: человек не может одобрить спеку, которая поменялась у него под руками, — нужен новый запрос. Новая версия плана гейт не трогает.
- **Решение — только человек** (запрос без агентской идентичности: дашборд, мобильный, свой терминал). Оркестраторы, воркеры и постоянные агенты получают `403`. Решить можно только `pending`-гейт — иначе `409 gate_not_pending`. Если спека задачи успела обновиться после запроса, решение отклоняется (`409 gate_superseded`) даже без снятия при записи — версия сверяется в той же транзакции. На задаче не больше одного `pending`-гейта (уникальный индекс).
  - **Go** — если задача в `brainstorm`, она переходит в `in_progress` тем же путём, что `rocket task move` (запись `status` в журнале, событие `task.status_changed`). Если задача уже не в `brainstorm` (например, воркер был заспавнен раньше), гейт всё равно фиксируется как `go`, статус не трогается, в журнал ложится `note`. Оркестратору уходит `[rocket gate] Go по спеке vN (план vM) — начинай реализацию.` (без плана — «план —»).
  - **Нужны правки** — комментарий обязателен (`400 comment_required`); оркестратору уходит `[rocket gate] Нужны правки по спеке vN: <комментарий>`. Статус задачи не меняется.
  - Нет живого оркестратора — решение всё равно записывается, сообщение пропускается.
- Статусы гейта: `pending` → `go` | `changes` | `superseded`. События: `task.gate_requested`, `task.gate_decided`, `task.gate_superseded` `{task_id, gate_id, status}`.

## Вопросы и ответы через задачу

Во время брейншторма пользователь и оркестратор общаются напрямую (терминал/чат карточки). Но когда работа уже идёт, вопрос, заданный просто в терминал, легко пропустить. Для этого — явный механизм Q&A:

**Вопрос — это тред, а не одна пара «вопрос-ответ».** Частый случай: вопрос оркестратора непонятен — нужно попросить переформулировать, раскрыть контекст, уточнить детали, и только потом отвечать по существу. Поэтому вопрос живёт как мини-диалог до явного разрешения.

**И у треда не две стороны, а список участников.** Изначально тред был жёстким диалогом «человек ↔ оркестратор»: постоянный агент вроде `cto` не мог ни ответить оркестратору, ни закрыть тред, и обходил это, выдавая себя за человека. Теперь права привязаны к участию, а не к роли, и в одном треде могут разговаривать человек, оркестратор задачи и один или несколько постоянных агентов.

### Участники

Идентификатор участника — одно из трёх:

| Значение | Кто |
|---|---|
| `human` | человек |
| id постоянного агента (`cto`) | агент `kind=agent` |
| session id (`reply-answer-orch`) | оркестратор или воркер |

Участником становятся двумя способами: **вас назвали в `--to`** любой записи треда, либо **вы сами написали** в тред. Сверх этого при создании треда сразу сеются обе его стороны: человек — всегда, и вторая сторона предмета треда (оркестратор задачи, `task.SessionID`), если она есть. Без этого тред, открытый человеком на задаче без оркестратора, было бы некому доставить; если оркестратора у задачи нет, никто и не сеется — участник «из воздуха» не выдумывается.

Список участников треда отдаётся в поле `participants` и виден в CLI и дашборде.

### Идентификатор треда: локальная ссылка

У треда один пользовательский id — **локальная ссылка**: `1023/Q2` для треда задачи, `cto/Q1` для треда роли. Её печатают все команды, её же принимают `reply` и `close`, и ею подписана каждая доставленная запись: `[#1023/Q2 reply from cto]`. Глобальный числовой id (`372`) остаётся в базе и в API и по-прежнему принимается CLI, но нигде не печатается.

Это лечит главную причину мисдоставок: раньше в доставленной записи агент видел «task #1023 Q2», а отвечать должен был глобальным номером, который надо было отдельно выяснять — и под нагрузкой ответ уходил в чужой тред.

### Attention set — «чей ход» как хранимое состояние

Кого тред ждёт, **хранится** (таблица `question_attention`), а не вычисляется из последней записи. Раньше `--to` был свойством одной записи, которое затирала следующая: любая реплика без `--to` возвращала ход всем сразу, включая тех, кого уже вывели из очереди. Этого правила больше нет.

Два разных механизма по-прежнему не надо путать:

- **Доставка (уведомления).** Каждая новая запись треда — открытие, реплика, закрытие — доставляется **всем участникам, кроме автора**. Всегда. `--to` доставку **не сужает**.
- **Attention (`waiting_on`).** Кого ждут. Вот его `--to` и меняет.

Автоправила (по образцу attention set в Gerrit, реализация — `internal/store/attention.go`):

1. **Открытие треда** — attention = адресаты `--to`, если они заданы; иначе все участники, кроме автора вопроса.
2. **Любая запись в открытом треде** (реплика, а также реплика с `--dispute` в закрытый тред, которая его переоткрывает) — автор **выходит** из attention, названные в `--to` **входят** (и становятся участниками). Если после этого множество опустело — ход переходит ко всем участникам, кроме автора записи.
3. **Закрытие** — attention очищается. `fyi`-тред рождается сразу закрытым и не ждёт никого.
4. **Реплика в закрытый тред** — с `--dispute` тред переоткрывается и работает правило 2; без флага запись просто ложится в историю, attention **не трогается**: тред как не ждал никого, так и не ждёт.

Практическое следствие правила 2: если тред ждал двоих и ответил один, второй **остаётся** в очереди. И наоборот — `rocket task reply 1023/Q2 --to cto "разберись"` передаёт ход именно `cto`, а не «всем, кроме меня».

Attention отдаётся в поле `attention`; `waiting_on` — то же множество под прежним именем (совместимость). Рядом API отдаёт `your_turn` — входит ли в attention тот, кто спрашивает; именно он зажигает бейдж «ждут вас». Совместимое поле `whose_turn` (`user` | `orchestrator`) сохранено для старых клиентов и выводится из attention: `user`, если в нём есть человек, иначе `orchestrator` при непустом множестве.

**Видеть тред и быть в его attention — намеренно разные вещи.** Человек видит **все** треды всегда, в том числе адресованные не ему: `--to cto` не прячет тред от человека, а лишь снимает с него бейдж. `your_turn` только помечает треды и включает необязательный фильтр, но ничего не скрывает.

### Тип треда: decision, fyi и brainstorm

У треда есть тип (`questions.type`):

- `decision` (по умолчанию) — ждёт решения: открыт, имеет непустой attention, считается в бейджах и счётчиках, устаревает (см. ниже);
- `fyi` (`--fyi` при создании) — статусная заметка в историю: доставляется всем участникам, **создаётся сразу `resolved`** с резолюцией `fyi`, никого не ждёт и бейджей не зажигает. Реплика человека в fyi-тред переоткрывает его как обычный `decision` — значит, кому-то оказалось не всё равно (флаг `--dispute` для этого не нужен).

- `brainstorm` (`--brainstorm` при создании, только на тредах задачи) — вопрос шторма оркестратора. Ведёт себя как `decision` (участники, attention, бейджи, устаревание, переоткрытие), но вдобавок записывает рекомендацию агента и то, как к ней отнёсся человек. Подробнее — ниже, «Вопрос шторма».

Статусное сообщение больше не обязано становиться вопросом, который кто-то должен закрывать: это и была одна из причин, по которым открытые треды копились.

### Вопрос шторма (brainstorm)

Каждая развилка шторма, которую решает человек, — тред типа `brainstorm` (задача #4901). Из его ответов складывается метрика качества рекомендаций агента.

- **Создание:** `rocket task ask <id> --brainstorm --option A --option B --recommend 2 ...`. Вопрос шторма — всегда развилка с рекомендацией: нужны хотя бы два варианта и `--recommend` (номер рекомендованного, 1-based). Меньше двух вариантов, нет `--recommend` или он вне диапазона — отказ (CLI до вызова daemon, API — `400 bad_request`): открытый вопрос без вариантов всегда давал бы `wrong_turn` и искажал метрику. `--recommend` у не-brainstorm треда — тоже `400`. На тредах ролей тип `brainstorm` не принимается (`400`).
- **Ответ из вкладки / CLI** (`rocket task close <тред> --choose N ["<комментарий>"]` или свой текст): сохраняются номер варианта (`chosen_option`), текст человека (`answer_comment`) и `answer_source=ui`. Тело ответа в треде — текст варианта и, через пустую строку, комментарий.
- **Ответ из терминала оркестратора:** человек ответил в терминале — оркестратор сразу записывает его дословно: `rocket task brainstorm record <тред> [--choose N] "<текст человека>"`. Это единственное исключение из правила «агент не закрывает треды»: агент записывает ответ человека, а не свой. Поэтому оно узкое: только оркестратор задачи этого треда (воркер, чужой оркестратор, постоянный агент и сам человек — `403`), только `brainstorm` (`400 not_brainstorm`), только открытый тред (`409`). Запись в треде — от `human`, у треда `answer_source=terminal`; ответ рассылается участникам как обычный, кроме записавшего его оркестратора.
- **Исход** (`outcome`) вычисляется при ответе:

  | Что сделал человек | Исход |
  |---|---|
  | выбрал рекомендованный вариант (с комментарием или без) | `accepted` |
  | выбрал другой вариант | `corrected` |
  | не выбрал вариант, написал своё | `wrong_turn` |

  «Принято с комментарием» — `accepted` с непустым `answer_comment`.
- **Переопределение исхода:** человек может поправить вычисленный исход (`PATCH /v1/questions/{id}/outcome`) — тогда `outcome_overridden=true`. Только человек: агенты, включая постоянных, получают `403` — агент не оценивает собственные рекомендации. Только у отвеченного brainstorm-треда (у открытого или закрытого как неактуальный — `409`).
- **Переоткрытие** brainstorm-треда (`reply --dispute`) оставляет тип `brainstorm` и рекомендацию, но сбрасывает ответ и исход; следующий ответ вычисляет их заново.
- **Кто ответил:** у любого треда API отдаёт `answered_by` — автора ответа, которым тред закрыт (`human`, id постоянного агента; пусто, пока ответа нет). Ответы постоянных агентов на brainstorm-треды записываются так же (`answer_source=ui`), и метрика считает их — каждый своему автору (задача #5019); ответ, записанный оркестратором из терминала, — ответ человека.
- **Метрика:** `rocket stats brainstorm` / `GET /v1/stats/brainstorm` — доля `accepted` среди ответов по ISO-неделям (по времени ответа, локальное время daemon) отдельно для каждого скилла шторма задачи (`brainstorm_skill`, пусто → `unknown`) и каждого отвечавшего (`human` или id агента — человек и агенты не складываются в одну цифру), и штормы: кто штормил (участники в порядке первого ответа, со счётчиками по каждому), вопросов, принято / с комментарием / поправлено / не туда, правок до Go (гейты `changes`, решённые до первого Go; `superseded` не правка), Go с 1-го раза, дата Go. Счётчики одной задачи — `GET /v1/tasks/{id}/brainstorm/stats`. Исход берётся хранимый, с учётом переопределения; открытые, переоткрытые и закрытые как неактуальные треды в доли не входят. Определения — 03-daemon-api.md, «Метрика брейншторма».

### Варианты ответа (options)

`ask` принимает повторяемый флаг `--option "<текст>"` — до N вариантов, они хранятся в `questions.options`. Дашборд рисует их кнопками, CLI печатает нумерованным списком, а закрытие выбором — `rocket task close 1023/Q2 --choose 2` (нумерация 1-based, как в выводе). Текст рядом с `--choose` — комментарий к выбору: он идёт в ответ после текста варианта (`rocket task close 1023/Q2 --choose 2 "но без кэша"`). Смысл — снизить цену ответа для человека.

### Эхо цели, `--dry-run` и guard `--join`

Три страховки от записи не в тот тред:

- **Эхо цели.** `reply` и `close` печатают, куда ушла запись: `→ 1023/Q2 «первые ~60 символов вопроса» (task #1023 "заголовок")`. Промах виден сразу, а не через день.
- **`--dry-run`.** Печатает то же эхо и не отправляет ничего.
- **`--join`.** Запись в тред, участником которого вы не являетесь, отклоняется (`not_a_participant`) с эхом цели, составом треда и подсказкой повторить с `--join` — осознанное «да, я понимаю, куда пишу». Повторить с `--join` могут человек и постоянные агенты: их и втягивают в чужие треды по делу. Оркестратор и воркер чужой задачи остаются без доступа вовсе, а на своих тредах (оркестратор — своей задачи, воркер — своей корневой) пишут без `--join`, как и раньше.

### Как идёт диалог

1. **Оркестратор открывает вопрос:** `rocket task ask <task-id> "<вопрос>"` (можно с контекстом: `--context "<md>"`, с адресатами: `--to cto`, с вариантами: `--option "A" --option "B"`, длинный markdown — из файла: `--file q.md`). Вопрос получает номер (Q3) и статус `open`; оркестратор продолжает работать над тем, что не заблокировано вопросом (или ждёт, если заблокировано всё).
2. **Те, кто в attention, это видят:** человеку — бейдж «? ждёт ответа» на карточке канбана и в списке проектов, баннер с вопросом наверху карточки задачи, счётчик открытых вопросов в `rocket ls` / `rocket task show`, строка в `rocket questions --waiting-on human`. Агенту-участнику — доставка в сессию или в инбокс (см. ниже).
3. **Участник пишет в тред** — двумя способами:
   - **Уточнение или обсуждение** («не понял, переформулируй», «что значит X?») — `rocket task reply 1023/Q3 "<текст>"`. Тред остаётся `open`, автор выходит из attention, названные в `--to` входят.
   - **Закрытие** — `rocket task close 1023/Q3 "<резолюция>"` (или `--choose <n>` выбором варианта, или `--dismiss ["<почему>"]` как неактуальный; в дашборде — кнопка варианта или «Ответить и закрыть»). Тред становится `resolved`, attention очищается. Это доступно **человеку и постоянным агентам**; оркестратор и воркер получают `403` с подсказкой использовать `reply`.
4. **Оркестратор отвечает в тред** тем же `rocket task reply` — переформулировка/раскрытие. Получив реплику-уточнение, оркестратор обязан ответить в тред, а не открывать новый вопрос.
5. **Делегирование.** Человек может не отвечать сам, а передать ход тому, кто в теме: `rocket task reply 1023/Q3 --to cto "разберись и ответь"`. `cto` вступает в тред, оказывается в attention один (человек из него вышел как автор записи), и дальше вправе закрыть тред своим `close` — оркестратор получает решение без человека.
6. Тред может иметь сколько угодно раундов; каждая запись доставляется через очередь сообщений (гарантия, ретраи, видимый статус).

Статусы вопроса: `open` (+ `attention` / `your_turn`) → `resolved`. **Resolved — не навсегда:** если у участника есть доказательства, что финальный ответ противоречит фактам, его реплика в тот же тред с флагом оспаривания (`rocket task reply <ref> "<почему>" --dispute`) **переоткрывает** вопрос — статус снова `open`, пользователю поднимается бейдж, публикуется событие `task.question_reopened`. **Без `--dispute` реплика в закрытый тред ничего не переоткрывает:** она просто ложится в историю, статус остаётся `resolved`, attention не меняется, бейдж не зажигается — обычное «принял, работаю» больше не возвращает решённый вопрос человеку (CLI печатает подсказку про флаг). Переоткрывать может любой участник, кроме человека; для человека resolved-вопрос финален (реплика → `409 question_resolved`): передумал — просто жди реакции или напиши в чат. Оркестратору промпт предписывает не исполнять оспоренное решение до повторного ответа и спорить только фактами. Переоткрытие — узкий инструмент строго про сам ответ (выбранное не может работать / выбрано явно не то / ответ непонятен); всё, что обнаруживается дальше по ходу работы, — НОВЫЕ вопросы (со ссылкой на старый номер), иначе задача рискует навсегда остаться в одном треде.

### Уведомления

Каждая запись треда рассылается всем участникам, кроме автора, тем же путём, что обычное сообщение:

- **постоянный агент** — живой сессии тело доезжает в очередь; мёртвой пишется строка в инбокс, а при оживлении демон инжектит `[rocket] You have N unread messages` (см. [10-agents.md](10-agents.md));
- **оркестратор или воркер** — живой сессии тело в очередь; сессия в терминальном состоянии инбокса не имеет, поэтому запись просто не доставляется и логируется;
- **человек** — ему ничего не инжектится: он читает тред в CLI, дашборде и мобильном приложении.

Формат доставляемой записи: `[#12/Q3 reply from cto] <текст>` — локальная ссылка на тред, вид записи (`question` | `reply` | `answer`) и автор. У тредов ролей ссылка без решётки: `[cto/Q2 answer from human] ...`. `from <id>` пишется единообразно, включая человека: при нескольких участниках автора иначе из рамки не вывести. **Ссылка в рамке — это ровно то, что нужно набрать в ответ** (`rocket task reply #12/Q3 "..."`; решётка необязательна, `12/Q3` работает так же); прежний формат `[task #12 Q3 ...]` называл тред одной строкой, а принимал другую — на этом и терялись ответы.

### Права

| Действие | Человек | Постоянный агент | Оркестратор задачи | Воркер |
|---|---|---|---|---|
| `ask` — открыть тред (в т.ч. `--fyi`, `--option`) | да | да | да, на своей задаче | нет |
| `reply` | да | да | если участник (плюс своя задача) | если участник (плюс своя корневая задача) |
| `close` (`--choose` / `--dismiss`) | да | да | нет — `403`, «use reply» | нет — `403` |
| `brainstorm record` (ответ человека из терминала) | нет — `403` | нет — `403` | да, только на своей задаче | нет — `403` |
| Переопределить исход brainstorm | да | нет — `403` | нет — `403` | нет — `403` |
| Запись в чужой тред | да, с `--join` | да, с `--join` | нет | нет |
| Реплика в resolved (история, без переоткрытия) | нет (`409`; кроме `fyi`) | да | да | да, если участник |
| Переоткрыть resolved репликой с `--dispute` | нет (`409`) | да | да | да, если участник |
| Чтение тредов | все | все | треды своей задачи и где участвует | треды своей корневой задачи и где участвует |

`reply` доступен любому участнику; оркестратор задачи допускается и до того, как впервые написал, — иначе тред, открытый человеком, был бы ему недоступен. «Своя задача» для воркера — **корневая** задача над его подзадачей: вопросы живут только на корневых задачах, поэтому сравнение с самой подзадачей закрыло бы воркеру контекст его же фичи.

Полные треды навсегда остаются в истории задачи (видны в Journal вперемешку с остальной хронологией — это тоже часть «как шла задача»). Воркеры по умолчанию участниками не становятся — их канал общения с оркестратором остаётся `rocket send`; но воркера можно втянуть в тред через `--to`, и читать треды своей корневой задачи он может всегда.

Открытый вопрос не двигает статус задачи, но подсвечивается как требующий внимания; heartbeat оркестратора продолжает работать (воркеры-то работают). Если вопрос висит в статусе «ждёт оркестратора» дольше порога — heartbeat напоминает оркестратору ответить. А если тред не двигается дольше `question_stale_after` (по умолчанию 24h), heartbeat напоминает **всем, чьего хода ждут**: агентам и сессиям — сообщением с готовыми командами, человеку — флагом `stale` у треда, из которого рисуется бейдж (подробности — [08-orchestrators.md](08-orchestrators.md), §«Устаревание вопросных тредов»).

### Обратное направление: пользователь спрашивает оркестратора

Тот же механизм работает и в обратную сторону — пользователь может сам открыть тред, адресованный оркестратору задачи (только на корневой задаче, воркеры по-прежнему недоступны напрямую):

- **Пользователь открывает вопрос:** `rocket task ask-orch <task-id> "<вопрос>"` (или тот же POST `/v1/tasks/{id}/questions`, но без `X-Rocket-Session`). Вопрос сохраняется с `asked_by = ""` (конвенция «пусто = человек»; наружу API отдаёт канонический `human`) и сразу же попадает в очередь сообщений оркестратора как `[#12/Q4 question from human] <текст>` — не нужно ждать, пока оркестратор сам заглянет в тред.
- **Attention свежего треда — оркестратор** (правило 1: все участники, кроме автора), поэтому `whose_turn` — `"orchestrator"`, а не пользователь, в отличие от треда, который открыл сам оркестратор.
- **Оркестратор отвечает в тред** тем же `rocket task reply 12/Q4 "<ответ>"`. Оркестратор НЕ закрывает такие треды (`rocket task close` ему недоступен и по смыслу не подходит) — закрывает их только пользователь, как обычно.
- Остальной механизм (реплики, статусы, доставка) идентичен направлению «оркестратор → пользователь».

## CLI

```
rocket task add "<title>" [--project <id>] [--desc <md>|--desc-file <f>]
rocket task ls [--status <s>] [--project <id>]     # канбан в терминале; «⏳ ждёт ввода в терминале — вероятно, застрял» у корневой задачи (оркестратор), «⏳ ждёт ответа в терминале» у подзадачи (воркер)
rocket task show <id>                              # карточка: статус, сессия, подзадачи, доки, журнал
rocket task start <id> [--agent <name>]            # создать оркестратора и назначить на задачу
rocket task move <id> <status>
rocket task doc put <id> --kind problem|spec|plan|report|doc --title "..." --file <f.md>
rocket task gate request <id>                      # оркестратор: запросить Go по последним spec/plan
rocket task gate ls <id>                           # история гейтов, новые первыми
rocket task gate go <gate-id>                      # человек: Go
rocket task gate changes <gate-id> "<комментарий>" | --file <f>   # человек: нужны правки
rocket task log <id> --kind decision|problem|note "<текст>" | --file <f>
rocket task ask <id> "<вопрос>" | --file <f> [--context <md>] [--to a,b]
                [--option "<текст>"]... [--fyi]    # открыть тред
rocket task ask <id> ... --brainstorm --option "<текст>" --option "<текст>"... --recommend <n>
                                                   # вопрос шторма с рекомендацией
rocket task ask-orch <id> "<вопрос>" | --file <f> [--context <md>] [--to a,b]
                [--option "<текст>"]... [--fyi]    # пользователь: вопрос оркестратору (доставляется сразу)
rocket task questions [<id>] [--open]              # треды задачи, участники, варианты, attention
rocket task reply <тред> "<текст>" | --file <f> [--to a,b] [--dry-run] [--join]
rocket task close <тред> "<резолюция>" | --file <f> [--to a,b] [--dry-run] [--join]
rocket task close <тред> --choose <n> ["<комментарий>"]
                                                   # закрыть выбором варианта (1-based)
rocket task close <тред> --dismiss ["<почему>"]    # закрыть как неактуальный
rocket task brainstorm record <тред> [--choose <n>] ["<текст человека>" | --file <f>]
                                                   # оркестратор: записать ответ человека из терминала
rocket task cancel <id>

rocket task add "<title>" --milestone              # майлстон: задача вне проектов
rocket task ls --milestones                        # канбан майлстонов
rocket task take <id>                              # агент берёт майлстон (из своей сессии)
rocket task assign <id> <agent-id> | --none        # человек назначает/снимает

rocket questions [--waiting-on <id>] [--all]       # все открытые треды задач и ролей одним списком
```

`<тред>` в `reply`/`close` — это **локальная ссылка**: номер треда внутри задачи, тот самый `Q1` из вывода `rocket task questions` и из рамки доставленной записи. Писать её можно двумя способами: `rocket task reply 799/Q1 "…"` или `rocket task reply --task 799 Q1 "…"` (регистр `Q` не важен). Глобальный id вопроса (`372`) продолжает приниматься, но больше нигде не печатается. Голый `Q1` без задачи — ошибка с подсказкой обеих форм; несуществующий номер — «у задачи #799 нет вопроса Q7».

Для тредов агента (`rocket agent reply|close`) действует то же самое, но скоуп — агент: `sre/Q1`, а изнутри сессии агента достаточно `Q1` (агент берётся из сессии, как в `rocket agent questions`).

`rocket task answer` — прежнее имя `close`: работает без изменений (включая `--dismiss`), но скрыто из help.

`--to` принимает идентификаторы участников (`human`, id постоянного агента, session id) — через запятую, флаг можно и повторять. Названные вступают в тред, получают уведомление и **входят в attention** — одинаково при `ask`, `reply` и `close`. Без `--to` работает правило 2: автор записи выходит из attention, а если оно опустело — ход переходит остальным участникам.

Везде, где команда принимает текст позиционным аргументом, есть `--file <path>` (и `-` = stdin): markdown с бэктиками иначе исполняется шеллом и доезжает с дырами.

`rocket up "<описание>"` остаётся как шорткат: создаёт задачу и сразу делает `task start`.

Для агентов те же команды (`task doc put`, `task log`, `task move`, `task add --parent`); демон проверяет права: постоянный агент (`sessions.kind='agent'`) — как человек, оркестратор — только своя задача и её подзадачи, воркер — только своя подзадача.

Кто что может с задачами:

| Кто | Создать задачу | Запустить (`task start` / `up`) | Править |
|---|---|---|---|
| Человек (без `X-Rocket-Session`) | да, любую | да | любую |
| Постоянный агент (`kind='agent'`) | да, любую; `created_by='agent'` | да | любую |
| Оркестратор | только подзадачи своей задачи | нет — `403 only the human user or a registered agent may start a task` | своя задача и её подзадачи |
| Воркер | нет — `403 workers may not create tasks` | нет — тот же `403` | только своя подзадача |

## Майлстоны

Обычная задача — это фича: человек её создаёт, назначает оркестратора, тот спавнит воркеров. Но у постоянного агента (`cto`, `sre`, см. [10-agents.md](10-agents.md)) работа устроена иначе: он не фича-проект, у него нет ни проекта, ни воркеров, а результат всё равно должен быть виден человеку так же, как результат фичи. **Майлстон** — это и есть такая единица: корневая задача **вне всех проектов**, которую агент берёт на себя.

Вся механика задачи у майлстона своя, не отдельная: те же документы, тот же журнал, те же вопросные треды, тот же канбан. Отличий ровно три — у него нет проекта, его берут, а не запускают, и принимает его человек.

### Модель

- `milestone = 1` — явный признак, а не «project_id пуст»: `project_id` объявлен `NOT NULL` ещё в первой миграции, у майлстона он `''` (та же конвенция, что у `agents.project_id`), и `''` от `NULL` не отличить. Колонки добавлены миграцией 0012 ([05-state.md](05-state.md)).
- `assigned_role` — id постоянного агента, держащего майлстон; пусто — не взят.
- Проекта и родителя у майлстона нет: `--milestone` взаимоисключающ с `--project` (`400 milestone_with_project`) и с `--parent` (`400 milestone_with_parent`). Подзадач майлстон не порождает — воркеров он не спавнит.

Создаёт майлстон человек или постоянный агент: `rocket task add "<title>" --milestone` (API — `POST /v1/tasks {milestone: true}`).

### Take и assign: два входа, взаимоисключающие

| Кто | Команда | Что делает |
|---|---|---|
| Постоянный агент | `rocket task take <id>` | берёт **не взятый** майлстон из своей сессии |
| Человек | `rocket task assign <id> <agent-id>` | вручает майлстон агенту (агент получает уведомление в сессию или в инбокс) |
| Человек | `rocket task assign <id> --none` | снимает майлстон с агента |

Права разведены намеренно: агент берёт работу **сам и на виду**, человек — раздаёт и забирает. Поэтому `take` доступен только сессии `kind='agent'` (иначе `403 agent_only`), а `assign` — только человеку (вызов от любой сессии → `403 human_only`). Агенты не переназначают работу друг друга.

Краевые случаи: взять уже взятый другим → `409 already_taken` с именем держателя; взять свой же — no-op `200`; `take`/`assign` на обычной проектной задаче → `403 not_a_milestone`; несуществующий агент в `assign` → `400 agent_not_found`.

Каждое взятие, назначение и снятие оставляет запись в журнале задачи (`kind=status`: «milestone taken by cto» / «milestone assigned to cto (by human)» / «milestone unassigned (by human)») и публикует событие `task.assigned` `{task_id, agent_id, by, verb}`. Кто держит майлстон, видно из карточки, а не из переписки.

### Кто в него пишет

В майлстон пишут (журнал, документы, смена статуса) **человек и только его держатель**. Постоянный агент, который майлстон не брал, прав на запись не имеет — в отличие от обычной задачи, где любой постоянный агент приравнен к человеку. Взять свободный майлстон при этом может любой агент: `take` идёт своим путём и через эту проверку не проходит.

### Статусная механика

| Переход | Триггер |
|---|---|
| `backlog → brainstorm → in_progress` | `rocket task move` держателем или человеком (взятие статус само не двигает; автоматики в майлстонах нет — оба перехода руками, и `brainstorm` можно пропустить) |
| `in_progress → review` | держатель доложил о готовности; проходит, только если в майлстоне есть что смотреть |
| `review → done` | **только человек** — это приёмка |
| `→ cancelled` | **только человек** |

- `rocket task start` на майлстоне отвечает `403 milestone_not_startable`: майлстон берут, а не запускают фичей.
- `rocket task cancel` от сессии — `403 human_only`.
- **Мини-гейт review.** Перевод в `review` отклоняется с `422 milestone_empty`, пока в майлстоне нет **ни одного документа** (чьего угодно — док и есть предмет разговора) и **ни одной не-`status`-записи журнала от держателя**. Автозаписи take/assign/move — это бухгалтерия, а не работа: смотреть по ним нечего. Отказ прямо называет, чем его закрыть: `rocket task doc put` или `rocket task log`.
- `done`/`cancelled` от агента — `403 human_only` с подсказкой попросить приёмку через `rocket task move <id> review`.

### Тишина: `quiet`

Майлстон — обещание работы, а не тикет: агент может месяцами держать его и ничего не показывать. Поэтому демон измеряет **видимые следы** держателя в майлстоне.

Следом считается что угодно, что человек потом прочтёт: запись журнала (кроме `kind=status`), положенный документ, открытый в майлстоне вопрос или сообщение в его треде. Всё — строго за авторством текущего держателя (`assigned_role`), поэтому док, написанный человеком, или запись предыдущего держателя чужие часы не сбрасывают. Если следов нет вовсе, тишина отсчитывается от `updated_at` задачи, который ставят take/assign, — часы идут с момента, когда майлстон стал чьим-то.

Порог — `milestone_quiet_after` (yaml, по умолчанию 24h). Тише порога считаются только майлстоны **в работе (`brainstorm` или `in_progress`) и взятые**: в `backlog` работа не начиналась, а `review`/`done`/`cancelled` — ход человека, не агента. Обдумывание — тоже работа, и агент, замолчавший на стадии `brainstorm`, — ровно тот случай, ради которого напоминание и заведено.

Из этого правила растут два канала, и они не могут разойтись — правило одно (`heartbeat.QuietMilestone`):

- **агенту** — напоминание `[rocket quiet milestone] #N "…" has had no visible activity from you for …` с тремя готовыми командами (журнал, документ, вопрос); живому в сессию, спящему в инбокс, не чаще одного раза в 24 часа на майлстон;
- **человеку** — производное поле `quiet` в ответах API (в базе не хранится, считается на каждом чтении) и событие `milestone.quiet`; из них дашборд и мобильное приложение рисуют бейдж. Сообщений человеку heartbeat не шлёт.

Подробности прохода — [08-orchestrators.md](08-orchestrators.md), §«Молчащие майлстоны».

### Где майлстон виден

- `rocket task ls --milestones` — канбан майлстонов в терминале; `rocket task show <id>` печатает `Milestone: yes`, держателя и готовую команду `rocket agent attach <agent>`.
- `rocket agent show <agent>` и `GET /v1/agents/{id}` — список майлстонов агента (`id`, `title`, `status`): одно место, где видно, что агент на себя взял.
- Дашборд: отдельная страница Milestones вне переключателя проектов, в mobile — таб Milestones ([11-dashboard.md](11-dashboard.md)).

Сессия у постоянного агента одна на все его майлстоны (её имя = id агента), поэтому «войти в майлстон» — это `rocket agent attach <agent>`, а не attach к сессии задачи: своей сессии у майлстона нет.

### Права: сводка

| Действие | Человек | Держатель | Другой постоянный агент | Оркестратор / воркер |
|---|---|---|---|---|
| Создать (`--milestone`) | да | да | да | нет |
| `take` | нет (у него `assign`) | no-op | да, если не взят | `403 agent_only` |
| `assign` / `--none` | да | `403 human_only` | `403 human_only` | `403 human_only` |
| Журнал, документы, `move` | да | да | нет | нет |
| `→ review` | да | да, если есть что смотреть | нет | нет |
| `done` / `cancelled` | да | `403 human_only` | `403 human_only` | `403 human_only` |
| `task start` | `403 milestone_not_startable` | то же | то же | то же |

## Интеграция с терминалом (Warp и любой другой)

Требование: из карточки задачи мгновенно попасть в tmux-сессию оркестратора.

- В карточке задачи (API, `task show`, дашборд) всегда есть: `session_id`, `tmux_name`, готовая команда `rocket attach <session>`.
- `rocket attach` принимает и id задачи: `rocket attach 12` → резолвит в сессию оркестратора задачи #12. Изнутри tmux использует `switch-client`, снаружи — `attach`.
- Имена tmux-сессий человекочитаемы (`billing-v2-orch`) — `tmux ls` / Warp-палитра сессий находят их поиском по slug.
- Дашборд показывает кнопку «копировать команду attach» на каждой карточке.
