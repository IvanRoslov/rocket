# Задачи (канбан)

Задача — первоклассная сущность в базе демона. Всё начинается с задачи: пользователь описывает, что нужно сделать, видит её на канбане, назначает на неё фича-оркестратора. Декомпозиция, документы, решения и проблемы стекаются в задачу — это durable-запись фичи, которая живёт дольше сессий и worktree.

## Модель

Два уровня:

- **Задача** (фича) — создаёт пользователь. На неё назначается оркестратор.
- **Подзадача** — создаётся **автоматически демоном** при `rocket spawn`: одна подзадача = один воркер. Оркестратор может создавать подзадачи и заранее (при декомпозиции), а потом привязывать к ним воркеров при спавне (`rocket spawn --subtask <id>`).

Так пользователь видит всю декомпозицию: как оркестратор разбил фичу, кто над чем работает, что уже сделано.

### Поля

- `id` — короткий числовой (#12), используется в CLI и UI.
- `parent_id` — NULL у задачи, id задачи у подзадачи.
- `title`, `description` (markdown).
- `project_id` — проект, которому принадлежит задача (канбан сгруппирован по проектам); у подзадачи дополнительно `repo_id` — репозиторий её воркера.
- `status` — `backlog | in_progress | review | done | cancelled`.
- `feature_slug` — присваивается при назначении оркестратора; общий для задачи и её подзадач.
- `session_id` — привязанная сессия: у задачи — оркестратор, у подзадачи — воркер. Через неё из карточки задачи всегда доступны `tmux_name` и команда attach (см. «Интеграция с терминалом»).
- `created_by` — `user | orchestrator`.
- `created_at`, `updated_at`, `completed_at`.

## Статусная механика

Статусы двигаются и автоматически (из жизненного цикла сессий/PR), и явно (командой). Явное всегда побеждает автоматическое.

**Задача (фича):**

| Переход | Триггер |
|---|---|
| `backlog → in_progress` | назначен оркестратор (`rocket task start`) |
| `in_progress → review` | оркестратор доложил о готовности: `rocket task move <id> review` (kickoff требует сделать это, когда все PR смержены) |
| `review → done` | пользователь принял работу (CLI или канбан) |
| `→ cancelled` | пользователь; убивает оркестратора каскадно |

**Подзадача (воркер):**

| Переход | Триггер |
|---|---|
| создана `in_progress` | `rocket spawn` (или `backlog`, если создана оркестратором заранее без воркера) |
| `in_progress → review` | автоматически: у воркера открылся PR |
| `review → done` | автоматически: PR смержен (вместе с авто-cleanup воркера) |
| любые ручные переходы | `rocket task move` — оркестратором или пользователем |

## Документы и журнал задачи

Оркестратор обязан (это часть kickoff-промпта) складывать в задачу все значимые артефакты. Хранение — в базе демона, привязано к задаче, переживает смерть сессий.

**Документы** (`task_docs`) — версионируемые markdown-документы:

- `kind`: `spec` (спека фичи), `plan` (план/декомпозиция), `report` (итоговый отчёт), `doc` (прочее).
- Обновление того же документа создаёт новую версию (старые сохраняются).

**Журнал** (`task_log`) — append-only записи-события хода работы:

- `kind`: `decision` (принятое решение + почему), `problem` (возникшая проблема), `note` (заметка), `status` (автозаписи о переходах статусов, спавнах, PR).
- Автор — сессия (оркестратор или воркер) либо пользователь.

Воркеры тоже пишут в журнал своей подзадачи (их системный промпт требует фиксировать решения и проблемы).

## Вопросы и ответы через задачу

Во время брейншторма пользователь и оркестратор общаются напрямую (терминал/чат карточки). Но когда работа уже идёт, вопрос, заданный просто в терминал, легко пропустить. Для этого — явный механизм Q&A:

1. **Оркестратор задаёт вопрос:** `rocket task ask <task-id> "<вопрос>"` (можно с контекстом: `--context "<md>"`). Вопрос сохраняется со статусом `open`; оркестратор продолжает работать над тем, что не заблокировано вопросом (или ждёт, если заблокировано всё).
2. **Пользователь видит, что от него ждут ответа:** бейдж «? ждёт ответа» на карточке канбана и в списке проектов, баннер с вопросом наверху карточки задачи, счётчик открытых вопросов в `rocket ls` / `rocket task show`.
3. **Пользователь отвечает:** поле ответа под вопросом в дашборде (кнопка «Отправить оркестратору») или `rocket task answer <question-id> "<ответ>"`.
4. **Доставка:** ответ сохраняется рядом с вопросом (`answered`), и демон кладёт его в очередь сообщений оркестратору: `[task #12 answer Q3] <ответ>`. Оркестратор получает его как обычное входящее сообщение.

Вопросы и ответы навсегда остаются в истории задачи (видны в Journal вперемешку с остальной хронологией — это тоже часть «как шла задача»). Воркеры механизмом не пользуются: их канал — оркестратор (`rocket send`); в Q&A задачи ходит только оркестратор.

Открытый вопрос не двигает статус задачи, но подсвечивается как требующий внимания; heartbeat оркестратора продолжает работать (воркеры-то работают).

## CLI

```
rocket task add "<title>" [--project <id>] [--desc <md>|--desc-file <f>]
rocket task ls [--status <s>] [--project <id>]     # канбан в терминале
rocket task show <id>                              # карточка: статус, сессия, подзадачи, доки, журнал
rocket task start <id> [--agent <name>]            # создать оркестратора и назначить на задачу
rocket task move <id> <status>
rocket task doc put <id> --kind spec --title "..." --file <f.md>
rocket task log <id> --kind decision|problem|note "<текст>"
rocket task ask <id> "<вопрос>" [--context <md>]   # оркестратор → пользователь
rocket task questions [<id>] [--open]              # открытые вопросы
rocket task answer <question-id> "<ответ>"         # пользователь → оркестратор
rocket task cancel <id>
```

`rocket up "<описание>"` остаётся как шорткат: создаёт задачу и сразу делает `task start`.

Для агентов те же команды (`task doc put`, `task log`, `task move`, `task add --parent`); демон проверяет права: оркестратор — только своя задача и её подзадачи, воркер — только своя подзадача.

## Интеграция с терминалом (Warp и любой другой)

Требование: из карточки задачи мгновенно попасть в tmux-сессию оркестратора.

- В карточке задачи (API, `task show`, дашборд) всегда есть: `session_id`, `tmux_name`, готовая команда `rocket attach <session>`.
- `rocket attach` принимает и id задачи: `rocket attach 12` → резолвит в сессию оркестратора задачи #12. Изнутри tmux использует `switch-client`, снаружи — `attach`.
- Имена tmux-сессий человекочитаемы (`billing-v2-orch`) — `tmux ls` / Warp-палитра сессий находят их поиском по slug.
- Дашборд показывает кнопку «копировать команду attach» на каждой карточке.
