# Задачи (канбан)

Задача — первоклассная сущность в базе демона. Всё начинается с задачи: пользователь описывает, что нужно сделать, видит её на канбане, назначает на неё фича-оркестратора. Декомпозиция, документы, решения и проблемы стекаются в задачу — это durable-запись фичи, которая живёт дольше сессий и worktree.

## Модель

Два уровня:

- **Задача** (фича) — создаёт пользователь. На неё назначается оркестратор.
- **Подзадача** — создаётся **автоматически демоном** при `rocket spawn`: одна подзадача = один воркер. Оркестратор может создавать подзадачи и заранее (при декомпозиции), а потом привязывать к ним воркеров при спавне (`rocket spawn --subtask <id>`).

Так пользователь видит всю декомпозицию: как оркестратор разбил фичу, кто над чем работает, что уже сделано.

### Поля

- `id` — короткий числовой (#12), используется в CLI и UI.
- `parent_id` — NULL у задачи, id задачи у подзадачи.
- `title`, `description` (markdown).
- `project_id` — проект, которому принадлежит задача (канбан сгруппирован по проектам); у подзадачи дополнительно `repo_id` — репозиторий её воркера.
- `status` — `backlog | in_progress | review | done | cancelled`.
- `feature_slug` — присваивается при назначении оркестратора; общий для задачи и её подзадач.
- `session_id` — привязанная сессия: у задачи — оркестратор, у подзадачи — воркер. Через неё из карточки задачи всегда доступны `tmux_name` и команда attach (см. «Интеграция с терминалом»).
- `created_by` — `user | orchestrator | agent`.
- `created_at`, `updated_at`, `completed_at`.

## Статусная механика

Статусы двигаются и автоматически (из жизненного цикла сессий/PR), и явно (командой). Явное всегда побеждает автоматическое.

**Задача (фича):**

| Переход | Триггер |
|---|---|
| `backlog → in_progress` | назначен оркестратор (`rocket task start`) |
| `in_progress → review` | оркестратор доложил о готовности: `rocket task move <id> review` (kickoff требует сделать это, когда все PR смержены) |
| `review → done` | пользователь принял работу (CLI или канбан) |
| `→ cancelled` | пользователь; убивает оркестратора каскадно |

**Подзадача (воркер):**

| Переход | Триггер |
|---|---|
| создана `in_progress` | `rocket spawn` (или `backlog`, если создана оркестратором заранее без воркера) |
| `in_progress → review` | автоматически: у воркера открылся PR |
| `review → done` | автоматически: PR смержен (вместе с авто-cleanup воркера) |
| любые ручные переходы | `rocket task move` — оркестратором или пользователем |

## Документы и журнал задачи

Оркестратор обязан (это часть kickoff-промпта) складывать в задачу все значимые артефакты. Хранение — в базе демона, привязано к задаче, переживает смерть сессий.

**Документы** (`task_docs`) — версионируемые markdown-документы:

- `kind`: `spec` (спека фичи), `plan` (план/декомпозиция), `report` (итоговый отчёт), `doc` (прочее).
- Обновление того же документа создаёт новую версию (старые сохраняются).

**Журнал** (`task_log`) — append-only записи-события хода работы:

- `kind`: `decision` (принятое решение + почему), `problem` (возникшая проблема), `note` (заметка), `status` (автозаписи о переходах статусов, спавнах, PR).
- Автор — сессия (оркестратор или воркер) либо пользователь.

Воркеры тоже пишут в журнал своей подзадачи (их системный промпт требует фиксировать решения и проблемы).

## Вопросы и ответы через задачу

Во время брейншторма пользователь и оркестратор общаются напрямую (терминал/чат карточки). Но когда работа уже идёт, вопрос, заданный просто в терминал, легко пропустить. Для этого — явный механизм Q&A:

**Вопрос — это тред, а не одна пара «вопрос-ответ».** Частый случай: вопрос оркестратора непонятен — нужно попросить переформулировать, раскрыть контекст, уточнить детали, и только потом отвечать по существу. Поэтому вопрос живёт как мини-диалог до явного разрешения.

**И у треда не две стороны, а список участников.** Изначально тред был жёстким диалогом «человек ↔ оркестратор»: постоянный агент вроде `cto` не мог ни ответить оркестратору, ни закрыть тред, и обходил это, выдавая себя за человека. Теперь права привязаны к участию, а не к роли, и в одном треде могут разговаривать человек, оркестратор задачи и один или несколько постоянных агентов.

### Участники

Идентификатор участника — одно из трёх:

| Значение | Кто |
|---|---|
| `human` | человек |
| id постоянного агента (`cto`) | агент `kind=agent` |
| session id (`reply-answer-orch`) | оркестратор или воркер |

Участником становятся двумя способами: **вас назвали в `--to`** любой записи треда, либо **вы сами написали** в тред. Сверх этого при создании треда сразу сеются обе его стороны: человек — всегда, и вторая сторона предмета треда (оркестратор задачи, `task.SessionID`), если она есть. Без этого тред, открытый человеком на задаче без оркестратора, было бы некому доставить; если оркестратора у задачи нет, никто и не сеется — участник «из воздуха» не выдумывается.

Список участников треда отдаётся в поле `participants` и виден в CLI и дашборде.

### Очередь ответа: `--to` — это «кто должен ответить», а не «кому доставить»

Это главное место, где модель понимают неправильно. Два разных механизма:

- **Доставка (уведомления).** Каждая новая запись треда — открытие, реплика, финальный ответ — доставляется **всем участникам, кроме автора**. Всегда. `--to` доставку **не сужает**.
- **Очередь (`waiting_on`).** Кого ждут. Вот её `--to` и задаёт.

`waiting_on` считается по **последней записи треда** — это либо последнее сообщение, либо, пока сообщений нет, сам вопрос. Адресаты есть и у того, и у другого, поэтому правило одно:

- тред `resolved` → не ждут никого;
- у последней записи непустой список адресатов (`--to`) → ждут ровно их;
- иначе → ждут всех участников, кроме автора последней записи.

`--to` поэтому сужает очередь одинаково и при `ask`, и при `reply`: `rocket task ask 722 "..." --to cto` даёт `waiting_on = [cto]`, и человека этот тред не дёргает.

Неочевидная часть — **побеждает именно последняя запись, в том числе когда адресатов у неё нет**. Реплика без `--to` не наследует адресатов, с которыми тред открывали: она возвращает очередь ко всем участникам, кроме своего автора. То есть `--to` — это не свойство треда, которое держится до конца, а свойство одной записи.

Рядом с `waiting_on` API отдаёт `your_turn` — тот же список, но применительно к тому, кто спрашивает (человеку, агенту, оркестратору — каждому своё значение). Именно `your_turn` зажигает бейдж «ждут вас». Совместимое поле `whose_turn` (`user` | `orchestrator`) сохранено для старых клиентов и выводится из `waiting_on`: `user`, если в нём есть человек, иначе `orchestrator` при непустом списке.

**Видеть тред и быть в очереди по нему — намеренно разные вещи.** Человек видит **все** треды всегда, в том числе адресованные не ему: `--to cto` не прячет тред от человека, а лишь снимает с него бейдж. `your_turn` только помечает треды и включает необязательный фильтр, но ничего не скрывает.

### Как идёт диалог

1. **Оркестратор открывает вопрос:** `rocket task ask <task-id> "<вопрос>"` (можно с контекстом: `--context "<md>"`, можно с адресатами: `--to cto`). Вопрос получает номер (Q3) и статус `open`; оркестратор продолжает работать над тем, что не заблокировано вопросом (или ждёт, если заблокировано всё).
2. **Те, от кого ждут ответа, это видят:** человеку — бейдж «? ждёт ответа» на карточке канбана и в списке проектов, баннер с вопросом наверху карточки задачи, счётчик открытых вопросов в `rocket ls` / `rocket task show`. Агенту-участнику — доставка в сессию или в инбокс (см. ниже).
3. **Участник пишет в тред** — двумя способами:
   - **Уточнение или обсуждение** («не понял, переформулируй», «что значит X?») — `rocket task reply <question-id> "<текст>"`. Вопрос остаётся `open`, очередь переходит к остальным (или к тем, кого назвали в `--to`).
   - **Финальный ответ** (`rocket task answer` / кнопка «Ответить и закрыть») — вопрос становится `resolved`. Это доступно **человеку и постоянным агентам**; оркестратор и воркер получают `403` с подсказкой использовать `reply`.
4. **Оркестратор отвечает в тред** тем же `rocket task reply` — переформулировка/раскрытие. Получив реплику-уточнение, оркестратор обязан ответить в тред, а не открывать новый вопрос.
5. **Делегирование.** Человек может не отвечать сам, а перевести очередь на того, кто в теме: `rocket task reply <qid> --to cto "разберись и ответь"`. `cto` вступает в тред, получает уведомление, и дальше вправе закрыть тред своим `answer` — оркестратор получает решение без человека.
6. Тред может иметь сколько угодно раундов; каждая запись доставляется через очередь сообщений (гарантия, ретраи, видимый статус).

Статусы вопроса: `open` (+ `waiting_on` / `your_turn`) → `resolved`. **Resolved — не навсегда:** если у участника есть доказательства, что финальный ответ противоречит фактам, его реплика в тот же тред (`rocket task reply`) **переоткрывает** вопрос — статус снова `open`, пользователю поднимается бейдж, публикуется событие `task.question_reopened`. Переоткрывать может любой участник, кроме человека; для человека resolved-вопрос финален (реплика → `409 question_resolved`): передумал — просто жди реакции или напиши в чат. Оркестратору промпт предписывает не исполнять оспоренное решение до повторного ответа и спорить только фактами. Переоткрытие — узкий инструмент строго про сам ответ (выбранное не может работать / выбрано явно не то / ответ непонятен); всё, что обнаруживается дальше по ходу работы, — НОВЫЕ вопросы (со ссылкой на старый номер), иначе задача рискует навсегда остаться в одном треде.

### Уведомления

Каждая запись треда рассылается всем участникам, кроме автора, тем же путём, что обычное сообщение:

- **постоянный агент** — живой сессии тело доезжает в очередь; мёртвой пишется строка в инбокс, а при оживлении демон инжектит `[rocket] You have N unread messages` (см. [10-agents.md](10-agents.md));
- **оркестратор или воркер** — живой сессии тело в очередь; сессия в терминальном состоянии инбокса не имеет, поэтому запись просто не доставляется и логируется;
- **человек** — ему ничего не инжектится: он читает тред в CLI, дашборде и мобильном приложении.

Формат доставляемой записи: `[task #12 Q3 reply from cto] <текст>` — вид записи (`question` | `reply` | `answer`) и автор. `from <id>` пишется единообразно, включая человека (`[task #12 Q3 answer from human] ...`): при нескольких участниках автора иначе из рамки не вывести.

### Права

| Действие | Человек | Постоянный агент | Оркестратор задачи | Воркер |
|---|---|---|---|---|
| `ask` — открыть тред | да | да | да, на своей задаче | нет |
| `reply` | да | да | если участник | если участник |
| `answer` / `dismiss` | да | да | нет — `403`, «use reply» | нет — `403` |
| Переоткрыть resolved репликой | нет (`409`) | да | да | да, если участник |
| Чтение тредов | все | все | треды своей задачи и где участвует | треды своей корневой задачи и где участвует |

`reply` доступен любому участнику; оркестратор задачи допускается и до того, как впервые написал, — иначе тред, открытый человеком, был бы ему недоступен. «Своя задача» для воркера — **корневая** задача над его подзадачей: вопросы живут только на корневых задачах, поэтому сравнение с самой подзадачей закрыло бы воркеру контекст его же фичи.

Полные треды навсегда остаются в истории задачи (видны в Journal вперемешку с остальной хронологией — это тоже часть «как шла задача»). Воркеры по умолчанию участниками не становятся — их канал общения с оркестратором остаётся `rocket send`; но воркера можно втянуть в тред через `--to`, и читать треды своей корневой задачи он может всегда.

Открытый вопрос не двигает статус задачи, но подсвечивается как требующий внимания; heartbeat оркестратора продолжает работать (воркеры-то работают). Если вопрос висит в статусе «ждёт оркестратора» дольше порога — heartbeat напоминает оркестратору ответить.

### Обратное направление: пользователь спрашивает оркестратора

Тот же механизм работает и в обратную сторону — пользователь может сам открыть тред, адресованный оркестратору задачи (только на корневой задаче, воркеры по-прежнему недоступны напрямую):

- **Пользователь открывает вопрос:** `rocket task ask-orch <task-id> "<вопрос>"` (или тот же POST `/v1/tasks/{id}/questions`, но без `X-Rocket-Session`). Вопрос сохраняется с `asked_by = ""` (конвенция «пусто = человек») и сразу же попадает в очередь сообщений оркестратора как `[task #12 Q4 question] <текст>` — не нужно ждать, пока оркестратор сам заглянет в тред.
- **`whose_turn` для свежего треда — `"orchestrator"`:** очередь ответа сразу за оркестратором, а не за пользователем (в отличие от треда, который открыл сам оркестратор).
- **Оркестратор отвечает в тред** тем же `rocket task reply <question-id> "<ответ>"`. Оркестратор НЕ закрывает такие треды (`rocket task answer` ему недоступен и по смыслу не подходит) — закрывает их только пользователь, как обычно.
- Остальной механизм (реплики, статусы, доставка) идентичен направлению «оркестратор → пользователь».

## CLI

```
rocket task add "<title>" [--project <id>] [--desc <md>|--desc-file <f>]
rocket task ls [--status <s>] [--project <id>]     # канбан в терминале
rocket task show <id>                              # карточка: статус, сессия, подзадачи, доки, журнал
rocket task start <id> [--agent <name>]            # создать оркестратора и назначить на задачу
rocket task move <id> <status>
rocket task doc put <id> --kind spec --title "..." --file <f.md>
rocket task log <id> --kind decision|problem|note "<текст>"
rocket task ask <id> "<вопрос>" [--context <md>] [--to a,b]   # открыть тред
rocket task ask-orch <id> "<вопрос>" [--context <md>] [--to a,b]  # пользователь: открыть вопрос оркестратору (доставляется сразу)
rocket task questions [<id>] [--open]              # вопросы, их треды и участники
rocket task reply <question-id> "<текст>" [--to a,b]   # реплика в тред (любой участник)
rocket task answer <question-id> "<ответ>"         # финальный ответ, закрывает; человек и постоянный агент
rocket task answer <question-id> --dismiss         # закрыть как неактуальный
rocket task cancel <id>
```

`--to` принимает идентификаторы участников (`human`, id постоянного агента, session id) — через запятую, флаг можно и повторять. Названные вступают в тред, получают уведомление и становятся `waiting_on` — одинаково при `ask`, `reply` и `answer`. Без `--to` ждут всех участников, кроме автора записи.

`rocket up "<описание>"` остаётся как шорткат: создаёт задачу и сразу делает `task start`.

Для агентов те же команды (`task doc put`, `task log`, `task move`, `task add --parent`); демон проверяет права: постоянный агент (`sessions.kind='agent'`) — как человек, оркестратор — только своя задача и её подзадачи, воркер — только своя подзадача.

Кто что может с задачами:

| Кто | Создать задачу | Запустить (`task start` / `up`) | Править |
|---|---|---|---|
| Человек (без `X-Rocket-Session`) | да, любую | да | любую |
| Постоянный агент (`kind='agent'`) | да, любую; `created_by='agent'` | да | любую |
| Оркестратор | только подзадачи своей задачи | нет — `403 only the human user or a registered agent may start a task` | своя задача и её подзадачи |
| Воркер | нет — `403 workers may not create tasks` | нет — тот же `403` | только своя подзадача |

## Интеграция с терминалом (Warp и любой другой)

Требование: из карточки задачи мгновенно попасть в tmux-сессию оркестратора.

- В карточке задачи (API, `task show`, дашборд) всегда есть: `session_id`, `tmux_name`, готовая команда `rocket attach <session>`.
- `rocket attach` принимает и id задачи: `rocket attach 12` → резолвит в сессию оркестратора задачи #12. Изнутри tmux использует `switch-client`, снаружи — `attach`.
- Имена tmux-сессий человекочитаемы (`billing-v2-orch`) — `tmux ls` / Warp-палитра сессий находят их поиском по slug.
- Дашборд показывает кнопку «копировать команду attach» на каждой карточке.
