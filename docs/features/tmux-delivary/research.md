# Исследование доставки сообщений без повреждения ручного ввода

Задача: #5902. Дата: 31 октября 2026.

## Вывод

Среди проверенных средств tmux и расширений не найден канал, который доставлял бы сообщение прямо в контекст произвольного терминального агента, обходя его строку ввода. Практический путь — использовать интерфейс самого агента. Для Pi такой интерфейс есть внутри обычного TUI. Для Codex есть очередь и серверный протокол, но текущий способ запуска Rocket с ними требует отдельной проверки. Для Kimi серверный API существует, однако его нельзя считать внешним входом в уже работающий TUI.

Это исследование документации, исходников и установленных CLI. Одновременный ручной ввод и доставка в живые сессии ещё не проверялись. Рекомендации ниже не означают подтверждённую совместимость или выбранный человеком объём реализации.

## Текущее состояние Rocket

Проверен собственный worktree: `86f21d85bb45f1ec894d9078321f9aa5ce3b3fd3`. Во время проверки `git ls-remote origin refs/heads/main` вернул тот же коммит. Файлы зеркала не использовались как источник актуального состояния.

- `internal/queue/queue.go:206`: отдельный сокет выбирается только для `claude-code` при включённой настройке `socket_delivery`.
- `internal/queue/socket.go:31`: существующий `SocketSender` описывает именно Claude; нельзя механически выдать за тот же протокол очереди других агентов.
- `internal/runtime/tmux.go:254`: перед вставкой Rocket читает экран, распознаёт черновик, затем отдельно очищает ввод, загружает буфер, вставляет текст и нажимает Enter. Между проверкой и изменением ввода остаётся гонка.
- `internal/runtime/tmux.go:280`: для стандартного диалекта очистка — `C-u`; для Kimi выбираются собственные клавиши очистки. Pi не очищается, но вставка всё равно использует общий ввод.
- `internal/queue/queue.go:621`: Codex/Kimi после длительного черновика могут получить принудительную доставку с очисткой. Для Pi такой обход отключён.
- `internal/config/config.go:28`: стандартный срок ожидания черновика — 10 минут.
- `internal/agent/codex/codex.go:230`: `--no-daemon` добавлен намеренно: общий сервер Codex терял переменные `ROCKET_*` конкретной сессии (#5707/Q1).

Следовательно, проблема не сводится к регулярному выражению для символов в строке: есть гонка между отдельными действиями и предусмотренное принудительное удаление черновика.

## tmux и готовые средства

[Руководство tmux](https://raw.githubusercontent.com/tmux/tmux/master/tmux.1) описывает `pipe-pane -I` как ввод, эквивалентный набранному пользователем. Control mode управляет командами tmux; он не предоставляет API контекста приложения внутри панели. Bracketed paste меняет обработку вставки приложением, но не создаёт отдельного получателя.

Проверены примеры смежных инструментов:

- [tmux-yank](https://github.com/tmux-plugins/tmux-yank) занимается копированием в системный буфер обмена.
- [tprompt: механизм доставки](https://github.com/aurokin/tprompt/blob/main/docs/tmux/delivery.md) использует `load-buffer` / `paste-buffer` либо `send-keys`. По архитектуре это тот же путь через терминальный ввод.

Вывод о непригодности этих механизмов для независимой доставки — инженерный вывод из их устройства. Он не доказывает отсутствие любого возможного стороннего расширения. Ускорение вставки, блокировка клавиатуры или сохранение/возврат текста по снимку экрана не дают общей гарантии для разных редакторов ввода и всех подключённых клиентов.

Версии и команды подтверждены локально через `--version` / `--help`, включая `codex queue --help`, `codex app-server --help`, `kimi session --help`, `kimi web --help`. Никакие рабочие сессии не получали тестовых сообщений.

## Codex

[Официальная документация CLI](https://learn.chatgpt.com/docs/developer-commands) подтверждает `codex queue --thread <UUID> --message <TEXT>`, точные имена сессий и `--remote`. Для адресации Rocket следует предпочесть UUID, не имя. `--no-daemon` означает работу без общего фонового сервера.

[Документация app-server](https://learn.chatgpt.com/docs/app-server) описывает Unix socket с WebSocket handshake, несколько транспортов, подключение штатного TUI через `--remote`, начало и steering хода. Это настоящий протокол приложения, а не имитация клавиш. Серверные экспериментальные возможности требуют проверки по установленной версии.

Кандидат для проверки: отдельный app-server на сессию Rocket с её окружением и локальным сокетом; штатный TUI и отправитель подключаются к нему. Так можно сохранить интерфейс, не возвращая ошибку общего окружения. Это гипотеза, не проверенный рецепт запуска.

Нужно проверить UUID работающей сессии, доставку idle/busy, видимость внешнего сообщения в TUI, целость черновика, окружение shell-tools, восстановление процесса и подтверждение неоднозначной отправки. Нельзя пробовать отправку через `queue` в текущую standalone-сессию наугад: это не доказательство доставки в тот же процесс.

## Pi

[Документация расширений](https://pi.dev/docs/latest/extensions) и [официальный пример](https://raw.githubusercontent.com/earendil-works/pi/main/packages/coding-agent/examples/extensions/send-user-message.ts) предоставляют `sendUserMessage`, режимы `steer` / `followUp` и загрузку расширения через `--extension`. Сокет следует открывать при `session_start` и закрывать при `session_shutdown`.

В установленном пакете Pi 1.4.0 дополнительно проверен `dist/core/agent-session.js`: `sendUserMessage` передаёт текст в `prompt` с источником `extension`, не через редактор ввода. Однако внешний Extension API вызывает асинхронную отправку с обработчиком ошибок и не возвращает вызывающему подтверждение сохранения. Поэтому ответ моста «получил запрос» нельзя автоматически трактовать как надёжную доставку агенту.

Кандидат: поставляемое Rocket расширение Pi с локальным UDS, привязкой к текущей сессии, идентификатором сообщения и подтверждением по событию/истории. Поддержка DeepSeek в данном месте зависит от Pi, а не от особого терминального протокола модели. Сохранение черновика при перерисовках TUI ещё нужно подтвердить живым опытом.

## Kimi Code

[Server API](https://moonshotai.github.io/kimi-code/en/reference/server-api.html) позволяет подавать prompt в очередь, получать его ID и состояние, задавать клиентский ID для повторной отправки. Но API отдельно описывает конфликты сессии, занятой другим процессом, и запрещает отбирать блокировку у живого владельца: история может перемешаться. Поэтому запустить второй процесс `kimi web` и писать в файл той же сессии — не доказанный безопасный мост в TUI.

[Hooks](https://moonshotai.github.io/kimi-code/en/customization/hooks) также не решают задачу пробуждения: `Stop` может продолжить уже завершающийся ход, а `SessionHeartbeat` относится к наблюдательным событиям, чьи возвращаемые значения не меняют основной поток. Доставка только на следующем ручном сообщении не удовлетворяет желанию автоматически будить простаивающего агента.

Старая документация Python `kimi-cli --wire` относится к другому поколению CLI. Локальный Kimi 2.4.0 — TypeScript/Bun CLI; его `--help` не предлагает этот режим. Подменять им исследование текущего адаптера нельзя.

Для сохранения штатного TUI нужен дополнительный ресерч по поддерживаемому входу в его процесс либо изменение upstream. Альтернатива — серверный Kimi и клиент Rocket, но это уже изменение пользовательского интерфейса и отдельный объём работ.

## Сравнение подходов и рекомендация

1. Продолжить улучшать вставку через tmux: небольшой объём, но общий ввод и гонки остаются; исходную гарантию не даёт.
2. Отдельные интерфейсы агентов с сохранением штатных TUI: наиболее прямое решение для Pi; для Codex — после проверки собственного server/TUI запуска; Kimi требует отдельного подтверждения возможности. Рекомендую этот путь поэтапно.
3. Собственный интерфейс Rocket поверх серверных API всех агентов: единый владелец ввода и доставки, но существенно больший проект с воспроизведением диалогов, очередей, истории и восстановления.

В storm-вопросе 5902/Q1 человек выбрал: «Сохранить штатные терминалы, внедрять поэтапно». Для Go предложен первый этап: рабочее подключение Pi и воспроизводимые проверки Codex/Kimi; их рабочее подключение — по следующей спецификации после проверки.

## Условия будущей проверки

- Одна и та же сессия и история при ручном и программном вводе; другой процесс с похожим именем не подходит.
- Однострочный, многострочный, кириллический черновик и курсор внутри строки сохраняются при idle/busy и перерисовках.
- Ни очистка, ни paste, ни Enter в терминал не вызываются на отдельном канале.
- Потеря соединения до/после принятия сообщения различается; неоднозначный результат не вызывает слепую повторную отправку и дубль.
- Перезапуск Rocket, агента и смена текущей сессии не доставляют сообщение прежнему или соседнему получателю.
- Если отдельный канал выбран как обязательный, его отказ не должен молча возвращать небезопасную вставку.
- Проверяется окружение дочерних инструментов Codex; существующие возможности Claude сохраняются.

Это критерии для согласования и планирования, а не результаты уже выполненных live-тестов.
