# Протокол cross-session messaging Claude Code (UDS)

Реверс-инжиниринг протокола, по которому одна сессия Claude Code доставляет
сообщение в другую через unix-сокет. Цель для rocket — доставлять сообщения
воркерам, не инжектируя текст в tmux (инжект стирает недописанный ввод
пользователя).

**Источник фактов:** бандл CLI `~/.local/share/claude/versions/2.1.226`
(Mach-O arm64, внутри — минифицированный JS; `VERSION 2.1.226`,
`GIT_SHA e140b3281c1e8d834468889bd0a5c3fd2f15507c`, `BUILD_TIME 2026-08-08`).
Модуль в бандле логируется под префиксами `[uds-messaging]` (сервер),
`[uds-client]` (клиент), `[cross-session-inbound]` (политика приёма),
`[peer-guard]` (антифлуд). Имена функций ниже — минифицированные идентификаторы
из этой сборки, они приведены только чтобы находки можно было перепроверить.

Проверено на практике: Go-прототип `internal/socketmsg` доставил сообщение в
живую сессию (см. «Проверка»).

---

## 1. Реестр сессий на диске

Каждая сессия при старте пишет `~/.claude/sessions/<pid>.json`
(`CLAUDE_CONFIG_DIR` переопределяет `~/.claude`). Каталог создаётся с правами
`0700`. Имя файла — pid процесса `claude`; CLI считает истиной именно имя
файла и удаляет файлы, где `basename` не совпадает с числом.

Пример живой записи:

```json
{
  "pid": 65759,
  "sessionId": "1d29aac6-19e2-47e6-a959-a60d4bd1df66",
  "cwd": "/Users/ivanroslov/.rocket/worktrees/rocket/claude-code-draft-guard",
  "startedAt": 1786352705321,
  "procStart": "Mon Aug 10 09:05:04 2026",
  "version": "2.1.226",
  "peerProtocol": 1,
  "kind": "interactive",
  "entrypoint": "cli",
  "tmux": "claude-code-draft-guard:@2569.%2569",
  "messagingSocketPath": "/tmp/cc-socks/65759.sock",
  "name": "claude-code-draft-guard-a2",
  "nameSource": "derived",
  "status": "busy",
  "updatedAt": 1786352705553,
  "statusUpdatedAt": 1786352705553
}
```

Поля, значимые для rocket:

| поле | смысл |
|---|---|
| `pid` | pid процесса `claude`; совпадает с именем файла |
| `sessionId` | UUID сессии (то же, что `CLAUDE_CODE_SESSION_ID`) |
| `messagingSocketPath` | путь к сокету; **пусто, если сокет не поднят** |
| `peerProtocol` | версия peer-протокола, сейчас `1`; CLI требует `>= 1` при листинге пиров |
| `kind` | `interactive` / `bg` и т. п.; сам CLI показывает как пиров только `interactive` |
| `name`, `nameSource` | отображаемое имя (`derived` — выведено из cwd) |
| `status` | `idle` / `busy`; обновляется рантаймом |
| `procStart` | строка времени старта процесса — защита от переиспользования pid |
| `tmux` | окно tmux, если сессия там живёт |
| `cwd` | рабочий каталог |

**Как определять живость.** Наличие файла ничего не значит: CLI сам сверяет
`pid` (жив ли процесс) и `procStart` (тот ли это процесс), и удаляет запись,
если процесс мёртв. Более дешёвая и надёжная для внешнего процесса проверка —
попробовать подключиться к `messagingSocketPath`: мёртвый сокет-файл остаётся
на диске после падения процесса, но `connect` по нему падает с `ECONNREFUSED`.
Сам CLI делает ровно это (`MLS`/`N4p`, таймаут 250 мс). Прототип: функция
`socketmsg.Probe`.

Записи с пустым `messagingSocketPath` встречаются регулярно (по нашему
снимку — ~25% сессий): это либо сессии, поднятые до включения фичи, либо
случаи, где bind не удался. Такие сессии по сокету недостижимы, для них
остаётся tmux-инжект.

## 2. Сокет

Путь строится так (`DLS`):

1. `${XDG_RUNTIME_DIR:-<tmpdir>}/cc-socks/<pid>.sock`;
2. если получившийся путь длиннее **103 байт** (лимит `sun_path`) —
   `/tmp/cc-socks-<uid>/<pid>.sock` (на Termux вместо `/tmp` берётся
   `$PREFIX/tmp`).

На macOS в нашей среде это `/tmp/cc-socks/<pid>.sock`.

Права: каталог `0700`, сам сокет `chmod 0600` после `listen`. То есть
**доступ ограничен владельцем** — это единственная реальная аутентификация в
протоколе. Никакого токена, рукопожатия или подписи нет: кто может открыть
файл, тот может слать сообщения.

Путь также экспортируется дочерним процессам как
`CLAUDE_CODE_MESSAGING_SOCKET` и показывается в `/status` как «Peer address» с
префиксом `uds:`.

Сервер: `net.createServer({allowHalfOpen: true})`, слушающий сокет
`unref()`-нут (не держит процесс живым). При выходе сессия рвёт все соединения
и удаляет файл сокета.

## 3. Формат кадра

**NDJSON:** один JSON-объект на строку, разделитель `\n`, кодировка UTF-8.
Соединение можно закрыть сразу после записи; хвост без завершающего `\n`
сервер тоже разберёт на событии `end`.

Ограничения приёмника (`ILS`):

- если в буфере накопился **1 MiB** без `\n` — соединение уничтожается,
  буфер сбрасывается;
- строка, которая не парсится как JSON, логируется (`warn`) и **пропускается**;
  соединение остаётся живым;
- пустые/пробельные строки игнорируются.

Рукопожатия нет. **Ответа на сообщение по тому же соединению нет** —
приёмник в это соединение вообще ничего не пишет. Единственное, что возвращает
`connect`+`write` без ошибки, — «байты приняты ядром», не «сообщение
доставлено пользователю».

Отправитель в самом CLI (`L4p`) ставит таймаут **5 с** на всю операцию, а на
macOS перед `end()` выжидает небольшую паузу — немедленный `shutdown(WR)` там
способен обрубить ещё не вычитанные данные. Прототип воспроизводит и то, и
другое (`DefaultTimeout`, `macOSLingerDelay`).

## 4. Сообщение типа `user`

Это то, что попадает в очередь промптов получателя.

```json
{
  "msgV": 1,
  "msg_id": "8714b783-f8bc-4448-acc2-74ff2a02566a",
  "type": "user",
  "message": { "role": "user", "content": "<конверт, см. §5>" },
  "priority": "next",
  "from": "uds:/tmp/cc-socks/rocket-spike.sock",
  "session_id": "1d29aac6-19e2-47e6-a959-a60d4bd1df66",
  "file_attachments": []
}
```

| поле | обяз. | смысл |
|---|---|---|
| `type` | да | единственное строковое поле, которое валидируется до всего остального (`Nkf`); без него сообщение отбрасывается |
| `message.content` | да | тело; **не строка или пустая строка → сообщение молча игнорируется** |
| `msgV` | нет | версия конверта, сейчас `1`. Приёмник 2.1.226 его не проверяет, но слать стоит |
| `msg_id` | нет | UUIDv4 (`^[0-9a-f]{8}-...{12}$`); нужен только чтобы сопоставить квитанцию (§7) |
| `priority` | нет | `now` / `next` / `later`; по умолчанию `next`. `now` обходит внутреннюю сериализацию обработки |
| `from` | нет | обратный адрес, см. §5.1. Без него квитанций не будет |
| `session_id` | нет | если задан и **не совпал** с `sessionId` получателя — сообщение отбрасывается (`Bkf`). Дешёвая защита от гонки «pid переиспользован» |
| `uuid` | нет | идентификатор записи в очереди; если не задан, приёмник сгенерирует сам |
| `file_attachments` | нет | вложения; в спайке не разбирались. Пустой/отсутствующий массив — нормальный случай |

`priority: "now"` без вложений обрабатывается вне общей цепочки промисов —
для нас это самый быстрый путь, но и самый агрессивный по отношению к тому,
чем сессия занята.

## 5. Конверт `cross-session-message`

`message.content` — не голый текст. CLI заворачивает тело в тег
`cross-session-message` (`PCr`):

```
<cross-session-message from="uds:/tmp/cc-socks/rocket-spike.sock" from-name="rocket-spike">
[from rocket-spike] текст сообщения
</cross-session-message>
```

Правила, которые обязан соблюдать отправитель:

- **порядок атрибутов фиксирован**: `from`, `from-session`, `hop-chain`,
  `from-name`, `from-mode`; любые лишние или переставленные атрибуты ломают
  разбор;
- ровно по одному `\n` до и после тела;
- получатель (`Pjd`) разбирает конверт регуляркой **и затем пересобирает его
  заново и сравнивает со входом**: если строки не совпали побайтно, конверт
  считается не-конвертом, и текст показывается как есть;
- вхождения `</cross-session-message` внутри тела экранируются как
  `<\/cross-session-message` (`cUt`) — иначе тело закроет конверт досрочно;
- `from-name` не должен содержать `"`, `<`, `>`, `\r`, `\n`. Для показа имя
  ещё раз чистится до `[\p{L}\p{N}._-]` и обрезается до 20 символов, так что
  длинные имена и пробелы всё равно потеряются — лучше сразу слать
  slug-подобное имя.

Незакрытый или неполный конверт — не ошибка протокола: сообщение просто
покажется получателю как обычный текст без атрибуции. Если вы уже
префиксуете тело строкой вида `[from claude-code-orch] ...`, конверт всё равно
стоит слать: он даёт получателю машинно-читаемый обратный адрес.

Атрибуты `from-session` и `hop-chain` относятся к защите от петель
пересылки между сессиями; `hop-chain` — цепочка HMAC-меток, ключ которой
(`xzb`) генерируется случайно при старте **каждого** процесса. Внешний
отправитель воспроизвести её не может и не должен — просто не передавайте эти
атрибуты.

### 5.1. Адрес отправителя

Адрес — это `uds:` + путь к сокету, где каждый байт вне
`[A-Za-z0-9:_/.\-]` заменён на `%XX` (заглавные hex, `Cjd`). Итог должен
попадать под `^(?:uds|bridge|did):[A-Za-z0-9%:_/.\\-]{1,200}$`.

Одно и то же значение кладётся и в поле `from` JSON-объекта, и в атрибут
`from` конверта.

### 5.2. `from-mode` и режим прав

Атрибут `from-mode` принимает `bypass` или `prompting` и означает «в каком
классе разрешений работает отправитель». Он влияет только на решение
получателя, находящегося в bypass-режиме (§6). Внешнему отправителю честнее
его **не** ставить: тогда сообщение к bypass-сессии будет придержано и
показано пользователю, а не пролезет с чужими привилегиями.

## 6. Что происходит на стороне получателя

Решение принимает `crossSessionInbound` — настройка со значениями
`accept` / `hold` / `refuse`. Она читается из цепочки
`policySettings → flagSettings → userSettings`, затем ужесточается
`localSettings`/`projectSettings` (репозиторий может только ужесточить, не
ослабить).

Если настройка **не задана явно**, действует правило по режиму прав
получателя (`gKp`):

| режим получателя | `from-mode` отправителя | итог |
|---|---|---|
| обычный (prompting) | любой / отсутствует | `accept` |
| `bypassPermissions` (или `plan` при доступном bypass) | отсутствует | `hold` (причина `no-mode-asserted`) |
| `bypassPermissions` | `bypass` | `accept` |
| `bypassPermissions` | `prompting` | `hold` (`mode-mismatch`) |
| режим не определён | — | `hold` (fail-closed) |

Исходы:

- **accept** — сообщение кладётся в очередь промптов как `origin.kind = "peer"`.
  Никакой квитанции отправителю **не** шлётся.
- **hold** — сообщение попадает в буфер удержания (не более 50 штук; при
  переполнении самое старое вытесняется со статусом `expired`), получателю
  показывается запрос на одобрение. Отправителю немедленно уходит квитанция
  `held`, затем — `delivered` (одобрено), `denied` (отклонено) или `expired`.
- **refuse** — сообщение отбрасывается. Отправителю уходит `denied`, только
  если оно до этого лежало в hold-буфере; сообщение, отклонённое сразу,
  никакой квитанции не порождает.

Отдельно, до политики, работает антифлуд на отправителя (`peer-guard`,
дефолты переопределяются флагом `tengu_harbor_kite_limits`):

- token bucket: ёмкость **30**, пополнение **0.5/с**;
- дедупликация: сообщение с телом, идентичным предыдущему от того же
  отправителя, в окне **30 с** отбрасывается (`duplicate`);
- не более **256** отслеживаемых отправителей (LRU);
- защита от петель: `hop-loop` (≥10 своих меток в цепочке), `hop-runaway`
  (цепочка длиннее 28);
- `queue-full` при более чем 50 недоставленных peer-сообщениях.

Отброшенные антифлудом сообщения **не порождают квитанций** — отправитель
узнаёт о них только по тишине. Для rocket это значит: не слать один и тот же
текст дважды подряд и не превышать ~0.5 сообщения в секунду на воркера в
установившемся режиме.

### Peer-credentials

Приёмник получает pid отправителя через `getPeerPid` по fd соединения
(`Ikf`). Это **не** аутентификация: pid запрашивается только когда получатель
сам в bypass-режиме, и используется, чтобы понять, не является ли отправитель
предком текущего процесса (self-sent — такое пропускается без удержания).
На Windows не поддерживается.

## 7. Квитанции: сообщения типа `control`

Обратный канал — **отдельное исходящее соединение** к сокету отправителя, а не
ответ в то же соединение. Формат:

```json
{
  "msgV": 1,
  "msg_id": "<новый uuid>",
  "type": "control",
  "action": "peer_message_status",
  "status": "held",
  "reason": "Your message is held for the recipient user's approval ...",
  "from": "uds:/tmp/cc-socks/65366.sock",
  "orig_msg_id": "<msg_id исходного сообщения>"
}
```

`status` ∈ `held` | `delivered` | `denied` | `expired`.

**Условия, при которых квитанция вообще будет отправлена** (`$oi`-колбэк):

1. у исходного сообщения был `from` вида `uds:...`, проходящий валидацию адреса;
2. распакованный путь лежит **в том же каталоге**, что и сокет получателя;
3. путь оканчивается на `.sock`;
4. исход — `held`/`delivered`/`denied`/`expired`, то есть сообщение прошло
   через удержание.

Следствие для rocket: чтобы видеть судьбу придержанных сообщений, демон должен
сам слушать unix-сокет **внутри `/tmp/cc-socks/` (или того же каталога, что и
сокеты сессий) с именем `*.sock`**. Иначе квитанции молча не отправляются.
Успешно принятое (`accept`) сообщение квитанции не порождает никогда — «нет
новостей» означает и «доставлено», и «съедено антифлудом».

Второй известный `action` — переименование сессии:

```json
{"msgV":1,"msg_id":"...","type":"control","action":"rename","name":"новое-имя"}
```

Неизвестные `action` логируются и игнорируются. Поле `session_id` в control-
сообщениях проверяется так же, как в `user`.

## 8. Как внешнему (не-Claude) отправителю заполнять поля

Минимально корректное сообщение из rocket:

```json
{
  "msgV": 1,
  "msg_id": "<uuid v4>",
  "type": "user",
  "priority": "next",
  "from": "uds:/tmp/cc-socks/rocket-daemon.sock",
  "session_id": "<sessionId получателя из реестра>",
  "message": {
    "role": "user",
    "content": "<cross-session-message from=\"uds:/tmp/cc-socks/rocket-daemon.sock\" from-name=\"claude-code-orch\">\n[from claude-code-orch] текст\n</cross-session-message>"
  }
}
```

Рекомендации:

- `from-name` — короткий slug имени сессии-отправителя rocket
  (`claude-code-orch`), он же попадает в шапку у получателя;
- тело оставляем уже отпрефиксованным (`[from ...] ...`) — это работает и
  когда конверт по какой-то причине не распознался;
- `from-mode` **не** ставим (§5.2);
- `session_id` ставим всегда: он превращает гонку «pid переиспользован» из
  «сообщение ушло чужой сессии» в «сообщение отброшено»;
- `hop-chain` / `from-session` не ставим.

## 9. Хрупкость по версиям

Что выглядит стабильным (описано в публичной документации фичи, завязано на
формат файлов и системные ограничения):

- реестр `~/.claude/sessions/<pid>.json` и ключевые поля в нём;
- расположение сокета `.../cc-socks/<pid>.sock` и права `0700`/`0600`;
- NDJSON-кадрирование и поля `type` / `message.role` / `message.content`;
- отсутствие рукопожатия и отсутствие ответа в том же соединении;
- наличие трёх исходов delivered / held / refused и настройки
  `crossSessionInbound`.

Что может поехать при обновлении CLI:

- **`peerProtocol`** — прямой сигнал версии. Сейчас `1`; при росте значения
  считать нашу реализацию несовместимой, пока не перепроверили.
- Точный синтаксис конверта: порядок атрибутов, набор атрибутов
  (`from-mode` появился недавно), экранирование. Разбор на приёмнике
  строгий и с побайтовой пересборкой — любая правка формата ломает атрибуцию
  (но не доставку: текст всё равно дойдёт, просто без шапки).
- Значения антифлуда — они уже сейчас управляются серверным флагом
  `tengu_harbor_kite_limits`, то есть меняются без релиза CLI.
- Условия отправки квитанций (требование «тот же каталог» + `.sock`)
  выглядят как реализационная деталь, а не как контракт.
- `file_attachments` — активно развивающаяся часть, в спайке не покрыта.

Практический вывод: наша реализация должна деградировать мягко — при
`peerProtocol != 1`, отсутствующем `messagingSocketPath` или неудачном
`connect` откатываться на tmux-инжект, а не считать доставку выполненной.

## 10. Проверка

Прототип: `internal/socketmsg` (+ ручной драйвер `cmd/ccsend`).

```
$ go run ./cmd/ccsend list
PID    ALIVE  KIND         NAME                                  STATUS  PROTO  SOCKET
...
65366  live   interactive  claude-code-spike-socket-protocol-8c  busy    1      /tmp/cc-socks/65366.sock

$ ./ccsend listen /tmp/cc-socks/rocket-spike.sock &
слушаю /tmp/cc-socks/rocket-spike.sock (адрес uds:/tmp/cc-socks/rocket-spike.sock)

$ CCSEND_REPLY_SOCKET=/tmp/cc-socks/rocket-spike.sock CCSEND_NAME=rocket-spike \
    ./ccsend send 65366 "[from rocket-spike] E2E-проверка UDS: ..."
```
